## 4. Simpler alternative

[MAJOR] §4.3 introduces a second in-tx read mechanism beside §4.4's merge cursor: set arithmetic over `searchSnapshotBase`, a JSON-array parameter through `json_each` (new SQL surface, needs a driver-pinning test), and a per-backend `GROUP BY state` twin — three formulas that must agree with the cursor's view. Counting over the §4.4 cursor itself (committed rows selecting `entity_id, state` only, merged with the buffer, deletes excluded) is O(1) memory, one code path, no new SQL, and by construction agrees with `Iterate`/`GetPage`. The property §1 states is "no payload bytes copied beyond what they return", not O(buffer) time, and the doc records no reason for preferring the arithmetic. — §4.3 — either count over the merge cursor (id/state projection) or write down why in-tx count latency must be O(buffer) rather than O(model-ids); "consolidate, don't leave two in-tx read paths" is the default.
[MINOR] §2.3's submit-time dry-run adds a translation per submit to reach a 400 that §2.1 itself calls unreachable from validated input, while the execution-time path already fails the job closed (`writeAsyncFailure`). The alternative — no dry-run — is not recorded as considered. — §2.3 — either drop it (the job fails closed, `path-grammar.md` §11 "An async job fails rather than answering short" is already satisfied) or state what the dry-run buys that "unreachable" does not.
