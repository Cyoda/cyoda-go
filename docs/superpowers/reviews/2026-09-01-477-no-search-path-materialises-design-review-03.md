## 2. Invariants

Touched: `.claude/rules/correctness-over-availability.md`, `.claude/rules/multi-node-primary.md`, `.claude/rules/tdd.md`, `.claude/rules/test-coverage.md`, `.claude/rules/documentation-hygiene.md`, `.claude/rules/security.md`, CLAUDE.md Gate 7 and the backend-parity sentence, `docs/cloud-parity/direct-search-bounded-or-fail.md`, `tx-aware-search.md`, `path-grammar.md` §11, `operator-semantics.md` (semantics unchanged).

[CRITICAL] §4.2 pins a delete-then-`CompareAndSave` outcome the backends do not share, and never states which outcome is the contract. As written, memory and sqlite compare the CAS against the committed row only (memory `entity_store.go:220-237`; sqlite `:375-383`, "Check CAS against committed store (not buffer)"), so after a same-tx `Delete` the CAS passes, `unstageDelete` clears the delete, and the entity commits present. Postgres executes the in-tx delete immediately and re-stamps the tombstone's `transaction_id` with the deleting transaction (`plugins/postgres/entity_store.go:340-385`, "its TransactionID is stale unless overwritten here"), and its CAS reads `transaction_id` without excluding tombstones (`:168-189`), so the same sequence answers `ErrConflict` and the entity stays deleted. Pinning this in `Transaction/DeleteThenCompareAndSave` therefore bakes a divergence into the conformance suite, against CLAUDE.md: "A storage backend (memory/sqlite/postgres) diverging from the others on the same contract is a bug to fix, not an 'accepted divergence'" — §4.2, §6 — state the oracle as "CAS compares against the transaction's own view: a same-tx delete (or save) is the current latest", so delete-then-CAS answers `ErrConflict` on every backend; make memory/sqlite CAS consult `tx.Deletes`/`tx.Buffer` before the committed row; keep `unstageDelete` for `Save` only; and run the case against all three in-tree plugins before the SPI commit is pinned.
[MAJOR] §4.2 claims the outcome "is reachable over the wire (`DELETE /entity/{id}` then `PUT` with `If-Match` under one `X-Tx-Token`)". It is not: `updateEntityCore` calls `entityStore.Get(txCtx, input.EntityID)` first (`internal/domain/entity/service.go:2213`) and a same-tx delete makes that `ErrNotFound`, answering `404 ENTITY_NOT_FOUND` before `CompareAndSave` (`:2371`) is reached; the PR-3 HTTP parity scenario would pin a 404, not the CAS outcome — §4.2, §6 — drop the HTTP scenario (or restate it as pinning the 404) and keep the pin at the spitest seam.
[MINOR] `correctness-over-availability.md` ("never with a substituted or fallback value standing in for the correct one"): satisfied — the fallback is deleted, translation failure fails closed, and a missing `Iterate` becomes a compile error — §2, §3 — none.
[MINOR] `security.md` ("Every data path must be verified for cross-tenant leakage"): satisfied — the §4.4 cursor is built on `searchSnapshotBase`, which binds `tenant_id`, and `TenantIsolation/GetPage` is added — §4.4, §3.3 — none.
[MINOR] Gate 7: `direct-search-bounded-or-fail.md` invariant 2 currently tells Cloud "`limit <= 0` is a deliberate request for the complete matched set", while the wire already answers `400 BAD_REQUEST` for `limit < 1` (`handler.go:137`; `grpc/search.go:354`); §8 edits the file but does not say what replaces the invariant — §8 — write the replacement rule Cloud must mirror ("`limit < 1` is rejected at the boundary; the engine, not the plugin, supplies the default") in the same edit.

## 3. Completeness

[MAJOR] §2.3 says an execution-time translation failure "can only mean the schema changed after submission", and §6 carries a row "execution-time failure → job FAILED". `spi.ConditionToFilter` fails only on a nil condition, a `FunctionCondition`, an unsupported type, or path grammar (`condition_filter.go:148-181`); none of those reads `fields`, so a condition that translated at submit cannot fail translation at execution, and the row has no seam to drive it (package function, no double) — §2.3, §6 — keep the fail-closed branch, correct the sentence ("cannot occur; the branch is a guard"), and replace the row with a direct test of the branch's classification through `writeAsyncFailure` or a one-line waiver.
[MINOR] §4.1 says the in-tx `s.db` reads "queue behind the flush, which hides the window". The writer pool is one connection but not FIFO: an in-tx read can take it before `flushToSQLite`'s `BeginTx` (`txmanager.go:453`) does, so the lost-update window is live today, narrow, on `s.db` — §4.1 — record §4.1 as a bug fix in the CHANGELOG, not only a prerequisite.
[MINOR] Equal-microsecond edge the design is silent on: `Begin` floors `SnapshotTime` to `lastSubmitTime`; a commit in the same microsecond after `Begin` gets `submitTime == SnapshotTime` (`max(now, last+1)` with `now == SnapshotTime`, `:353-366`), so its rows satisfy `submit_time <= SnapshotTime` and are visible iff flushed before a given cursor opens — two snapshots inside one transaction (FCW's `>=` still catches conflicts, so no lost update) — §4.1 — under `commitMu`, have `Begin` reserve its snapshot (`lastSubmitTime = max(lastSubmitTime, snapshot)`) so every later commit's `submitTime` is strictly greater.
[MINOR] §4.4 states the pool assumption for one consumer only. In-tx cursors now hold a `readDB` connection for their lifetime and contend with non-tx `GetPage` (`:1108`), `GetVersionMetadata` (`:1401`) and async `GetResultIDs` (`search_store.go:228`) for `readers` connections, and an open cursor pins the WAL checkpoint — §4.4 — state both as availability-only effects, and that the engine's in-tx consumers (`selectDeleteIDs`, `getPageTx`) close promptly.
[MINOR] §4.5's "records nothing" rule: the engine never calls `GroupedAggregate` in a transaction (`grouped_stats_service.go:262`, `!inTx`), so the rule governs only direct SPI callers and the spitest pin is its sole consumer — §4.5 — say so; it is the justification for choosing "nothing".
[MINOR] §2.2 is silent on error precedence when `it.Close()` fails after the `Limit + 1` raise — §2.2 — the 400 wins; the close error is logged.
[MINOR] §3.4 lists `searcher.go` and `iterable.go` but not `condition_filter.go:59-62`, which still calls a `FunctionCondition` translation failure "the signal to fall back to in-memory evaluation" — §3.4, §9 — add it, plus an exit grep for "fall back" over the SPI's non-test files.
