# Audit events: identity and a fixed order — design

Issue: cyoda-go#586. Milestone v0.9.0. Branch base `release/v0.9.0`.

## 1. Problem

`GET /audit/entity/{entityId}` returns the audit trail of one entity. It
merges two kinds of event:

- **Entity change event** — one per stored version of the entity (create,
  update, delete).
- **State machine event** — one per step the workflow engine recorded for the
  entity (transition made, processor result, finish, and so on).

No emitted field separates two events of the same transaction. Every event of
one transaction carries that transaction's commit instant — the parity
scenario `RunAuditCommitInstantSharedWithVersionHistory`
(`e2e/parity/audit.go:197`) requires it. `transactionId`, `actor`,
`changeType` and `severity` are shared or constant. So when one transaction
saves an entity twice, the two entity change events are identical, and a
consumer cannot tell them apart or tell them from one row served twice.

Paging makes this worse. The cursor is an offset into a list rebuilt per
request, and the list is sorted on `utcTime` alone with an unstable sort
(`internal/domain/audit/handler.go:148-153`), so events of one instant come
back in an arbitrary order that can change between requests. An offset walk
over that list can repeat or skip rows even when no new event arrives.

## 3. Cyoda Cloud today

Read from `~/dev/cyoda`:

- Neither audit DTO carries a version or an event id
  (`client/src/main/resources/api/openapi-audit.yml:604-712`). The platform
  keeps a `timeUuid` per event and uses it only to derive `microsTime`.
- A state machine event's `timeUuid` is generated by the engine's event
  factory, not the DAO; it is the Cassandra clustering key.
- Order: `microsTime` DESC, then `auditEventType` name ASC (EntityChange
  before StateMachine), then each source's own order
  (`backend/.../audit/EntityAuditInteractor.kt:281-293`).
- Cursor: base64 JSON of a per-source offset — the same shifting window.

## 4. Design

### 4.1 Two new fields

- `EntityChangeAuditEventDto.version` — `integer`, `int64`, required. The
  entity's version number for that change. Strictly increasing over the
  entity's whole history, including across delete and recreate.
  `(entityId, version)` identifies one entity change event.
- `StateMachineAuditEventDto.eventId` — `string`, `format: uuid`, required.
  A time-based UUID (RFC 9562 version 1) assigned by the store when it
  recorded the event. Unique per event; the same value on every read.

Both endpoints that return a state machine event emit `eventId`: the search
and `GET /audit/entity/{entityId}/workflow/{transactionId}/finished`. One
builder function produces the state machine event map for both (today the
code is duplicated, `handler.go:127-141` and `:266-280`).

### 4.2 The store owns the state machine event id

The event id is server-determined metadata, so it belongs to the store, as
for entity metadata: a caller's value is ignored.

Contract (SPI doc comment on `StateMachineAuditStore` and
`StateMachineEvent.TimeUUID`): `Record` assigns a new time-based UUID to the
event and ignores any `TimeUUID` the caller set. `GetEvents` and
`GetEventsByTransaction` return that id in `TimeUUID` on every event, the
same on every read. `Record` returns an error if it cannot generate one.

- **postgres, sqlite:** `Record` always generates the id with the plugin's
  injected `UUIDGenerator`, writes it into the document and the `event_id`
  column. Reads set `TimeUUID` from the `event_id` column, the same way the
  `timestamp` column already overrides the document copy.
- **memory:** `Record` generates the id with the injected generator, threaded
  from the plugin into the store factory (the transaction manager already
  holds one).
- **cassandra:** already assigns in `Record`. No change expected; the new
  conformance case checks it at cassandra's next SPI pin bump.
- **engine:** stops setting `TimeUUID` at both record sites. The
  `transition_aborted.go` helper loses its `uuids` parameter if nothing else
  uses it.
- **SPI conformance** (`spitest/audit.go`), new case `Audit/EventID`: record
  two events with no id and one with a caller-set id; `GetEvents` returns
  three non-empty, distinct ids that parse as UUIDs; none equals the
  caller-set value; a second `GetEvents` returns the same ids; 
  `GetEventsByTransaction` returns the same ids for its subset.
- **Existing tests** asserting the caller's id comes back are rewritten
  (`plugins/postgres/sm_audit_store_test.go:71-75,131-132`, and any sqlite or
  memory equivalents found in the plan).

Rejected alternative: the caller must supply the id and the store rejects an
empty one. It contradicts the store-owns-metadata ruling, needs a Cassandra
change, rewrites every existing conformance case, and adds an error path only
a bug can reach.

### 4.3 memory: versions never repeat

memory numbers a new version (save path and commit-time tombstone path) from
the last row of any kind, tombstones included, matching the other backends.

New SPI conformance case `Entity/GetVersionMetadata/RecreateAfterDelete`:
create, delete (committed), save again; `GetVersionMetadata` returns three
rows whose versions are distinct and strictly decrease newest first.

### 4.4 One total order

The handler sorts the merged list by:

1. `utcTime` DESC, at stored precision;
2. `auditEventType` ASC — EntityChange before StateMachine (Cloud's
   tie-break);
3. entity change events: `version` DESC;
4. state machine events: the time field of `eventId` DESC, then the
   UUID's 16 bytes DESC.

Every event has a distinct key, so the order is total and the same on every
request over the same data. For entity change events of one instant it is the
save order. For state machine events of one instant it is fixed but not
promised to be the recording order: two version-1 UUIDs taken in the same
100 ns tick differ only in a wrapping 14-bit clock sequence, and a clock
step backwards inverts two ids. The contract says "deterministic", no more.

### 4.5 The cursor is a position

`nextCursor` encodes the sort key of the last event on the page: a format
tag, `utcTime`, `auditEventType`, and `version` or `eventId`, as URL-safe
base64 of JSON. The next page is the events strictly after that key under the
same comparator as the sort. The cursor stays an opaque string on the wire.

- The key does not depend on the filters. Changing filters between pages is
  well defined: the walk continues from that position under the new filters.
- A cursor whose event has since been deleted still positions correctly.
- `hasNext` is true when any filtered event follows the page.
- A cursor that does not decode or does not validate — bad base64 or JSON,
  unknown tag, unknown `auditEventType`, a non-UUID `eventId`, a `version`
  below 1, a missing field — answers `400 BAD_REQUEST`. Today it silently
  restarts from the first page, which is a substituted answer.
- An offset cursor from a previous build (`"20"`) no longer decodes and
  answers 400. There are no production instances; the changelog declares it.

Guarantee: for events committed before a walk starts, read outside a
transaction, the walk returns each event exactly once, in the order of 4.4.
Nothing stronger is claimed. memory and sqlite write state machine events
through before commit and restamp them to the commit instant at commit, and
postgres reads the commit instant before `COMMIT`, so an event that commits
during a walk can land behind the cursor and be missed. The help topic says
so. `limit` above 1000 stays clamped to 1000 as documented in
`cmd/cyoda/help/content/audit.md`; `hasNext` tells the caller more exist.

### 4.6 Fail closed on a state machine audit read failure

When state machine events are requested (no `eventType` filter, or one that
includes `StateMachine`), a failure of the `StateMachineAuditStore` factory
call or of `GetEvents` answers through `common.Internal`: 503
`STORAGE_UNAVAILABLE` (retryable) for a storage outage, 500 otherwise, with a
generic message and ticket id, the same as the finished endpoint. A request
for EntityChange only does not call the state machine audit store.

## 6. Coverage matrix

gRPC: no audit surface (F10), so every row is n/a there.

Two saves of one entity in one transaction are produced by a processor callout
whose compute member makes two joined updates of a secondary entity inside
the originating transaction (F11). The in-tree test compute node gets a
processor that does this if none exists.

| Scenario | unit (handler) | e2e (postgres) | parity (all backends) | SPI conformance |
|---|---|---|---|---|
| entity change event carries `version`; two joined saves in one transaction → two distinct versions | yes | yes | yes | — |
| state machine event carries `eventId`; distinct; same on a second read | yes | yes | yes | — |
| finished event's `eventId` equals the same event's id in the search | — | yes | yes | — |
| ties in one instant: EntityChange before StateMachine, versions DESC, eventIds DESC | yes | yes | yes | — |
| walk page by page (limit 1) over a same-instant tie of both kinds: each event once, in order | yes | yes | yes | — |
| a new transaction commits mid-walk: no repeat, no skip of events committed before the walk | yes | yes | — (not concurrency; single-backend) | — |
| create → delete → recreate: three distinct increasing versions in the audit trail | — | yes | yes | `RecreateAfterDelete` |
| undecodable cursor (bad base64 / JSON / old `"20"`) → 400 `BAD_REQUEST` | yes | yes | — | — |
| decodable but invalid cursor (unknown type, non-UUID `eventId`, version 0) → 400 | yes | yes | — | — |
| state machine audit store factory fails → 503 (outage) / 500 (other) | yes (stub) | — ¹ | — | — |
| state machine `GetEvents` fails → 503 / 500 | yes (stub) | — ¹ | — | — |
| EntityChange-only request with the state machine store failing → 200 | yes (stub) | — ¹ | — | — |
| store assigns the id, ignores the caller's, same on every read | — | — | — | `Audit/EventID` |

¹ A store outage cannot be produced on a live backend without fault injection;
the unit stubs follow the existing `handler_outage_test.go` pattern.

- `api/openapi.yaml`: both fields (in the subtype `required` lists), the
  `cursor` parameter and `nextCursor` descriptions; `go generate ./api`.
- Parity client: the strict flat decode structs and the testdata fixtures in
  `e2e/parity/client` learn both fields.
- `cmd/cyoda/help/content/audit.md`: fields, order, cursor semantics and its
  limit; the example's `"nextCursor": "20"` replaced.
- `CHANGELOG.md`: Added (fields), Changed (order; cursor format — old cursors
  answer 400), Fixed (state machine audit read failure no longer returns a
  partial trail; memory version reuse after delete/recreate).
- `docs/cloud-parity/audit-event-identity-and-order.md` + a README row;
  Cloud Jira ticket (project CP, `[CaaS]`) for Cloud to add both fields, the
  tie-break chain and a position cursor.
- SPI: doc comments + two conformance cases in a PR into `cyoda-go-spi`
  `main`; cyoda-go and the in-tree plugins pseudo-pin that commit
  (`make repin-plugins`). No tag mid-milestone. `COMPATIBILITY.md` changes
  at the tag.
