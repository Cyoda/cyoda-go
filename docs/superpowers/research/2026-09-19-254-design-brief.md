# Trying another compute node when a callout cannot be delivered — design brief

The design for issue #254 as agreed with Paul on 2026-09-19, in plain language.
It is written to be read on its own, and to be handed to an independent
reviewer before the detailed specification is written. The file-and-line
evidence behind every statement about today's code, and about Cyoda Cloud, is in
the companion document `2026-09-18-254-retry-policy-member-failover-research.md`.

## What this is about

When a workflow needs a calculation done outside the platform, cyoda-go sends
the work to a program the customer runs. Today it sends it once, to one such
program, and if anything goes wrong the customer's whole operation fails — even
when another copy of that program is connected and healthy. This change makes
cyoda-go try another one, where that is safe, and tell the client honestly what
happened where it is not.

It also repairs the way the processes of a cluster tell each other what they
host (part two, at the end), which breaks silently at a size a modest deployment
reaches, and on which the first part depends.

## The words used here

- **pnode** (processing node) — one running cyoda-go process. A **cluster** is
  several pnodes working together.
- **cnode** (compute node) — the customer's program. It connects to exactly one
  pnode, says which customer (**tenant**) it belongs to, and announces **tags**:
  labels such as `pricing` that say what work it can do. Several cnodes may
  announce the same tag, and one pnode may have several cnodes attached. Every
  connection gets a fresh identity, so a cnode that drops and reconnects counts
  as a new one.
- **Callout** — one piece of work sent to a cnode. There are three kinds: run a
  **processor**, evaluate a **criterion**, or run a **function** that computes
  when a scheduled transition should fire. The workflow names the tags it needs.
- **Transaction** — the unit of work a callout happens inside. For the common
  kind of processor it stays open while cyoda-go waits for the answer. While it
  works, a cnode may call back into the platform to read and write other data,
  and those calls **join that open transaction**.
- **Owner** — the pnode where the customer's operation arrived and where its
  transaction lives.

## How it works today, and what goes wrong

On one pnode: it picks whichever matching cnode it finds first, sends the work,
waits for the answer or a time limit. One try; any failure fails the operation.

In a cluster: each pnode knows in detail only its own cnodes. About the others
it knows one coarse thing — "that pnode has at least one cnode for tenant T with
tag X" — which pnodes tell each other over the cluster's membership channel, the
same channel that tells them which pnodes are alive. The owner looks at its own
cnodes first. Only if it has *none* with the tag does it hand the work to a
randomly chosen pnode that advertises the tag, which picks one of its own
cnodes. If no pnode advertises the tag, the owner waits up to five seconds in
case one appears.

What goes wrong:

1. One failure is final, even with a healthy cnode connected right beside it.
2. If the owner has a matching cnode and that one fails, other pnodes are never
   asked — they are consulted only when the owner has no match at all.
3. A cnode can answer "I failed, and a retry would help" or "…a retry is
   pointless". cyoda-go reads that verdict and drops it; the client always sees a
   plain failure marked "do not retry".
4. When the failing cnode is on another pnode, even its error message is lost:
   the client is told only that the other pnode's callout failed.

## What Cyoda Cloud does

Cloud keeps the full list of every cnode on every pnode, and the owner picks one
specific cnode itself, preferring its own. One retry loop on the owner: never
the same cnode twice, a fixed pause before every retry, four tries in all, and
"no cnode available" counts as a failed try so that one which connects in the
meantime picks the work up. It moves on to another cnode after *any* failure
except a cnode answering "I failed" without saying a retry would help — so also
after a timeout or a dropped connection. It passes no verdict on to the client.

Reading Cloud's code also showed what not to copy: nothing cleans up the cnodes
of a pnode that dies, a pnode that joins later never learns of existing cnodes,
and several failures on the far side only surface when the owner's time limit
expires. cyoda-go's membership layer already detects dead pnodes, and — unlike
Cloud, where a cnode's calls back into the platform run as separate
transactions — cyoda-go's join the transaction. That last difference is what
makes blind retrying unsafe here.

## The design

### 1. One dividing line: did the work reach a cnode?

A cnode that was given the work and then went quiet has not necessarily stopped,
and what it has already done does not go away. That matters in two ways, and the
second is the larger:

- **Inside cyoda.** A cnode's callbacks join the open transaction, so it may
  already have written into it and may still be writing. A second cnode given
  the same work could commit the processor's writes twice.
- **Outside cyoda.** A processor is the customer's code and may act on systems
  cyoda-go knows nothing about — charge a card, send a message, call another
  service. None of that is part of any cyoda transaction. Rolling the
  transaction back does not undo it, and running the processor again repeats it.

cyoda-go cannot solve the second in general. Making an action outside cyoda safe
to repeat, or undoing it when the operation fails, belongs to the application's
own design — a compensating step, a saga, a key the external system uses to
recognise a repeat. What cyoda-go can do is never repeat a processor on its own
initiative unless the author has said a repeat is safe, and report honestly what
happened. **The consequences of a failed or repeated callout are therefore not
confined to cyoda**, and nothing in this design should be read as if a rollback
made a failure harmless. So:

- **The work never reached a cnode** — no matching cnode attached; the cnode was
  gone before the send; the work could not be put on its connection; a
  connection to the other pnode could not be opened; the other pnode said in so
  many words that it delivered nothing, or that it had no cnode. No cnode has
  touched the transaction. **Try another.** (Only such an explicit statement
  counts. An error answer of any other kind from another pnode proves nothing: a
  pnode that fails *after* handing the work to its cnode also answers with an
  error.)

  The code draws this line exactly. A pnode hands work to a cnode's connection
  in one step that reports whether the hand-off happened: if it reports failure
  the work provably never left the pnode; once it succeeds the work may have
  reached the cnode, whatever happens next. Today both sides of that line
  produce the same errors ("disconnected", "timed out"), so the change adds a
  marker that tells them apart — inside a pnode, and in what one pnode reports
  to another. A connection to another pnode that was opened and then broke, or
  went unanswered, falls on the *other* side of the line: the work may have
  reached a cnode there. (Today such a break is followed by a try on the next
  pnode regardless, which for a processor can run it twice.)
- **The work reached a cnode, and then no answer came in time, or its connection
  dropped.** Whether to try another depends on whether a repeat is safe:
  - a **criterion** or a **function**: always safe — they compute, they do not
    write. Try another.
  - a **processor marked `idempotent`** in the workflow: the author has declared
    a repeat safe. Try another. This is Cloud's behaviour.
  - a **processor not so marked** (the default): do not try another. The
    operation fails and the transaction is rolled back, which removes anything
    the cnode wrote *inside cyoda* and nothing it did outside. The failure is
    marked "try again later", as the same timeout and disconnect are today. That
    mark speaks for cyoda only: cyoda's own state is clean for a re-run. Whether
    a re-run is safe for whatever the processor did outside cyoda is for the
    application to know.
- **The cnode answered "I failed".** Stop at once, wherever that cnode is, and
  pass its message and its verdict to the client. With "a retry would help" the
  operation fails *marked retryable*: another cnode inside the same transaction
  would fail the same way, but the client re-running the whole operation can
  succeed. Without it, the operation fails as today.

### 1a. A cnode's pass into the transaction ends with its callout

Giving up on a cnode does not stop it. Its *answer*, if it comes late, is already
thrown away. But while it works a cnode makes ordinary calls back into the
platform — create, update, search — and each carries a pass that names only the
transaction. Nothing can tell a write from a cnode that was given up on from a
write by the cnode now doing the work, so such a write is accepted for as long as
the transaction is open — and the transaction may go on to commit: when a second
cnode takes over an idempotent processor, and, today already, in the processor
mode where a failed callout does not fail the operation. A write that arrives
late can land after the writes of a *later* processor and undo them. No promise
of "safe to repeat" covers that.

cyoda-go already has a gate per transaction: a callback that *writes* must hold
it while it touches the transaction, and the engine steps aside for the length of
a callout so that callbacks can get in. The rule that design assumes — *a
transaction is used either by the engine or by the callbacks of the callout in
progress, never both* — is not enforced. This change enforces it. A pass names
its callout, and is good only while that callout is in progress on the owner:

- a callback arriving with the pass of a callout that has ended is turned away at
  the door — reads and searches as well as writes;
- when a callout ends, for whatever reason, the owner takes the gate once, which
  waits out any write still in progress;
- a callback that was itself waiting on a callout of its own when its callout
  ended finds that out when it comes back, before it touches the transaction
  again, and is abandoned.

From the moment a callout has ended no callback of it starts, and none is writing
or goes back to writing. (A read already under way may finish.) This lives in the
engine, above the storage plugins, so it holds for every backend without any
plugin changing.

### 1b. The four ways a processor can be run

Where section 1 says "the operation fails and the transaction is rolled back, so
cyoda's own state is clean for a re-run", that is true of the two ordinary modes,
in which the processor runs inside the operation's one transaction. It is not
true of the other two, and the specification sets out each mode separately:

- **The mode in which a failed callout does not fail the operation.** The
  processor runs in a section of the transaction that is undone on failure, and
  the workflow carries on. Trying another cnode works as described. But nothing
  is reported to the client — not the failure, not a cnode's "a retry would
  help" — because the operation succeeds.
- **The mode that commits before calling out.** What the workflow did before the
  callout is already committed and stays committed whatever happens next, and
  in one variant the cnode's callbacks run as transactions of their own. After a
  failure cyoda's state is *not* as it was. This mode is documented today as
  "may run more than once"; that stays, and the "clean for a re-run" wording is
  not used for it.

### 2. What `idempotent` promises

A new yes/no setting on a processor in the workflow configuration, default
**no**. By setting it the author declares: *this processor may be run more than
once for the same callout — possibly only partly, possibly at the same time on
two cnodes — and the outcome is the same as running it once, **in cyoda and in
every system the processor touches.*** Inside cyoda, "set this field to X"
qualifies and "add 10 to the balance" does not. "Create a new entity" does not
either. Without a unique composite key on the model the repeat stores a second
entity. With one, no duplicate is ever stored — but the repeat does not pass
quietly: cyoda refuses the second create, on PostgreSQL at the moment of the
write and on the memory and SQLite backends when the transaction commits, and in
both cases the operation fails with a uniqueness error. The data is safe; the
operation is lost. A processor that creates entities is safe to repeat only if
it first checks whether its entity already exists. Outside, "charge the card" does
not qualify unless the payment system is given a key by which it recognises the
repeat. A processor that only returns a changed entity — no callbacks, no
outside systems — qualifies trivially, and should be marked so that it benefits.

Every try of one callout carries **the same request id**, as in Cloud, so an
author has a ready-made key for making an outside action safe to repeat within a
callout. It does not cover the client running the whole operation again: that is
a new callout with a new id, and needs a key from the application's own data.

Criteria and functions are treated as safe to repeat by definition. That is a
rule for cnode authors — *criteria and functions must have no effects, inside
cyoda or outside it* — which cyoda-go does not enforce today and will not start
enforcing in this change.

### 3. The procedure every pnode runs over its own cnodes

Try the matching cnodes attached to this pnode, one after another, never the
same one twice in one run, stopping at the first real answer or at the first
failure that must not be followed by another try (section 1). **No pause between
one cnode and the next**: a pause helps only when about to look at the same
thing again.

Which cnode comes next is decided by a small replaceable part with one job:
given the matching cnodes, pick one. The first version is **round robin** — it
remembers which one it called last — which spreads the load and makes tests
predictable.

### 4. Across pnodes

The owner runs that procedure first. If it comes up empty and tries remain, it
hands the work to one alive pnode that advertises the tag, **together with the
number of tries left**. That pnode runs the same procedure over its own cnodes
and answers either "done, here is the result" or "I couldn't — here is what
happened, and how many tries I used". The owner then moves on to the next such
pnode with what remains. A pnode that receives handed-over work never hands it
on; only the owner routes. Nothing about which cnodes were tried travels between
pnodes.

What the hand-over has to carry or guarantee, which today it does not:

- **The request id.** Today the other pnode invents its own id for handed-over
  work. For every try of a callout to carry the same id, the owner creates it
  and sends it along.
- **The answer limit.** The owner works out the limit that applies and sends it,
  so that two pnodes with different settings cannot disagree about how long a
  try lasts.
- **How long the owner waits for the other pnode.** Today one setting, 30
  seconds by default. The other pnode may now make several tries, so the wait is
  worked out from the tries handed over and the answer limit, and is longer than
  what the other pnode can take — the owner must never give up on an answer that
  is still coming. Every hand-over opens a connection of its own, with a short
  limit on opening it, so that a pnode that has died is found out at once and
  for certain — rather than after the whole wait, looking just like a pnode that
  took the work and then died.
- **The cnode's pass into the transaction.** Today valid for a fixed 90 seconds
  and refused after that even though the transaction is still open. A pass now
  lasts as long as the try it was issued for, and each try gets its own.
- **A protected answer.** The request between pnodes is encrypted and proven
  genuine; the answer is neither. The answer now decides whether work is tried
  elsewhere, so it gets the same protection.

**The number of tries is the normal number, not a hard limit.** When the other
pnode's answer is lost, the owner cannot know how many tries that pnode made. It
counts one and carries on — where carrying on is allowed at all: for a processor
not marked idempotent a lost answer means the work may have reached a cnode, and
nothing more is tried. The total can therefore exceed the setting in rare cases,
and the documentation for operators and for application developers says so.

**The time a callout may take is a hard limit**, fixed when it starts: tries ×
answer limit, plus the patience, plus a fixed allowance for the exchange between
pnodes. Nothing new is started after it, and whatever is in progress is cut off.
Without it, a pnode that hangs every time it is handed the work would cost about
seven minutes at the defaults — past PostgreSQL's ceiling — because each hang
costs the wait for several tries but counts as one.

On coming back to a pnode it already asked, that pnode may try a cnode it
already tried. That is accepted: it is rare, costs a few seconds, and avoiding
it would need bookkeeping out of proportion to the problem.

No question is ever broadcast. The owner already knows from the membership
channel which pnodes are alive and which advertise the tag, and it contacts only
those, one at a time — as it does today.

### 5. Tries, patience, and the answer limit

Two different things were tangled together in Cloud's design and in the first
draft of this one, and are kept apart here.

**Tries — how many cnodes the work may be handed to.** One number for the whole
callout, however many pnodes take part: `CYODA_RETRY_FIXED_NUM_RETRIES`, the
retries after the first try; default 3, so four tries in all. A workflow author
can switch retrying off for one callout (`retryPolicy: NONE`); then there is one
try. Left unset, retrying is on. There is no pause between one cnode and the
next, so there is no "delay" setting.

**Patience — how long a callout waits for a cnode to exist.** When there is
nothing to try — no matching cnode attached anywhere the owner knows of — the
callout waits for one to appear. That is not a try and costs none. cyoda-go
already has this, for clusters only: the five-second wait governed by
`CYODA_DISPATCH_WAIT_TIMEOUT`. It stays, and becomes the one way of waiting:

- it applies on a single pnode as well as in a cluster;
- it applies whether or not retrying is switched off — waiting for a cnode to
  exist is not a retry;
- it does not poll: the callout wakes the moment something changes — a cnode
  attaches here, or another pnode announces a new list — and looks again;
- it is one allowance per callout, however many times the callout has to wait.

This is what lets a cnode that drops and comes back, or one the customer has
only just started, pick the work up. One visible change: on a single pnode with
no cnode attached a callout fails at once today, and will now wait out the
patience first. A development set-up that wants the old behaviour sets it to 0.

**The answer limit — how long a pnode waits for one cnode's answer.**
`responseTimeoutMs`, set by the workflow author per processor, per criterion
function and per scheduled-transition function. Two environment properties
frame it: `CYODA_CALLOUT_RESPONSE_TIMEOUT_MS`, the limit used when the author
sets none (default 30000; today a constant in the code), and an upper bound on
what an author may set, checked when the workflow is imported. The upper bound
is the open issue #565, taken into this change because tries multiply the
answer limit: without a bound, four tries at a generous limit outlast the one
ceiling a transaction has.

That ceiling is PostgreSQL's. cyoda-go itself puts **no time limit on a
transaction**; PostgreSQL reclaims a connection that sits idle inside one for
five minutes (a setting), and the operation then fails as "storage unavailable,
try again". Waiting for a cnode is such an idle stretch. The memory and SQLite
backends have no ceiling.

The longest a callout can hold a transaction is therefore tries × answer limit +
patience + the allowance for the exchange between pnodes — at the defaults four
× 30 seconds + 5 + 30, a little over two and a half minutes; with the answer
limit at its upper bound, a little over four and a half. That is a hard limit
(section 4), and it stays inside PostgreSQL's five minutes. The documentation
will state it.

### 6. What the client sees

- All tries used up: one error listing what happened on each try, repeats
  collapsed, marked "try again later". A single failure is reported as itself,
  not wrapped.
- No cnode appeared within the patience: "no cnode available", marked "try again
  later", as today.
- A cnode answered "I failed": the workflow-failed error as today, now carrying
  the cnode's own message even when the cnode was on another pnode, and marked
  retryable when the cnode said a retry would help.
- A processor not marked idempotent that went quiet after receiving the work:
  the same timeout or disconnect error as today, marked "try again later".

### 7. What changes in the workflow configuration

- `idempotent` on a processor (new, default no).
- `retryPolicy` on a scheduled-transition function (new; processors and criteria
  already have it).
- `retryPolicy` on a criterion is checked on import, as it already is on a
  processor. Today any value is accepted there and ignored.

These are additions, so the workflow schema version goes from 1.4 to 1.5 and
older workflows stay valid. Every storage backend keeps a workflow as one
document, so none of them needs changing. One shared type definition gains two
fields, which needs a release of the shared interface module.

## The scenarios

Cluster: pnodes P1, P2, P3. Tenant Acme; tag `pricing`. The operation arrives at
P1, so P1 is the owner. Four tries; patience five seconds. The workflow author
has set the processor's answer limit — `responseTimeoutMs`, a setting on the
processor in the workflow configuration — to 5 seconds. The processor runs in
one of the two ordinary modes (section 1b).

1. **All healthy.** `c1` on P1 answers. One try — as today.
2. **The work cannot be given to a local cnode; another local one is fine.**
   `c1` has just dropped; P1 finds out as it goes to send. It moves straight on
   to `c2`, which answers. No other pnode involved. Today this fails. (A cnode
   that is attached but not taking data is slower to detect: the hand-off waits
   up to the answer limit before giving up. It still counts as never reached.)
3. **The owner has nothing; another pnode does.** P1's only cnode is gone before
   the send. P1 hands the work to P2 with "3 tries left"; P2's `c3` answers.
4. **The first cnode on another pnode cannot take the work.** P1 has none. P1
   hands the work to P2 with "4 tries left". P2 cannot put it on `c3`'s
   connection, moves to `c4`, which answers. One exchange between P1 and P2.
5. **Nothing anywhere, then a cnode appears.** No `pricing` cnode is attached.
   P1 has nothing to try and waits. Two seconds later the customer's `c5`
   attaches to P3; P3 announces it, P1 wakes, hands the work over, and `c5`
   answers. No try was used while waiting. Without `c5`, the operation fails
   after five seconds with "no cnode available", marked "try again later". The
   same happens with retrying switched off, and on a single pnode.
6. **A pnode cannot be reached.** P2 has just crashed and is not yet marked dead.
   Opening the connection fails, or runs into its short limit; P1 goes to the
   next pnode advertising the tag. No try is used: nothing was handed to a
   cnode. Seconds later P2 is marked dead and no longer considered.
7. **A cnode goes quiet after receiving the work — processor not marked
   idempotent.** `c1` gets the work and does not answer in 5 seconds. Nothing
   else is tried. The operation fails, marked "try again later"; the transaction
   is rolled back, taking with it anything `c1` wrote inside cyoda. If `c1`
   calls back later, its transaction no longer exists and the call is refused.
   Anything `c1` did outside cyoda — a payment, a message — stands, and is the
   application's to reconcile.
8. **The same, processor marked idempotent — or a criterion, or a function.**
   P1 moves on to `c2`, which answers. The operation succeeds, after 5 seconds.
   While `c2` works, a callback from `c1` is still accepted — two cnodes working
   at once is what the author's promise covers. Once `c2` has answered the
   callout is over and its passes are closed: if `c1` wakes up after that and
   calls back, the call is refused, though the transaction is still open.
9. **A cnode answers "I failed".** Stop. With "a retry would help" the client
   gets a retryable failure with the cnode's message; without, a plain one. The
   same whether the cnode was on P1 or on P2.
10. **Retrying switched off in the workflow.** One try. As today, except that the
    cnode's message and verdict survive.

Tenant isolation: a pnode only ever picks among the cnodes of the tenant named in
the request, and what it reports back names only cnodes of that tenant.

## What this does not include

- Making a processor's actions outside cyoda safe to repeat, or undoing them
  when an operation fails. That cannot be solved generically here; it is the
  application's design (a saga, a compensating step, a key the outside system
  recognises). cyoda-go's part is the `idempotent` setting, the stable request
  id, and an honest account of what happened. The help text for processor
  authors must say this plainly.
- A cluster-wide list of cnodes on every pnode, as in Cloud. Worth having for
  its own sake — the admin listing shows only the cnodes of the pnode you ask —
  but a feature of its own.
- Enforcing that criteria and functions do not write.
- Choosing cnodes by load. The picker is replaceable so that this can come later.
- The part of the issue about processors that answer asynchronously: importing
  such a workflow is refused today, so there is nothing to switch off.

## Where this departs from Cloud, for the alignment record

cyoda-go defines the contract and Cloud follows, so each of these is logged for
the Cloud team: the `idempotent` setting and its default (Cloud today behaves as
if every processor were idempotent); the cnode's verdict reaching the client
(Cloud passes none); no pause between one cnode and the next, and no delay
setting (Cloud pauses before every retry); waiting for a cnode to exist as a
separate allowance that costs no try (Cloud counts "no cnode" as a try); the
number of tries as the normal number rather than a hard limit; a cnode's pass
ending with its callout; an upper bound on the answer limit; `retryPolicy` on
scheduled-transition functions.

## Part two: how pnodes tell each other what they host

Found while researching the above, and fixed as part of this issue, because
everything above depends on it: the owner can only hand work to a pnode it can
see.

### What is wrong

Cluster membership is provided by a library. It lets each pnode publish a short
description of itself, which the library spreads to every other pnode in small
network packets sent many times a second. To keep several descriptions to a
packet, the library caps a description at **512 bytes**. That is a constant in
the library, not a setting.

cyoda-go puts two things in that description: who the pnode is (its id and its
two addresses — about 70 to 100 bytes), and **every tenant that has a cnode
attached to it, with that tenant's tags**. The second part grows without limit.
With ordinary 36-character tenant ids and one short tag each, the **eighth**
tenant takes a pnode over the limit; with the longest tenant ids allowed, the
fourth.

When that happens the pnode publishes an *empty* description, and:

- every other pnode can no longer read who it is, and drops it from its view;
- so no callout is ever handed to it — for *all* its tenants, not just the one
  that tipped it over;
- a cnode attached to it that calls back into its transaction through another
  pnode is refused, because that pnode cannot find the owner;
- the scheduler stops giving it work;
- it drops out of its *own* view as well. If every pnode is over the limit,
  every view is empty, each pnode concludes it is the one in charge of scheduled
  work, and each due scheduled transition fires once per pnode;
- nothing reports it. The publishing step says it succeeded, so nothing tries
  again; the only trace is one warning line in the log. The architecture
  document lists the limit and says "monitor and alert", which nothing does.

(Established by reading the code and working out the sizes from the real message
format; not yet reproduced by running it. The first test written will do that.)

### The fix

Keep in the 512-byte description only what is small and fixed: who the pnode is.
Move what grows — tenants and tags — to the way the same library provides for
data of any size.

- **Who the pnode is** stays where it is. Its size depends only on the
  operator's settings (the pnode's id and addresses), so it is checked once at
  startup, and a pnode whose identity would not fit **refuses to start** with a
  clear message, rather than running invisibly.
- **What it hosts** is sent, whenever it changes, directly to each other pnode
  over the library's reliable connection, which has no size limit. Each message
  carries the pnode's complete current list and a number that only goes up, so
  that a message overtaken by a newer one is recognised and ignored. Clusters
  are 2 to 20 pnodes and cnodes attach and detach rarely, so one short message
  per pnode per change is cheap.
- **Catching up and repairing.** A sent message is not proof of a received one.
  So each pnode also puts the number of its current list — a few bytes — in its
  small description, which the library spreads quickly and reliably on its own.
  What a pnode announces there is the authority: a pnode that holds a list with
  a *different* number from the one announced, or none, asks that pnode for it.
  "Different", not "older", so that a pnode restarted under the same name — the
  normal case under Kubernetes — is never taken for an older version of itself,
  even if its clock went backwards. One mechanism covers a lost message, a
  restart, a pnode that joins late — which Cloud's design never catches up — and
  a pnode that was briefly cut off.
- **A pnode that dies** is detected by the library as it is today. Its list is
  dropped with it, so work is never handed to it.

A view that is briefly out of date is harmless under the callout design: a pnode
believed to host a tag that no longer does answers "I couldn't, I have none" and
the owner moves on; one that hosts a tag the owner has not heard of yet is found
as soon as its list arrives, which wakes any callout that is waiting.

Everything on this channel is encrypted with the cluster's shared secret, as the
current description is; the independent review confirmed this in the library's
source for the reliable connection as well.

Along the way: the publishing step today can block for several rounds of the
membership protocol, and while it does, later changes queue up behind it; that
goes away with the move. And tags are currently published in a random order, so
an unchanged list can look changed; they will be sorted.

### What this does not include

A list of individual cnodes on every pnode. Pnodes still tell each other only
"tenant T, tag X", as today. The new channel would carry such a list if it is
wanted later.
