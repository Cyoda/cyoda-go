# #649 design brief: consistency time for point-in-time reads

Draft, revised after one fresh-context design review, 2026-10-04. Facts it
rests on: `2026-10-04-649-consistency-time-research.md` (same directory).
Issues: #649, #581 (absorbed). Tracker: #651 row 2.

## Goal

A point-in-time read never gives an answer that can change later, and a read
whose instant cyoda-go chooses includes every save already confirmed. Both
hold on every backend and on every node of a cluster.

## Definition

The **consistency time** `C` is an instant in the store's stamp domain,
returned by the store for the caller's tenant, with two properties:

1. **Complete** — every save of that tenant whose success was returned (on
   any node) before the request for `C` started has a stamp `≤ C`.
2. **Final** — a read at `T ≤ C` that starts after `C` was returned sees
   every save of that tenant stamped `≤ T`, now and later; every save not yet
   stamped will be stamped `> C`.

`C` is defined at the store's read resolution: a store that widens `T` when
it reads (cassandra widens to the whole millisecond) returns a `C` that
closes its whole unit.

The #649 notes' formula (`min(now, earliest stamped-not-committed) − ε`) is
final but not complete (research §1.1). Both properties need **reserve, then
wait**: raise the stamp floor to `C = max(store clock, highest stamp issued)`
so later saves stamp above it, then wait until every save of the tenant that
already holds a stamp `≤ C` has finished committing (or aborted).

## Design

1. **SPI.** New required method `spi.TransactionManager.ConsistencyTime(ctx)
   (time.Time, error)`, tenant from `ctx` as for every SPI call. The doc
   states both properties, the read-resolution rule, and "fails rather than
   guesses". No "not supported" escape: every backend implements it.
   Conformance cases in `spitest` (Tests). SPI PR into `cyoda-go-spi` main,
   pseudo-pinned, no tag until the release cut.

2. **memory.** `C` = the reservation `Begin` already does (`max(clock,
   lastSubmitTime)`, then `lastSubmitTime = C`). No wait: commit holds
   `entityMu` from stamp to publish and every reader takes
   `entityMu.RLock`. Fix: the wall clock strips Go's monotonic reading at the
   source (`plugins/memory/clock.go`), so the floor, stored stamps and `C`
   all compare wall time and a wall-clock step back is floored.

3. **sqlite.** `C` = take the commit gate (waits for a commit in flight to
   pass `sqlTx.Commit()`), reserve as `Begin` does, release. Fixes: the
   floor on open is seeded from the highest of the version stamps and the
   stored async-job instants (a job's instant is a `C` already handed out);
   a query error fails startup instead of leaving the floor at 0.

4. **postgres.**
   - A sequence holds the **stamp floor**: non-transactional, visible at once
     to every session on every node, never rolled back, flushed with the
     commit that raised it. Seeded by the migration from the highest stamp
     in the database.
   - **Stamp function** (one SQL call; replaces `SELECT clock_timestamp()` in
     `stampCommitInstant` and `stampOwnCommitInstant`, the only two stamp
     sites):
     1. take a transaction-level advisory lock keyed by (tenant, this
        transaction's id) — the *in-flight marker*, released when the
        transaction ends, after its rows are visible;
     2. set a transaction-local `idle_in_transaction_session_timeout` of a
        few seconds, so a session left behind by a dead node releases its
        marker promptly;
     3. under a short session-level advisory mutex (guarded by a handler
        that also catches `query_canceled`): `s = max(clock_timestamp(),
        floor + 1µs)`, raise the floor to `s`.
   - **Consistency-time function** (one SQL call, on its own pool connection
     in autocommit, never on a transaction's connection): under the mutex,
     `C = max(clock_timestamp(), floor)` and raise the floor to `C`; release
     the mutex; list the tenant's granted markers from `pg_locks`; take each
     in shared mode at transaction level (waits for that transaction to end;
     nothing leaks on a cancel, no later transaction uses the key). A
     transaction-local `lock_timeout` bounds the wait; on timeout the call
     fails.
   - Rule the design depends on: **nothing after the stamp waits on a lock**.
     The stamp-phase statements touch only the transaction's own rows, and
     the non-transactional stamp is the last statement before `COMMIT`. A
     fenced read that runs while the caller holds a transaction therefore
     cannot deadlock against the commits it waits for.
   - Remove `transaction_time <= CURRENT_TIMESTAMP` from the PIT SQL: the
     fence makes it redundant, and when the floor runs ahead of the DB clock
     it hides rows `≤ C`.
   - Named constants for the advisory key spaces (the two-int key space is
     used by nothing else); schema-qualified objects.
   - Documented exposure: with asynchronous replicas, failover to a host
     whose clock is behind can stamp below a `C` already returned — the same
     exposure as losing commits on asynchronous failover.
   - Probes: 0 violations in 461 + 2,942 checks under 16 concurrent writers,
     against 816 of 820 for "DB clock now"; no measurable commit-throughput
     cost (research §4).

5. **cassandra (commercial).** Cannot meet the contract on today's code
   (research §8). File a cassandra issue: implement `ConsistencyTime`
   (cluster-wide reserve-then-wait over shard owners), close `C`'s whole
   millisecond, prerequisites cassandra#110, #97 items 1-2, #64 and a
   takeover floor. "Snapshot at `Begin` = `C`" (would close #97 item 3) is an
   option to assess there, not prescribed: it adds a cluster round to every
   `Begin`. The cassandra v0.9.0 bump needs this implemented. No "not
   supported" answer is offered to bridge the gap: it would only let the
   plugin ship v0.9.0 while cassandra#110, which breaks commits in a cluster
   with or without #649, is still open. A single-node reserve-then-wait is
   sound today (research §8) and is the plugin's own choice to make.

6. **Engine: one consistency component** used by every read path, HTTP and
   gRPC alike:
   - **`Fresh(ctx)`** — a `C` from a store call that started after the
     caller did (completeness). Used for the async default.
   - **`Fence(ctx, T)`** — passes when `T ≤` the highest `C` this node has
     seen (a returned `C` stays final forever); otherwise joins or makes a
     store call; then applies D1 when `T > C`.
   - Store error or wait-budget timeout → the read fails with a retryable
     `503`; nothing is created; never a fallback to the process clock.

7. **Which reads.**
   - **Async search without `pointInTime`** uses `Fresh` (replaces
     `time.Now()`); stored with the job as today; every page and a reclaim
     on another node read at that instant.
   - **Every read with an explicit instant is fenced** before it runs:
     entity get, entity list, gRPC get-all, direct search, async submit,
     conditional delete, grouped stats, the six stats reads, change history
     with `Until`, transitions (`pointInTime` and `transactionId`).
   - Reads without an instant stay current-state reads (complete by the
     #501 contract) and do not touch `C`.
   - Not fenced: the audit-trail time window (a log query, expected to grow).

8. **D1 — an explicit instant later than `C`** (in the future, or inside a
   commit window). Not viable, by the no-substitute rule: serving it (the
   answer can change afterwards), marking it "not final", or clamping it to
   `C`. Also rejected: raising the floor to `T` itself — sound, but it moves
   the tenant's stamps up to the tolerance into the future. Viable:
   - **(a) wait, then refuse** — `T` at most a small tolerance ahead of `C`
     (proposed: 1 s, fixed): wait until the store clock passes `T`, fence
     again. Beyond the tolerance, or when the wait budget runs out: refuse.
   - **(b) refuse at once.** Simpler. A client clock a few ms ahead gets
     spurious refusals; the e2e host clock runs 3-13 ms ahead of the
     database today, so tests that pass "now" would fail.
   - Recommendation: (a). The refusal carries the current `C`.

9. **Fixes on the way** (same family):
   - The six stats reads honour `pointInTime` through the grouped-stats
     iterate path (the SPI `Count` takes no instant). Cost: a PIT stats read
     scans the model's entities; the cross-model statistics read scans every
     model. Without an instant they stay the pushed-down counts.
   - gRPC get-all passes `pointInTime` through.
   - The async page "not found → skip" branch is deleted as unreachable (no
     hard-delete path exists); the error takes the generic internal path.
   - `dropSchema` (test-only, uses `pg_stat_activity`) moves to a test file.
   - Docs: `api/openapi.yaml` async submit text; `search.md:236`;
     `crud.md:395`, `:579-614`; `docs/CONSISTENCY.md` §1a (stability rule,
     the sqlite claim, "not scheduled"); `docs/ARCHITECTURE.md:1475-1479`,
     DD-11; `docs/plugins/POSTGRES.md` (stamping, "no session-level state"
     at `:458-460`); the gRPC schemas that say "current consistency time";
     `pit_time.go` comments in `e2e/parity` and `plugins/postgres`;
     `COMPATIBILITY.md` for the SPI pin; help topics for new error codes.
   - Not done: `AuditEventDto.consistencyTime` stays unset. Cloud fills it
     with the `C` at transaction creation; computing a `C` per `Begin` is a
     cost with no consumer.

10. **Gate 7.** `docs/cloud-parity/consistency-time.md`; CaaS ticket. Cloud's
    `C` is final but not complete and a read later than `C` is served
    unfenced (research §6); Cloud follows cyoda-go.

## Error table (per fenced endpoint; HTTP and gRPC envelope alike)

| Case | HTTP | Code | Retryable | gRPC envelope |
|---|---|---|---|---|
| `T ≤ C` (after any D1 wait) | unchanged | — | — | unchanged |
| `T` beyond the D1 tolerance, or the D1 wait budget ran out | 400 | new `POINT_IN_TIME_NOT_YET_CONSISTENT` (detail carries `C`) | no | `Success=false`, same code |
| store cannot give `C` (error, wait budget) | 503 | new `CONSISTENCY_TIME_UNAVAILABLE` | yes | `Success=false`, same code, retryable |

Both codes get a `cmd/cyoda/help/content/errors/<CODE>.md` topic.

## Tests

- `spitest`: after an acknowledged commit, `GetSubmitTime ≤ C`; a commit
  started after `C` returned stamps `> C`; with the harness clock floored
  ahead, `C` is at or above the floor; repeated reads at `C` after further
  commits return the same answer.
- Per backend white-box: a commit held between stamp and visibility makes
  `ConsistencyTime` wait (postgres: hold a transaction after the stamp call;
  sqlite: hold the gate); per-tenant: another tenant's held commit does not
  make it wait; the wait budget fails the call; the floor survives a clock
  step back (memory/sqlite via `Clock`; postgres via the sequence set
  ahead); sqlite reopen with stamps and job instants ahead of the clock;
  a cancelled call leaves no lock behind.
- Engine unit: async default from the store; fence cache; join rule; D1.
- e2e (postgres): async search with the DB clock simulated ahead finds the
  confirmed saves; every fenced endpoint × each status; stats and get-all
  honour `pointInTime`.
- gRPC: each error class on each fenced handler.
- Parity: async default and fence behaviour across memory/sqlite/postgres.
- Multi-node (isolated postgres e2e): save confirmed on node A, async submit
  and fenced read on node B include it.
- Concurrency (isolated postgres e2e): writers + async submits; no confirmed
  save missing; repeated reads at a returned instant identical.
