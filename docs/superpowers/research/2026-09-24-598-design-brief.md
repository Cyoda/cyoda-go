# #598 design brief — every scheduled run has one owner

Status: design for review, 2026-09-24. Facts it rests on:
`2026-09-24-598-scheduler-ownership-research.md` (cited as "R§n").
Rulings from the product owner are marked **[ruling]**.

## 0. Terms

- **Task**: the stored row "fire transition T of entity E at time X".
- **Run**: one attempt to fire a task.
- **pnode**: a cyoda-go processing node. **cnode**: a compute node.
- **Hand-off**: the moment a callout is given to a cnode —
  `member.Send` returning nil (`internal/grpc/dispatch.go:189`), the line
  #254 already uses (R§4).
- **Claim number**: a number on the task that goes up every time a pnode
  claims it. Every write the owner makes carries the number it claimed under;
  the store refuses a write whose number is not current.
- **Unsafe work**: a processor callout whose processor is not declared
  `idempotent`. Criteria and functions are never unsafe (R§4).

## 1. What must be true afterwards (#598 acceptance)

1. No run starts while another run of the same task is in progress on a live
   pnode.
2. A processor that is not declared safe to repeat is never executed again on
   the platform's own initiative.
3. A task that cannot succeed reaches a recorded, visible terminal state.
4. The pnode that decides to run a task learns its outcome; an empty or
   partial cluster view is safe; the number of runs in progress is bounded.

## 2. The design

### 2.1 Claiming (replaces scan + throttle + coordinator + delegation)

Every pnode, every `CYODA_SCHEDULER_SCAN_INTERVAL` (1 s), asks the store to
**claim** due tasks, at most as many as it has free run slots
(`CYODA_SCHEDULER_MAX_RUNS`, replaces `CYODA_SCHEDULER_BATCH_SIZE`). One store
call does it atomically; concurrent claimers on different pnodes get disjoint
sets (PostgreSQL: one statement with `FOR UPDATE SKIP LOCKED`, the proven
async-search pattern, R§3). A claim raises the claim number and marks the task
running. The pnode that claims a task runs it itself.

A task is claimable when:
- it is waiting and its due time (first: the scheduled time; after a failed
  attempt: the next-attempt time) is not in the future by the pnode's clock;
- or it is running and its owner's heartbeat is older than
  `CYODA_SCHEDULER_STALE_AFTER`, judged by the **store's** clock (as async
  search does, R§3);
- or it was given back (§2.7).

Deleted: the lowest-node-id coordinator, round-robin distribution, the
scheduler RPC (`internal/cluster/scheduler_rpc.go`) and its setting
`CYODA_DISPATCH_FORWARD_TIMEOUT` (its only user, `app/app.go:608`),
`CYODA_SCHEDULER_DISTRIBUTION`, `CYODA_SCHEDULER_COORDINATOR`,
`CYODA_SCHEDULER_REDISPATCH_BACKOFF`, `CYODA_SCHEDULER_BATCH_SIZE`, and the SPI
methods `ScanDue` and `MarkRedispatch` with the fields `RedispatchAfter` and
`AttemptCount`. Acceptance 4 follows: there is no delegation, no cluster view
is read, and runs in progress never exceed free slots.

### 2.2 Liveness

While a run is in progress its owner writes a heartbeat every
`CYODA_SCHEDULER_HEARTBEAT_INTERVAL` (15 s). `STALE_AFTER` defaults to 5 min
and must be ≥ 4 × the interval (same rule as async search). A slow run keeps
heartbeating and is never taken ("too slow" is not "replaced"). A hung but
heartbeating run keeps its task — liveness is not progress, the same position
as #509; every callout in a run is bounded (R§2.7).

If a heartbeat is refused (the task was taken or re-armed), the owner cancels
the run's context. The run then fails its next store step, and its commit
would be refused anyway (§2.3).

**PostgreSQL constraint.** Entity transactions run at REPEATABLE READ
(R§3). The run's final transaction deletes the task row. If heartbeats (or the
unsafe mark, §2.4) wrote that row while the run was open, every such delete
would fail with a serialization error. So everything the owner writes *during*
a run lives apart from the task row that the run's transaction deletes (in
PostgreSQL: a separate claim table keyed by task id). The SPI contract states
the requirement; the table layout is the plugin's.

### 2.3 Finishing a run

The run's final transaction removes the task **only if the claim number is
still the one it claimed under**, atomically with the entity write
(`CompleteClaimed(id, number)` inside the transaction). If it is not, the
transaction fails and rolls back. This applies to every outcome that ends a
task: fired, declined, expired, transition gone, entity gone, entity moved on.

- PostgreSQL: a re-claim committed after the run's transaction began makes the
  delete fail with a serialization error; a re-claim attempted after the
  delete is skipped by `SKIP LOCKED` and then finds no row.
- Memory: the check runs in the commit's validation step
  (`plugins/memory/txmanager.go:530`, before anything is applied) — **to verify
  in the spec**.
- SQLite: staged ops are applied inside the same SQL transaction and an error
  rolls it back (`plugins/sqlite/txmanager.go:885-894`).

The fire path excludes its own task from the re-arm step's cancellation and
removes it with the fenced call instead.

### 2.4 The unsafe mark (acceptance 2)

Immediately before the hand-off of unsafe work, the pnode about to call
`member.Send` writes a mark on the task's claim: "unsafe work has been handed
off", carrying the claim number. The run's identity (tenant, task id, claim
number) travels with the callout, including across a #254 hand-over to a peer
pnode, so the mark is written by whichever pnode actually sends — one place,
`internal/grpc/dispatch.go`, before `member.Send`.

- If the write is refused (the task was taken), nothing is sent and the
  callout fails without a hand-off.
- A later attempt that finds the mark does not run the transition; the task
  fails for good (§2.6).
- The mark is written once per claim; later unsafe callouts in the same run
  find it set and write nothing.
- A processor declared `idempotent` is trusted for everything it causes,
  including callbacks that run other workflows (its declaration covers "cyoda
  and every system it touches", `SPI/types.go:244-251`).

This also closes the `COMMIT_BEFORE_DISPATCH` defect (R§2.5 item 8): the
earlier processors of a failed run are repeated only if every one of them was
declared safe to repeat.

### 2.5 A failed run where nothing unsafe was handed off (kind 1)

**[ruling]** Keep trying until the transition's own `timeoutMs` passes; no
attempt limit.

After the run's transaction has rolled back, the owner records the attempt in
a small bookkeeping write fenced on the claim number: attempts + 1, the error
(§2.9), the next-attempt time, and gives up the claim. The delay starts at
`CYODA_SCHEDULER_RETRY_DELAY` (30 s) and doubles up to
`CYODA_SCHEDULER_RETRY_DELAY_MAX` (15 min).

A run whose owner died is the same case when no mark is set: the new owner
counts one attempt (reason "owner lost") and runs it.

Lateness: when a task is picked up more than `timeoutMs` after its scheduled
time, it is not run.
- If it never had a failed attempt: expired, as today — removed,
  `SCHEDULED_TRANSITION_EXPIRE` on the entity.
- If it had failed attempts: **failed for good** (§2.6), reason
  "expired after failed attempts". The timer did not end as the author
  intended, so it stays visible.

With no `timeoutMs`, attempts continue at the longest delay until the cause is
fixed or the entity is written (which re-arms, §2.8).

The 100 ms grace band and `CYODA_SCHEDULER_EXPIRY_GRACE` are deleted: they
exist so two pnodes judging the same task at once cannot decide differently
(`docs/cloud-parity/scheduled-transitions.md` §1). With one owner, one pnode
decides, and only a fenced decision can commit.

### 2.6 Failed for good (kind 2)

**[ruling]** The entity is never moved. The task is kept with status FAILED
and a reason, and is visible through the task query (§2.10), telemetry and
logs.

Reasons:
- `UNSAFE_WORK_NOT_COMPLETED` — the mark is set and the run did not commit
  (the run failed, or its owner was lost).
- `EXPIRED_AFTER_FAILED_ATTEMPTS` — §2.5.

The transition to FAILED is a committed bookkeeping write fenced on the claim
number. It also records `SCHEDULED_TRANSITION_FAIL` (new audit event type) on
the entity, and logs at ERROR. This committed write is the point from which
the planned notification feature can later publish a "timer failed" event: it
commits, and (task id, claim number) identifies it uniquely and stably.

A FAILED task is never claimed again.

### 2.7 Shutdown

A stopping pnode stops claiming, lets runs finish for a short budget, then
cancels the rest and **gives their tasks back** (fenced; not counted as an
attempt). A given-back task is claimable at once. A given-back task whose mark
is set becomes FAILED on the next claim (reason `UNSAFE_WORK_NOT_COMPLETED`):
its outcome is unknown. The spec sets the budget; it should cover an ordinary
callout.

### 2.8 How a FAILED task ends

Unchanged arming rules decide it:
- The entity leaves the source state (a manual transition, another scheduled
  transition): the task is cancelled and removed, `SCHEDULED_TRANSITION_CANCEL`.
- The entity is written in the source state: the task is re-armed as a new
  task — fresh time, attempts 0, mark cleared, claim number raised (so any old
  owner is fenced out). A repeat of the unsafe processor then happens because
  the application wrote the entity, not on the platform's initiative.
- **The entity is deleted: its tasks are removed in the same transaction.**
  Today nothing removes them (R§2.1); with FAILED tasks kept, they would stay
  forever.

### 2.9 What the recorded error says

The error is shown to tenant users (§2.10), so it follows the 4xx/5xx rule:
- a failure the tenant's own compute node reported (processor failure,
  criterion error): its message;
- a domain error: its code and message;
- anything internal (storage, engine): `internal error` plus a ticket UUID;
  the details go to the log under that ticket. No internals are stored.

### 2.10 The task query

`GET /scheduled-tasks` (HTTP only). The tenant comes from the caller's token.
Filters: `status` (repeatable: `WAITING`, `RUNNING`, `FAILED`), `modelName` +
`modelVersion`, `entityId`, `transition`. Paging by cursor with `cursor` and
`limit`, copying the audit endpoint (`internal/domain/audit/handler.go:52-71`,
`cursor.go`). Response `{items, pagination:{hasNext, nextCursor}}`.

Item: `taskId` (string; the id is a hash, not a UUID), `entityId`,
`modelName`, `modelVersion`, `sourceState`, `transition`, `status`,
`scheduledTime`, `expiresTime` (when `timeoutMs` is set), `attempts`,
`lastAttemptTime`, `nextAttemptTime`, `lastError`, `failureReason`,
`failedTime`, `armedTime`, `armedBy`. Times RFC 3339, as elsewhere. No node
ids (internal detail).

Access: any authenticated user of the tenant, like the audit trail
(`internal/domain/audit/handler.go` checks no role). HTTP only, like the audit
trail: it is an operator's view, not something a cnode needs.

Tenant isolation: the scheduled-task table is not under PostgreSQL row-level
security (it must be scanned across tenants by the claim). Every read and
write that is not the cross-tenant claim therefore filters on the tenant
explicitly, and today's `Get` and `Delete` by id alone are changed to do so
(R§2.5). A cross-tenant test per operation.

### 2.11 Telemetry

- `cyoda.scheduler.runs` (counter, attribute `outcome`: fired, declined,
  expired, cancelled, attempt_failed, failed, given_back, taken).
- `cyoda.scheduler.run.duration` (histogram, seconds).
- `cyoda.scheduler.runs.in_progress` (gauge).
- `cyoda.scheduler.claims` (counter, attribute `reason`: due, stale,
  given_back).
- A `scheduler.run` span around each run.
- No tenant attribute (house rule, `help/content/telemetry.md:100-101`).
- WARN log per failed attempt, ERROR per task failed for good.

### 2.12 Also fixed in this change

- Memory and SQLite `Delete` report "removed" reliably (R§2.5 item 9), or the
  method disappears if the fenced calls replace every caller.
- The wrong comment at `fire_scheduled.go:482-486`.
- `docs/cloud-parity/scheduled-transitions.md` rewritten (Gate 7): one owner
  per run, no platform repeat of unsafe work, retry until `timeoutMs`, FAILED
  tasks and the query.
- cyoda-go-cassandra#68 updated to the new SPI contract.

## 3. SPI changes (summary)

`ScheduledTask` gains: status, claim number, attempts, last error,
last/next attempt time, failure reason, failed time, and the unsafe mark (read
side). `ScheduledTaskStore`:

- keeps `Upsert` (arm = new task, claim number raised, state reset),
  `ReconcileForEntity`;
- `Get(tenant, id)` tenant-scoped;
- adds `ClaimDue`, `Heartbeat`, `MarkUnsafeHandOff`, `CompleteClaimed` (in
  the entity tx), `RecordAttemptFailure`, `RecordFailed`, `GiveBack`,
  `DeleteForEntity` (entity delete), `Query` (tenant-scoped, cursor);
- removes `ScanDue`, `MarkRedispatch`, and `Delete` if no caller remains.

Conformance cases move to `spitest` next to async search. Mid-milestone SPI
workflow: SPI PR into main, cyoda-go pseudo-pins it.

## 4. Coverage (outline for the spec's matrix)

Every ending, each on a running backend, in cross-backend parity, and where it
involves more than one pnode, in the multi-node PostgreSQL suite:

| Ending | Case |
|---|---|
| fired | ordinary; after an earlier failed attempt |
| declined | criterion false |
| expired | late, no failed attempts |
| retrying | criterion error; cnode unavailable (no hand-off); idempotent processor fails; owner dies without mark |
| failed | unsafe processor fails; later step fails after unsafe hand-off; owner dies with mark; given back with mark; expired after failed attempts |
| no double run | run longer than several heartbeat intervals is not claimed by another pnode (multi-node) |
| fenced | a replaced owner's heartbeat, mark and commit are refused; a replaced owner sends no unsafe work |
| re-arm | FAILED task re-armed by an entity write; cancelled by leaving the state; removed by entity delete |
| query | each filter, paging, bad cursor/limit (400), no token (401), other tenant's tasks invisible |
| back-pressure | never more runs than `MAX_RUNS` |
| shutdown | runs given back; a given-back task runs promptly on another pnode |

Concurrency cases run in isolated single-backend e2e, not in the shared parity
suite.

## 5. Not included

- An API to retry or dismiss a FAILED task: an entity write already does both
  (§2.8).
- Notifications: the committed FAILED write is the future emission point
  (§2.6).
- Reclaiming a hung pnode that still heartbeats (§2.2).
- #599 and #600: separate issues.

## 6. Verification points for the spec

- V1: memory commit can refuse on the fenced check before applying anything.
- V2: the run identity can travel with a #254 hand-over without widening the
  peer wire beyond what is needed.
- V3: every path that ends a task today goes through the fenced call.
- V4: no other user of `ScanDue`, `MarkRedispatch`, `RedispatchAfter`,
  `AttemptCount`, the scheduler RPC or the deleted settings.
- V5: the re-arm upsert raising the claim number fences an owner that is still
  running (PostgreSQL and memory/SQLite).
