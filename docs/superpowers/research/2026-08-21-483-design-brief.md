# Design brief: auth-cache reconciliation (#483) — v2, post first review

Companion to `2026-08-21-483-auth-cache-reconcile-research.md` (factual
survey). v1 was reviewed by a fresh-context reviewer (verdict:
sound-with-changes); this revision incorporates all findings. Changes from
v1 are marked **[v2]**.

## Problem (from the issue)

Two per-node auth caches never reconcile against their authoritative KV
store:

- **A. Trusted keys** (`KVTrustedKeyStore`): no broadcast at all, no TTL.
  Revocation (Delete/Invalidate) on one node leaves peers accepting the
  revoked key until they restart. Fail-open, needs nothing to go wrong.
- **B. OIDC providers** (`oidc.Registry`): gossip broadcast exists but is
  best-effort; a dropped `invalidate`/`reload` message leaves a peer
  serving a deleted/deactivated provider's keys forever.

## Chosen architecture

**Broadcast fast path + periodic jittered KV-reconcile backstop + fail-closed
staleness bound — the model-cache layering, applied to both caches.**

Rejected alternatives (unchanged from v1):

- Per-entry TTL lease: structurally wrong — verification *enumerates* these
  caches (`ListForVerification`, `ResolveKey` candidate walk), so expiry has
  no read-through fallthrough and deletions must be noticed, not expired.
- Read-through on verification: KV round-trip on every token verification.
- Backstop-only for trusted keys (v1's position): **[v2]** dropped per
  review + `multi-node-primary.md` — registration/revocation would be
  cluster-visible only at reconcile granularity (~66s) with no fast path;
  the backstop removes the issue's stated objection to trusted-key gossip
  ("only worth it combined with a backstop"), so combine them.

### A. Trusted keys (`internal/auth/kv_trusted_store.go`)

- **Reconcile** — new `reconcile() error`: KV List + fresh-map build
  **off-lock**, then swap under `s.mu` guarded by a **generation counter**
  **[v2, review F1]**: every cache-mutating commit (`Register`, `Delete`,
  `Invalidate`, `Reactivate`, `loadOne`) bumps the counter; `reconcile`
  snapshots it before the List and retries the build (bounded, 5 attempts)
  if it changed by swap time; on exhaustion, error (loop: WARN + next
  tick). No KV I/O ever happens under `s.mu` — v1's hold-the-lock approach
  would have let a slow KV call (store ctx is deliberately deadline-free)
  block all token verification node-wide.
- **Error taxonomy** **[v2, review F2]**: transport-level List failure →
  abort tick, keep last-known state, retry next tick. Per-record
  deserialize failure → **skip that record, log ERROR, reconcile the
  rest** (matches `KVOidcProviderStore.LoadAll`, which already skips
  undecodable records). A deterministic corrupt record must not disable
  reconciliation forever — that would silently reintroduce the bug being
  fixed. Construction-time `loadAll` keeps its fail-fast.
- **Broadcast fast path** **[v2, review F6]**: new gossip topic
  `auth.trustedkeys`. Every successful mutation publishes an empty
  "changed" ping (no key material, no tenant data on the wire — nothing
  for a malicious peer to inject); receivers run a singleflight-debounced
  `reconcile()`. Sub-second propagation for both registration and
  revocation; the periodic loop remains the convergence guarantee when a
  ping drops. Broadcaster nil (single-node) → no-op, loop still runs.
- **Reconcile loop** — `StartReconcileLoop(ctx, interval)`: goroutine,
  per-tick jitter (interval × [0.9, 1.1)), `atomic.Bool` once-guard, exits
  on ctx cancel. Shape mirrors `Registry.StartWarmupRetryLoop`.
- **Known bounded window** **[v2, review F4]**: `Get`'s read-through
  (`loadOne`) KV-reads outside the lock; a Get racing a peer's Delete can
  re-insert a just-deleted key. The stale entry survives at most until the
  next reconcile (ping-triggered, typically sub-second). Documented, not
  claimed eliminated.

### B. OIDC providers (`internal/auth/oidc/registry.go`)

- `ReloadAll` is already the reconcile primitive (off-lock rebuild from KV,
  swap, carry over warm key sources, drop vanished providers; deactivation
  propagates because `Active()` gates every read; `LoadAll` returns
  inactive records too — verified).
- **Generation guard in `ReloadAll`** (as v1): counter bumped by direct map
  mutations (`addToProviderMap`, `invalidateOne`); snapshot before
  `store.LoadAll`, bounded retry (5) on change, error on exhaustion.
  Closes the resurrect race (mutation landing between LoadAll and swap
  clobbered by the older snapshot).
- **Skip-swap on no-change** **[v2, review F5]**: if the loaded snapshot is
  deep-equal to the current providers map, skip the swap entirely —
  `kidIndex` and sources untouched on quiet ticks (the overwhelming
  majority), so periodic reconcile causes zero cold-path churn.
- **Reconcile loop** — `Registry.StartReconcileLoop(ctx, interval)`: same
  loop shape, calling `ReloadAll` (NOT `ReloadAllAndWarm` — no per-tick
  outbound IdP traffic; JWKS freshness stays with the 5-minute per-source
  cache). Errors: WARN + keep state + next tick.
- **Composition property** **[v2, reviewer]**: reconcile ∘ warmup-retry
  closes the registration direction end-to-end — reconcile discovers a
  provider registered on a peer (dropped `reload` ping), warmup-retry
  (`coldActiveRefs`, 30s tick) warms it. Gets a test.
- Existing `oidc.providers` gossip unchanged.

### Fail-closed staleness bound **[v2, review F3]**

v1 kept last-known state indefinitely on persistent reconcile failure —
unbounded revocation staleness, which contradicts
`.claude/rules/correctness-over-availability.md` (the store being up is a
precondition for a correct answer; wrong-but-available is never returned)
and silently diverged from the model-cache precedent (whose entries fail
closed once the lease expires).

- Both caches track `lastSuccessfulReconcile` (initialized by the
  construction-time load).
- If `now − lastSuccessfulReconcile > 10 × interval` (default: 10 min),
  the affected verification paths **fail closed**: trusted-key
  verification (`ListForVerification` consumers / `Get`) and OIDC
  `ResolveKey` return errors → those tokens get 401. First-party JWTs are
  unaffected (in-process local key source, no KV dependency), so the
  breaker's blast radius is exactly the federated surface whose
  correctness depends on KV — which, after 10 min of KV unavailability, is
  a platform already down.
- Escalation before the breaker: WARN per failed tick, ERROR once
  consecutive failures exceed 3, plus metrics (consecutive-failure count,
  seconds-since-last-success) so operators can alert well before the bound.
- The bound is a fixed 10× multiple of the interval — one knob, not two.

## Configuration

- One new env var: `CYODA_AUTH_CACHE_RECONCILE_INTERVAL`, duration,
  **default 60s**, floor-validated in `ValidateIAM` (`app/config.go`) —
  reject < 1s **[v2, review F7c]**. No disable knob. Field on `IAMConfig`;
  help topic `auth`.
- Why 60s, not the model cache's 5m: this bounds *revocation* staleness —
  a security property, not a performance lease — and a tick costs one KV
  List + one KV LoadAll per node, no outbound traffic. With the broadcast
  fast path, the loop is purely the dropped-message backstop, so 60s is
  comfortable for both.
- Both loops share the single interval: one decision, applied twice.

## Wiring (`app/app.go`, jwt-mode block)

- After `NewKVTrustedKeyStore`: subscribe the store to the broadcaster
  (nil-safe) and `StartReconcileLoop(systemCtx, cfg.IAM.AuthCacheReconcileInterval)`.
- Inside `pendingWarmJWKS` (alongside `StartWarmupRetryLoop`):
  `oidcRegistry.StartReconcileLoop(systemCtx, ...)`.
- `systemCtx` is background-derived and never cancelled → loops run to
  process exit, same lifecycle as `StartWarmupRetryLoop` **[v2, F7a]**.
- Loops run in single-node mode too (KV-dependent, not gossip-dependent).
- Mock IAM mode: neither store exists; nothing to start.

## Not in scope

- No new endpoints, error codes, or API shape → no OpenAPI, no
  `errors/*.md`, no cloud-parity doc (bug fix to the existing contract).
- No change to `InMemoryTrustedKeyStore` (nothing authoritative to
  reconcile against).
- No change to the model cache or gossip transport.

## Test shape

- Trusted keys (unit, `internal/auth`; two stores over one shared fake KV
  = two nodes):
  - Delete / Invalidate / Register on store 1 → `reconcile()` on store 2 →
    `ListForVerification` / `Get` / `List` reflect it.
  - Per-record corruption: bad record skipped with ERROR, rest reconciled;
    transport failure: state kept, error returned.
  - Generation guard: mutation injected between List and swap (fake-KV
    hook) is not clobbered.
  - Broadcast: mutation on store 1 publishes ping; store 2's handler
    reconciles (fake broadcaster, existing pattern).
  - Staleness bound: reconcile failures past the bound → verification
    fails closed; recovery restores service.
  - Loop: short-interval eventually-converges (coarse, generous timeouts,
    `reload_warmup_test.go` pattern) + once-guard + ctx-cancel stop.
    Deterministic semantics live in the synchronous `reconcile()` tests
    **[v2, review F7b]**.
- OIDC (unit, `internal/auth/oidc`): store delete/deactivate without
  broadcast → loop → `ResolveKey` stops resolving; surviving provider's
  carried-over source still resolves (no re-fetch); skip-swap keeps
  kidIndex on identical snapshot; generation guard under fault-KV;
  reconcile ∘ warmup-retry composition (registered-on-peer provider
  becomes resolvable with no direct broadcast); staleness bound fails
  closed and recovers.
- Concurrency (isolated unit, not parity): reconcile loop racing
  Register/Delete under `-race` (in `make race` scope).
- No e2e/parity additions: no HTTP/gRPC surface change; cluster semantics
  are exercised at the two-stores-one-KV seam (same seam the existing
  multi-node trusted-key test uses).
