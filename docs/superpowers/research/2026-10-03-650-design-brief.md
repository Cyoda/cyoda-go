# #650 design brief: tenant-scoped M2M clients

Agreed in conversation with Paul on 2026-10-03. Facts it rests on:
`2026-10-03-650-tenant-scoped-clients-research.md` (same directory). Issue: #650.

## Goal

A client id is unique only inside its tenant. The token request names its
tenant in the URL; a client is found by (tenant, client id); a tenant may choose
its client ids.

## Design

1. **Token URL** `POST {CYODA_CONTEXT_PATH}/tenants/{tenant}/oauth/token`
   (default `/api/tenants/{tenant}/oauth/token`), unauthenticated, mounted on the
   inner mux before the authenticated catch-all, as `/oauth/token` is today.
   - `{tenant}` is taken verbatim: no case folding, no re-decoding. A segment
     outside the tenant grammar, or whose escaped form differs from its decoded
     form (any percent-encoding — never needed, the grammar has only unreserved
     characters), or equal to `SYSTEM`, answers `404` before the handler runs.
   - The old `/oauth/token` is removed (pre-1.0, no production instances).
   - Everything else unchanged: Basic auth, both grants, the error responses
     and their order, the bcrypt-cost equalisation. A wrong tenant, an unknown
     client and a wrong secret are the same `401 invalid_client`.
   - Mock IAM mode: the generated route moves with the OpenAPI path and still
     answers `501`.

2. **The `/tenants/{tenant}/…` route group.** Built now: one shared step that
   reads and checks the tenant segment (item 1) and hands the addressed tenant
   to the route. Not built now: the rule for routes that carry a bearer token —
   the addressed tenant must equal the token's tenant, a mismatch answers `404`
   like a missing resource. No planned route needs it (searched open issues:
   #645 takes the tenant from the token). The rule is recorded in the spec and
   in a comment on the group; the first such route builds it with its tests.
   Data routes, `/.well-known/jwks.json` and `/admin` stay outside the group.

3. **Store without the global index.** Records stay at namespace
   `m2m-clients:<tenant>`, key = client id. `Authenticate(ctx, tenant, id,
   secret)` and `Lookup(ctx, tenant, id)` read one key; hit and miss cost one
   read and one bcrypt comparison (the decoy read goes). Delete and reset act on
   the caller's namespace only; every damaged-index branch and its help text
   goes. Existing records keep working at the new URL; leftover
   `m2m-client-ids` rows in dev databases are never read again.

4. **Create is first-write-wins, cluster-wide.** New SPI operation on
   `spi.KeyValueStore`: write a key only if it is absent, atomically in the
   database (postgres/sqlite `INSERT` that fails on the primary key, memory
   under its lock, cassandra a lightweight transaction; a soft-deleted key
   counts as absent). Conformance case in `spitest`. Of two concurrent creates
   of one id in one tenant, on any nodes, exactly one succeeds; the other is
   `409 M2M_CLIENT_EXISTS`. SPI PR into `cyoda-go-spi` main, pseudo-pinned, no
   tag until the release cut; cassandra issue to implement before its v0.9.0
   bump (cassandra#108). The cap check stays as today (per node, may overshoot
   by one per node).

5. **Caller-chosen ids.** `POST /clients` takes an optional query parameter
   `clientId` beside `withAdminRole` and `onBehalfOf` (the operation has no
   body; Cloud's neither). Absent: a generated 16-character base32-hex id, as
   today. Taken in the tenant: `409 M2M_CLIENT_EXISTS` (new error code). Check
   order: `403` admin → `400` id grammar → `404 FEATURE_DISABLED` → `400` flag
   combinations → `400` OBO in PLATFORM → `409` exists → `400` cap.

6. **Client-id grammar** = tenant grammar `^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`,
   case significant, plus the user-id rule (a client's id is its user id on its
   tokens and in audit): `system` in any letter case is refused. Applies
   everywhere `ValidClientID` applies today (store, `/clients/{clientId}`, the
   validator's `cgen` and `act.sub` checks) and to the four OpenAPI patterns.

7. **Node-local maps keyed by (tenant, id)**: the per-client token rate limit
   (`client_bucket.go`) and the verified-secret cache (`secret_check.go`). Keyed
   by id alone, tenant A's `backend` would share tenant B's `backend` rate limit
   (cross-tenant denial of service) and evict its cache entry.

8. **`SYSTEM` is not an API tenant.** Refused at every door a tenant enters by:
   the `caas_org_id` claim (`401`), `cyoda token --tenant` (error), the path
   segment (`404`). No client can exist in SYSTEM; no API caller acts in it.
   `PLATFORM` is unchanged: operators get operator tokens at
   `/api/tenants/PLATFORM/oauth/token`.

9. **Compute stream re-check** looks the client up by the stream's tenant and
   the client id; the separate tenant comparison becomes unreachable and goes.

## Out of scope

- The authenticated half of the group (item 2).
- Exact cap enforcement across nodes.
- Cloud's own changes (CaaS ticket: same model, plus two Cloud defects — a
  wrong secret answers differently from an unknown client; ids and secrets from
  a non-cryptographic random source).

## Contract and docs

Breaking: token URL; client-id grammar widened; new `409`; SYSTEM refused.
OpenAPI (path + `tenant` parameter, `clientId` query parameter, `409`, four
patterns), oasdiff ignore entries, help topics (`auth`, `auth.clients`,
`auth.tokens`, `auth.integration`, `auth.trusted-keys`, `cli.token`,
`config.auth`, `config.grpc`, `grpc`, `helm`, errors), README, CHANGELOG
`### Breaking`, `docs/access-to-the-cyoda-api.html`, ARCHITECTURE, helm gateway
doc (rate limit on `/api/tenants/[^/]+/oauth/token`), cloud-parity doc, parity
client and compute-test-client token helpers.
