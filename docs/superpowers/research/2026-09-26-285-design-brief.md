# #285 design brief — signing key pairs shared by the cluster

Status: design for review, 2026-09-26 (revised after the first independent
review). Facts it rests on: `2026-09-26-285-signing-keys-research.md` (cited as
"R§n"). Rulings from the product owner are marked **[ruling]**.

## 0. Terms

- **Key pair**: an RSA private key that signs tokens and its public key that
  verifies them, with an id (KID), an audience (`client` | `human`), a validity
  window (`validFrom`, `validTo`) and an active flag (R§1).
- **Bootstrap key**: the key pair built from `CYODA_JWT_SIGNING_KEY` on every node;
  its KID is derived from its public key, so it is the same on every node (R§1).
- **Issued key pair**: a key pair created by `POST /oauth/keys/keypair`.
- **KV store**: the SPI `KeyValueStore`, SYSTEM tenant (R§5).
- **Wrapping key**: an AES-256 key used only to encrypt private keys at rest.
- **Owner** of an issued key pair: the bootstrap KID whose wrapping key sealed its
  private key. Recorded in the key pair's record.
- **Key vault**: the component that creates and opens private keys. No code
  outside it holds private-key material; it hands out a signer.
- **Node copy**: each node's in-memory copy of the records, used on every hot
  path (signing, verification, JWKS, `GET current`).

## 1. What must be true afterwards

1. A key pair issued, invalidated, reactivated or deleted on any node takes effect
   on every node, within the bound stated in §2.6 (#285 comment of 2026-09-24).
2. Issued key pairs and every change to them survive a restart on a backend that
   persists (sqlite, postgres, cassandra). The memory backend persists nothing, as
   for all its data.
3. An invalidation, reactivation or deletion of the **bootstrap** key takes effect
   on every node and survives a restart (today a restart brings it back, R§3).
4. Private keys are never stored unencrypted.
5. A KMS / Vault / HSM implementation can sign without the private key leaving it
   (#285 pre-design question 1).
6. Unchanged for the bootstrap key: its KID derivation, and its default state
   (active, no window) when nobody has changed it through the API.
7. Token verification is covered on both entry points: HTTP and gRPC (compute
   nodes authenticate with M2M tokens through the same authenticator,
   `internal/grpc/interceptor.go:56-83`, `app/app.go:782`).

## 2. The design

### 2.1 Records

One KV namespace `signing-keys` in the SYSTEM-tenant KV store (the store
`app/app.go:272-285` already builds). KV key = KID. JSON records.

- **Issued**: KID, audience, algorithm, active, validFrom, validTo, public key
  (SPKI DER, base64), vault `{kind, owner, sealed}`.
- **Bootstrap state**: KID = the bootstrap KID, kind `bootstrap`, active,
  validFrom, validTo, deleted. No key material. Written when the bootstrap key is
  invalidated, reactivated or deleted — directly, or as a sibling of a rotation
  (`invalidateCurrent` on the bootstrap audience invalidates it, `store.go:157-168`).

Reading the bootstrap state never relies on a list:

- Startup and every reconcile read it with a direct `Get` of the well-known key.
- `ErrNotFound` → the default state (active, no window).
- A record that does not parse → the bootstrap key is refused (fail closed) and an
  ERROR names the cause.
- Any other read error during reconcile → the node keeps its last-known state
  (as for every other record) and the staleness bound (§2.5) applies. At startup
  → startup fails, as the trusted-key store's initial load does
  (`kv_trusted_store.go:189-191`).
- `deleted` is terminal. No API call removes a bootstrap-state record; after a
  delete, reactivate answers 404. Recovery is to replace `CYODA_JWT_SIGNING_KEY`.

### 2.2 Wrapping (the default key vault, kind `wrapped`) **[ruling: Option A]**

- Wrapping key = HKDF-SHA256(IKM, salt = none, info =
  `"cyoda-signing-key-wrap-v1"`). IKM is canonical and independent of any
  encoding: the RSA primes of the parsed bootstrap key, sorted ascending, each
  left-padded to the byte length of the modulus, concatenated. The same key in
  PKCS#1 or PKCS#8, inline or `_FILE` (`jwt.go:156-171`), gives the same wrapping
  key. A golden-vector test pins the derived key for a fixed PEM.
- Seal = AES-256-GCM, random 12-byte nonce, stored as `nonce || ciphertext`.
- Associated data binds everything that must not be swapped under the sealed key:
  length-prefixed `"cyoda-signing-key-v1"`, KID, audience, algorithm, owner, and
  SHA-256 of the SPKI public key.
- Opening a record also checks that the opened key's public key equals the stored
  one. A record that fails either check is **broken** (§2.3).
- Threat model: this protects against **read** exposure of the store (backups,
  replicas, a read-only injection). **Write** access to the store is out of scope:
  it already allows registering a trusted key or changing any stored data. The
  binding catches corruption and record mix-ups, not a writer.

Why derive from the bootstrap key: no new required secret; every node has it with
the same value (R§6); no added exposure, since anyone holding the bootstrap key
can already sign tokens every node accepts. `CYODA_HMAC_SECRET` is not stable on a
single node (R§6).

### 2.3 Which records a node uses

Each record is classified when it is loaded:

- **Owned**: vault kind known, owner equals what this node's vault owns (for
  `wrapped`: this node's bootstrap KID), opens, and passes the public-key check.
  Used for everything.
- **Retired**: vault kind `wrapped` with another owner. Not used to sign, verify,
  publish in JWKS or answer `GET current`. Rotation ignores it. Invalidate,
  reactivate and delete answer 404 — so a node deployed with the wrong bootstrap
  key cannot delete or change the cluster's live key pairs. The record stays in
  KV; it becomes owned again if the operator puts the old bootstrap key back.
- **Broken**: owned by this node but will not open or fails the check, or its
  vault kind is unknown. Never verifies. It still takes part in choosing the
  signer, so if the rule picks it, signing fails closed (`/oauth/token` → 5xx, log
  names the KID) instead of silently using another key.

Consequences:
- Replacing `CYODA_JWT_SIGNING_KEY` retires every issued key pair, as it already
  ends every token the old bootstrap key signed. The new bootstrap key signs; no
  lockout. JWKS differs between old- and new-config nodes during the rolling
  restart, as bootstrap-signed tokens already do today.
- A node wrongly deployed with a different bootstrap key ignores the cluster's
  key pairs, and the cluster ignores the ones it issues.
- A database copied to another environment: the source's key pairs are retired
  there.
- Logging: a WARN when the retired set changes (count and KIDs), not every
  interval. An ERROR for each broken record, once per change.
- Recovery when a broken key pair is the signer (documented): invalidate it using
  an admin token from a federated OIDC provider or an unexpired token (default
  lifetime 1 h), or replace `CYODA_JWT_SIGNING_KEY`.

### 2.4 Key vault interface **[ruling: inside cyoda-go, `internal/auth`, not the SPI]**

```go
// Signer signs a SHA-256 digest (RS256 = PKCS#1 v1.5).
type Signer interface {
    Public() crypto.PublicKey
    Sign(ctx context.Context, digest []byte) ([]byte, error)
}

type KeyVault interface {
    Kind() string
    Owner() string // the owner value this vault writes and can open
    Generate(ctx context.Context, meta KeyMeta) (sealed []byte, s Signer, err error)
    Open(ctx context.Context, meta KeyMeta, sealed []byte) (Signer, error)
}
```

- `KeyMeta` carries the values bound into the associated data.
- `Sign` takes a context so a KMS call has a deadline; the wrapped vault ignores it.
- No `Destroy` until a vault needs it (the wrapped vault's key material goes with
  the record).
- `KeyPair.PrivateKey *rsa.PrivateKey` becomes `Signer`. `jwt.Sign` takes a
  `Signer` (`jwt.go:18`; callers `token.go:102,241`). The handler no longer calls
  `rsa.GenerateKey` (`keys_adapter.go:96`); the store asks the vault.
- A KMS vault stores a key reference as `sealed`, owns what its configured KMS
  scope owns, and returns a signer that calls the KMS. Not built now.
- Opened signers stay in memory per KID (the node already holds private keys in
  memory today).

### 2.5 Keeping every node current

The mechanism the trusted-key store uses (R§4), extracted into one component that
both stores use (M2M clients, #286, next). Per-store options keep trusted-key
behaviour unchanged (cache-only verification, its `tenant:kid` KV key layout).

- **Hot paths read the node copy only**: signing, verification, JWKS, `GET current`.
- **Admin writes read KV, not the node copy.** Invalidate, reactivate and delete
  `Get` the record from KV; a rotation `List`s the namespace to find the siblings
  to invalidate. Then write KV, update the node copy (generation bump), broadcast
  an empty message on gossip topic `auth.signingkeys`. A node that has not yet
  seen a delete therefore cannot write the record back, and a rotation cannot miss
  a key issued on another node.
- A received message triggers a re-read (coalesced, never dropped).
- Every node re-reads every `CYODA_AUTH_CACHE_RECONCILE_INTERVAL` (60 s default,
  ±10 % jitter).
- **Verification read-through (signing-key store only).** A token whose KID is not
  in the node copy triggers one KV `Get`, so a key issued on A verifies on B at
  once. Guarded, because it is reachable without authentication:
  - only when the token's unverified `iss` equals the first-party issuer (OIDC
    tokens never cause a read; the validator looks up the KID before it checks
    `iss`, `validator.go:69,82`);
  - one read in flight per KID; at most a small fixed number in flight per node,
    beyond which the KID is treated as unknown;
  - a per-read deadline;
  - the result enters the node copy only if no mutation or reconcile committed
    since the read started (generation check);
  - a KV error → unknown KID (the chain moves to the OIDC validator, which rejects).
- **Stale node copy**: after 10 intervals without a successful re-read, the store
  refuses every issued key pair and the bootstrap key, for signing and
  verification. The client sees 401, as for every validation failure today
  (`delegating.go:48-74`) **[ruling: keep 401]**. The only cause is the node being
  unable to read its own database for 10 intervals; every other request on that
  node is already failing with 503, so the code of the auth answer does not matter.

### 2.6 Timing bound (stated in the spec and the help topic)

- **Issue**: verification on every node at once (read-through). Signing, JWKS and
  `GET current` on other nodes: when the gossip message arrives.
- **Invalidate / reactivate / delete, and rotation**: when the gossip message
  arrives, normally well under a second. If it is lost: the next periodic
  re-read, at most 1.1 × the interval (66 s by default). If a node cannot read KV:
  at most 10 × the interval (10 min by default), after which it refuses all
  issued keys and the bootstrap key.
- An open gRPC stream is authenticated when it starts and is not re-checked after
  a revocation (existing behaviour).
- A synchronous "every node confirms" alternative is rejected: revocation must
  work while a node is unreachable.

### 2.7 Concurrency

The KV store has no conditional write (R§5).
- Two rotations at once on two nodes can leave two active key pairs; every node
  picks the same signer (latest `validFrom`, then greatest KID).
- Two admin writes to the same KID at the same moment: last writer wins (on
  cassandra an update can be lost, R§5). Admin-only and rare; documented.

### 2.8 Cap

`CYODA_IAM_KEYPAIR_MAX` (default 20): the number of owned issued key pairs whose
window has not ended. Issuing beyond it → 400 `KEYPAIR_CAP_REACHED`. Every node
lists and opens the whole namespace on each re-read (cassandra `List` costs
1 + 2N reads, R§5), and the trusted-key store has the same kind of cap
(`kv_trusted_store.go:41`).

### 2.9 Errors

- `ErrKeyPairNotFound` (like `ErrTrustedKeyNotFound`, `store.go:83-89`): adapters
  map it to 404 `KEYPAIR_NOT_FOUND`. Every other store error goes through
  `common.Internal`: 503 `STORAGE_UNAVAILABLE` when the plugin marks the storage
  unavailable (`common/errors.go:169-177,209-212`), otherwise 500 with a ticket.
  Today every error is 404 (R§2).
- `GetActive` returns typed errors: none → 404 on `GET current`, 5xx on
  `/oauth/token`; broken signer or stale store → 5xx.
- Sealed bytes, private keys and full records are never logged.

## 3. Tests

Fixture facts that shape the plan:
- All multi-node parity scenarios share one 3-node cluster
  (`e2e/parity/postgres/multinode_test.go:20-26`) whose tokens are signed with the
  bootstrap key (`fixtureutil.go:190`). Scenarios that invalidate the bootstrap
  key or use `invalidateCurrent` on `client` would break every later scenario, so
  they get their own cluster (`MustSetupMultiNodeWithEnv` with a short
  `CYODA_AUTH_CACHE_RECONCILE_INTERVAL`). Scenarios that only issue, invalidate,
  reactivate or delete issued key pairs run in the shared registry (postgres and
  cassandra) and delete their key pairs at the end.
- In-process e2e stacks each generate a fresh bootstrap key
  (`internal/e2e/callback_harness_test.go:190-205`), so restart tests need a
  harness option to reuse one PEM, and their own database so other stacks' key
  pairs do not appear as retired.
