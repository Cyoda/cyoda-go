# #477 design brief — no search path materialises a model

Companion to `2026-09-01-477-search-fallback-research.md` (the facts). This
is the agreed design, written for an independent reviewer before the spec.
**Revision 2** — after the first independent review. What changed and why is
in §"Revision notes" at the end.

## Goal

The property #475's contract requires: **no search path materialises a
model.** Today it is a property most paths happen to have: one engine branch
and four plugin-internal helpers still load a whole model into a slice, and
one shipped backend copies every entity's bytes on every search.

## What changes

### A. Engine — `SearchService.Search` (`internal/domain/search/service.go`)

1. **`Limit >= 1` is required.** `Limit <= 0` is a caller contract
   violation and returns a plain error (not a 400: no transport can produce
   it — HTTP resolves `DefaultDirectSearchLimit`, gRPC rejects `< 1` and
   defaults), exactly as `spi.Searcher.Search` and `spi.EntityStore.GetPage`
   treat it. No production caller passes `Limit <= 0` (research §4).
2. **A nil condition is rejected in `Search` and `SubmitAsync`** with
   `400 INVALID_CONDITION`, before `ValidateCondition` — not inside it:
   `ValidateCondition(nil)` is vacuously valid and two external callers rely
   on nil meaning "select everything" (delete-all) or guard it themselves
   (grouped stats). The downstream `cond == nil` special case is deleted.
3. **Translation failure is a 400.** `translateErr` goes through
   `ClassifyStoreQueryError` first — `ConditionToFilter` wraps
   `spi.ErrInvalidFilterPath`, `spi.ErrUnknownOperator` and the pattern
   compiler's error, and the client-visible code must not depend on which
   layer rejected the input (`INVALID_FIELD_PATH` for a path-shaped failure)
   — then defaults to `400 INVALID_CONDITION` carrying the translator's
   message. No new error code: the branch is unreachable from the wire
   (research §3a), so a new code could never earn the e2e coverage the
   project requires of one. Unit tests reach it with a caller-built
   `predicate.Condition` type outside the five wire types (validation
   accepts unknown types; translation rejects them).
4. **Routing is a two-rung ladder, then fail closed:**
   - store implements `spi.Searcher` → `Searcher.Search` (unchanged);
   - otherwise → `Iterate` with the translated filter (pushdown at the
     store, residual inside `Next()` by the same kernel), drained to at most
     `Limit + 1` entities; the `Limit + 1`-th raises `400
     SEARCH_RESULT_LIMIT` (`spi.ErrSearchResultLimitExceeded` cause) and
     the iterator is closed without reading further. `TrackingRead` and
     `PointInTime` forward as today; `OrderBy` stays out of `IterateOptions`
     (in-tx ordered iteration is an error at the SPI) and the bounded match
     set is sorted in Go by `sortEntities`, as today. Peak memory:
     `Limit + 1` entities. On this rung a 400 may leave up to `Limit + 1`
     entities recorded in the read-set — a prefix, never the model.
   `drainIterate` becomes this bounded drain rather than being deleted.
   There is **no `GetPage` rung**: offset paging outside a transaction is
   not a snapshot (each page is its own statement; a concurrent insert or
   delete sorting before the cursor shifts the window, so a match can be
   skipped — a silently wrong result, which the project forbids — or
   returned twice). A store with neither capability is refused (see B2).
5. **Async executor** (`runAsyncJob`): the translate-failure branch that
   called `Search` is deleted. A translation failure at execution fails the
   job closed (`writeAsyncFailure`). `SubmitAsync` dry-runs
   `spi.ConditionToFilter` against the validated FieldsMap and answers via
   the same classification as A3 on failure, so a submitted job carries a
   condition that translated at least once; an execution-time failure can
   then only mean the schema changed after submission. Cost: one
   translation per submit, result discarded.

### B. SPI — `cyoda-go-spi` (one PR, before the row-14 tag)

1. **`EntityStore.GetAll` and `GetAllAsAt` are removed.** After A and C they
   have no caller; a required whole-model read on the interface invites the
   next one. The replacements are `GetPage` (paged) and `Iterate` with a
   zero-value filter (streamed).
2. **`Iterate` moves onto `EntityStore` as a required method; the
   `Iterable` interface is deleted.** Every engine path that reads more than
   one entity — direct search's second rung, async search, delete-all,
   conditional delete, grouped stats — already requires it and fails closed
   without it (five type assertions, each with its own refusal branch). All
   four in-house backends implement it. An optional capability that every
   consumer requires is a fiction, and the five refusal branches are dead
   code once the compiler guarantees the method. `Searcher` stays optional:
   it is the bounded-or-fail optimisation over `Iterate`.
3. spitest: the `GetAll` empty/populated cases, `GetAllAsAt`,
   `GetAllAsAt/CommittedOnlyInTx`, `TenantIsolation/GetAll`, and
   `testEntityEmptyTenant`'s use are deleted or moved to `GetPage`;
   `TenantIsolation/GetPage` is **added** (it does not exist today). The
   `Iterable` conformance suite stops gating on a type assertion. SPI test
   doubles (`default_save_all_test.go`, `persistence_extendschema_test.go`)
   drop the methods.
4. Doc comments: `Searcher` (`:8-11` "fall back to in-memory filtering",
   `:26-28` "identical to what GetAll + in-memory match would produce") and
   the former `Iterable` doc (`:42-46`) state the new contract: a store
   without `Searcher` is searched through `Iterate` with a bound; there is
   no in-process whole-model path.
5. CHANGELOG `### Breaking` entry for both removals and the move.

### C. Plugins (memory, sqlite, postgres) — sibling defects, same family

1. Delete the `GetAll`/`GetAllAsAt` methods.
2. **memory + sqlite in-tx `Count` / `CountByState`** currently call their
   own `GetAll` to build the merged view and count it (O(model)). Replace
   with one committed query at `tx.SnapshotTime` minus the buffered ids,
   plus the buffer:
   `count = committedTotal − Σ_chunks committed(id IN chunk) + |buffered
   entities of this model not in tx.Deletes|`, where the chunks partition
   `Buffer ∪ Deletes` under `sqliteMaxVariableNumber` (disjoint chunks sum
   correctly; a chunked `NOT IN` would not). `CountByState` is the same
   with `GROUP BY state`, the buffered entity supplying its own state. No
   per-id lookups. `tx.Deletes` carries no model, so a deleted id that is
   not committed in this model contributes nothing — the `IN` subtraction
   handles that by construction. Postgres counts on the transaction's
   connection and needs nothing.
   Gate-6 sibling: `CompareAndSave` does not clear `tx.Deletes` (memory
   `:224-237`, sqlite `:392-393`), so delete-then-CAS leaves an id in both
   `Buffer` and `Deletes`; `Save` and `Delete` keep them disjoint. Seal the
   invariant in `CompareAndSave` so every reader agrees.
3. **sqlite in-tx `Iterate`** materialises the merged view via the private
   `getAllTx`. Replace with `spi.MergeOrdered` over a committed cursor and
   the sorted buffered adds — the unbounded twin of `searchTxOverlay`'s
   `spi.MergeBounded`. Constraints the first review established: the
   committed cursor reads from `readDB`, never the single writer connection
   (a second statement on `s.db` while a cursor is open deadlocks; committed
   rows at `tx.SnapshotTime` are the same bytes on either connection);
   `adds` and `tx.Deletes` are copied into locals at open under
   `tx.OpMu.RLock` (the overlay is snapshotted at call time per the
   contract); with `TrackingRead`, each yield records under a short
   `OpMu.RLock` with a `RolledBack` check. `getAllTx` then has no caller
   and is deleted.
4. **sqlite in-tx `GetPage`** (`getPageTx`) drains
   `offset + limit + len(tx.Deletes)` committed rows before merging, so a
   deep page — and the last page of any in-tx `ListEntities` scan —
   materialises the model. Rewrite it over the same `MergeOrdered` stream
   as C3, discarding the first `offset` merged rows as they are pulled;
   memory bounded to `limit + len(adds)`.
5. **memory `Searcher.Search`** calls `getAllSnapshotUnlocked` on every
   branch (`searcher.go:72`, `:101`, `:118`) and `currentStateMatchesUnlocked`
   copies too (`:238`): each search deep-copies every entity's `Data` bytes
   in the model before filtering. Filter over pointers under `entityMu`
   (the immutability invariant `buildSnapshot` already relies on) and copy
   only survivors, which `matchSortBounded` bounds at `Limit + 1`.
6. `make repin-plugins` after plugin code changes.

Accepted and documented, not changed: the memory plugin's in-tx `GetPage`
builds a merged pointer map and sorts it per page (`entity_store.go:971-993`).
It is CPU per page over pointers; no payload is copied. Streaming it would
need a sorted index the memory store does not keep.

### D. Tests

- The six unit tests pinning the old fallback are rewritten against the
  `Iterate` rung. An explicit contract test: a store wrapper without
  `Searcher` is searched, `Iterate` is called, the result is correct, and
  bounded-or-fail raises after exactly `Limit + 1` yields (yield count
  asserted). It carries the one real assertion of the deleted e2e test: Go
  `sortEntities` on this rung agrees with SQL `ORDER BY` on the `Searcher`
  rung for a numeric sort key.
- Unit tests for A3 (classified translation failure, both codes), A2, A1,
  A5 (dry-run 400; execution-time failure → job FAILED).
- Plugin tests for C2 (each buffer shape: create, update, delete of
  committed, create-then-delete, delete-then-CAS, state change), C3/C4
  (yield sequence equals the old materialised sequence; deadlock-free with
  a same-tx `Delete` while the iterator is open; `TrackingRead` gating),
  C5 (survivor-only copies; results unchanged).
- Test call sites: **70 lines in 17 files** read a model with `GetAll`.
  Most migrate to a shared drain helper over `Iterate`. Two are not
  mechanical: `e2e/parity/txsearchryw/tx_search_ryw_test.go:198-231` uses
  `GetAll` as the RYW oracle ("Search = GetAll + Prepare.Match") → the
  oracle becomes an `Iterate` drain with a zero-value filter plus
  `Prepare.Match`; `internal/e2e/list_intx_readset_test.go:154-201` uses
  `GetAll` as the "model-wide read-set" control leg → the control becomes
  a full `GetPage` drain, which records identically.
- `internal/e2e/search_test.go` `TestSearchSort_PushdownFallbackAgree` is
  deleted: its premise (a wildcard leaf fails translation) is stale since
  row 11 and it compares pushdown with itself.
- Exit checks (greppable): no `GetAll(`/`GetAllAsAt(`/`getAllTx`/`Iterable`
  in non-test code of the three repos; `grep -rn GetAll plugins/
  internal/domain/search` finds no prose describing behaviour by reference
  to it (about forty comments today); no `cond == nil` in
  `search/service.go`; no `ErrBackendNotSupported` "neither" branch; the
  `drainIterate` mention in `entity/grouped_stats_service.go:351` updated.
- The strongest exit check is the compiler: once the SPI has no `GetAll`,
  no engine or plugin build can call it.

## Wire contract

Unchanged. Every status/error code on every search, delete and list endpoint
stays. The 400s A2/A3 add are unreachable from a client today and are
covered at unit level. Gate 7: an edit to the two existing parity docs that
describe the fallback, no new file.

## Explicitly out of scope

- `internal/match` traversal sharing with the kernel (#464).
- Memory/sqlite in-tx `Iterate` tracking every scanned row into the
  read-set (`service.go:650-657` follow-up).
- The memory plugin's per-page pointer sort (above).

## Revision notes (v1 → v2)

- **Dropped the `GetPage` rung** (v1 A4/A5). The reviewer showed offset
  paging is not a snapshot outside a transaction; a skipped match is a
  wrong-but-available answer. `Iterate` is one cursor and already the
  streamed primitive every other engine path uses.
- **`Iterate` becomes required; `Iterable` goes.** Follows from the above:
  once direct search needs it too, every consumer requires it and the five
  fail-closed branches are dead.
- **Added C4 and C5**: sqlite in-tx `GetPage` drains to `offset + limit`,
  and memory `Search` deep-copies the model's bytes. Both are the property
  under repair, on shipped backends.
- **C2 restated** as one committed query minus disjoint `IN` chunks plus
  the buffer, with the `CompareAndSave` invariant seal.
- **A3 classifies** through `ClassifyStoreQueryError` before defaulting.
- **A1 is a plain error**, not a 400; **A2 lives in `Search`/`SubmitAsync`**.
- Test inventory corrected (70 lines, 17 files; two non-mechanical);
  spitest `TenantIsolation/GetPage` must be added.

## Revision notes (v2 → v3, after the second review)

The spec `docs/superpowers/specs/2026-09-01-477-no-search-path-materialises-design.md`
supersedes this brief. What the second review changed:

- **sqlite `Begin` must gate on in-flight commits** before any in-tx read
  can use `readDB`: `Commit` bumps `lastSubmitTime` (step 4) before its
  `sqlTx` commits, and `Begin` floors `SnapshotTime` to it without waiting.
  Today the single writer connection queues every in-tx read behind the
  flush, which hides the window. Prerequisite for C2–C4.
- **`unstageDelete` helper** deleting from both `tx.Deletes` and
  `tx.DeleteAttribution`, called from `Save` and `CompareAndSave`;
  `Save` today clears only `Deletes`.
- **memory `Iterate` records on yield**, not the whole merged model at
  open; the former out-of-scope line is withdrawn.
- **in-tx `DeleteAll` stages ids without payload copies** on both plugins.
- **memory `Search`**: pointer snapshot under the lock, filter outside it.
- **`json_each` instead of chunked `IN`** for the in-tx counts.
- **Three PRs**: plugin internals (no SPI change) → SPI → engine + pin.
- SPI `MAINTAINING.md` pre-1.0 break conditions: cassandra#95 addendum is
  the KNOWN_CONSUMERS notification; CHANGELOG states why no deprecation
  window (a deprecated `Iterable` alias would keep the dead branches
  compiling).
