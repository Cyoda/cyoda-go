# #598 — should a failed scheduled run be retried?

Status: decision brief, 2026-09-25. The product owner asked: what if cyoda-go
does not retry a failed scheduled transition at all, like Cyoda Cloud? This
brief gives the facts and the two viable answers.

## Terms

- **Task**: the stored record "fire transition T of entity E at time X".
- **Run**: one attempt to fire a task.
- **Owner**: the cyoda-go processing node (pnode) that claimed the task and
  runs it. It is not the user of the run's transaction.
- **Unsafe processor**: a processor whose `config.idempotent` is not true. The
  platform must never run it twice on its own initiative.
- **Hand-off**: the moment a processor request reaches a compute node. After
  it, the compute node may have done the work, even if the run then fails.
- **Safe failure**: a failed run in which no unsafe processor was handed off.
  Running it again cannot repeat unsafe work.
- **FAILED**: a task that stopped for good. It stays stored, is visible in
  `GET /scheduled-tasks`, and records `SCHEDULED_TRANSITION_FAIL` on the
  entity. It never moves the entity. An entity write re-arms or removes it.

## What Cyoda Cloud does

- A task runs once. Any failure of the action marks the task `FINISHED` with
  `success=false` and a `FAIL:` message. It is not run again
  (`~/dev/cyoda-platform/core-libs/service/src/main/java/com/cyoda/service/scheduling/ExecuteScheduledTaskActionProcessor.java:59-66`).
- Only a storage error is retried, up to three attempts, and that retry runs
  the action again, including its processors
  (`runnable-apps/processing/.../EventReferenceRunnableTask.java:283-287`).
- The failure is visible only on the task row and in logs. Cloud has no API to
  list tasks.

## What the current #598 design does (option A)

- A safe failure is retried with a growing delay until the transition's
  `timeoutMs` passes. Without `timeoutMs` it is retried without end, and stays
  visible.
- Before each unsafe processor is dispatched, the owner writes a durable
  **mark** on the task. A later run that finds the mark does not run: the task
  becomes FAILED.
- The mark is removed only if the callout layer proves the request never
  reached a compute node (for example: no compute node was connected). This
  proof needs changes in the callout layer (plan stream K, 7 tasks).
- A run that committed part of a cascade and then stopped becomes FAILED
  (`PartialCommit`), because a retry would start from the wrong state.
- A task whose owner is lost three times becomes FAILED.
- A watchdog stops an owner's runs before other pnodes may treat it as lost, so
  a retry on another pnode never overlaps the old run.
- At shutdown, a run whose unsafe processor is in flight is not cut.

## What "no retry" would mean here (option B)

- Any failed run makes the task FAILED at once, with the error recorded.
- A task taken from a lost owner becomes FAILED. The new pnode does not run it,
  because it cannot know how far the old run got.
- At shutdown, every run in progress is waited for, up to the existing grace
  period. A run cut after that is reclaimed later and becomes FAILED.
- A criterion that evaluates to false, a late first run (expired), and a
  cancelled task behave as in option A.

**Removed from the plan by option B:** the mark and its store methods; the
callout-layer proof (stream K, the change with the most risk); `PartialCommit`;
the attempt count, the retry delays and "expired after failed attempts"; the
lost-owner cap; the watchdog; the shutdown exemption for unsafe work. That
removes 12 of the ~90 tasks outright (K-1 to K-7, E-4, E-5, T-6, T-10, T-12)
and shrinks about 18 others (estimate). Three settings go
(`CYODA_SCHEDULER_RETRY_DELAY`, `…_RETRY_DELAY_MAX`, `…_MAX_LOST_OWNERS`).

**Kept by option B:** claims, the heartbeat, the task-row write in every commit
(it stops an old owner from committing after its task was taken), FAILED with
its audit event, `GET /scheduled-tasks`, the delete and import clean-up.

Both options meet the #598 guarantee that an unsafe processor is never repeated
by the platform. They differ in what happens after a failure that could safely
be run again.

## Option A — retry safe failures (current design)

Pros:
- A short outage heals by itself. The common case is a compute node that is
  not connected when the timer fires (for example during the application's own
  deploy), or a database failover. The platform runs the task again when it is
  safe, before `timeoutMs`.
- The platform is the only party that knows whether unsafe work was handed
  off. With option B the application must decide whether to re-arm, without
  that knowledge.
- A pnode crash or a lost database connection does not fail every task the
  pnode was running.

Cons:
- 12 more tasks and larger versions of about 18 others, including callout-layer changes shared with
  ordinary transitions.
- More states to explain: attempts, retry delays, `PartialCommit`, lost-owner
  cap.
- cyoda-go defines the contract and Cloud follows it (Gate 7). Cloud would have
  to add retries, marks and the hand-off proof to match. That is a large Cloud
  change.
- A failure that will never succeed (a processor bug) is retried until
  `timeoutMs`, or forever without it. It stays visible, but it uses capacity.

## Option B — no retry, like Cloud

Pros:
- A much smaller change, and the riskiest part (the callout-layer proof) is not
  needed.
- One simple rule for users and operators: a scheduled run happens at most
  once; if it fails, the task is FAILED and visible.
- Cloud already runs a task once. Its parity work is smaller: it still needs
  the task query, and its storage-error retry must stop repeating processors
  (a Cloud defect under either option).

Cons:
- Every short outage becomes a permanent FAILED task. The application must
  watch for `SCHEDULED_TRANSITION_FAIL` or poll `GET /scheduled-tasks`, and
  write the entity to re-arm it. Until notifications exist, that is polling.
- A pnode crash fails every task it was running, even tasks that had not yet
  called any processor.
- The published promise changes from "fires once, retried when safe" to "fires
  at most once". Applications that use timers for time-outs (for example
  "cancel the order after 30 minutes") must add their own recovery.

## Why there is no third option

Keeping retries but dropping only the callout-layer proof saves 7 tasks. It
then treats "no compute node was connected" — the most common short outage —
as unsafe, so that case becomes FAILED as in option B, while all the other
machinery of option A stays. It has most of B's cost and little of its saving.

## Recommendation

Option A. A timer that silently needs the application to rescue it after every
short compute-node outage moves the hardest part of the problem — knowing
whether unsafe work happened — to the party that cannot see it. The extra work
is already designed, reviewed and planned.

Choose option B if matching Cloud with the smallest change matters more than
self-healing timers. The plan then shrinks as listed above, and the spec needs
one more review round before execution.
