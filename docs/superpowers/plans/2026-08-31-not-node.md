# NOT node — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `NOT` to the condition language, and close the three defects that `NOT` would otherwise turn from a silently-short answer into a positively wrong one.

**Architecture:** `spi.Filter` gains a `FilterNot` branch node carrying exactly one child. Evaluation stays two-valued, which is sound only because a leaf that cannot be evaluated is refused before any entity is read — so `spi.Prepare` gains an error return and the swallow sites propagate it. Separately, an *unsatisfiable* comparison is not a failure but a determinate answer, and today it answers `false` for every operator; it is fixed to follow operator polarity per stored-value type family.

**Tech Stack:** Go 1.26+, `github.com/tidwall/gjson`, testify, testcontainers-go (postgres e2e). Two modules: `cyoda-go-spi` (the SPI) and `cyoda-go` (engine + three plugin submodules, each with its own `go.mod`).

**Spec:** `docs/superpowers/specs/2026-08-30-not-node-design.md`

In `eval_leaf.go`, delete the `if exp.void { return false }` arm from `EvalLeaf` — `void` stops being an evaluation signal — and make `evalCompare` report whether the stored value's family had any candidate sub-condition:

```go
// isNegativeOp reports whether op asserts the ABSENCE of a relation. When no
// sub-condition survives for the stored value's own type family, the comparison
// is unsatisfiable for that value: a positive operator is false and a negative
// one is true. Null and absent are handled earlier and never reach here.
func isNegativeOp(op FilterOp) bool {
	switch op {
	case FilterNe, FilterINe,
		FilterNotContains, FilterINotContains,
		FilterNotStartsWith, FilterINotStartsWith,
		FilterNotEndsWith, FilterINotEndsWith:
		return true
	}
	return false
}
```

Change `evalCompare` to return `(matched bool, familyHadCandidate bool)`. Each `case` in its `switch stored.Type` reports `true` for the second value when at least one sub-condition was considered for that family — for `gjson.Number`, when any `e.numeric` entry passed `IsAssignableTo`; for `gjson.String`, when any `e.temporal` entry matched the stored subtype or any `e.others` entry was applicable; for booleans, when any `e.others` entry had `typ == Boolean`. At `EvalLeaf`'s `kindCompare` arm:

```go
case kindCompare:
	matched, hadCandidate := exp.evalCompare(stored)
	if matched {
		return true
	}
	if !hadCandidate {
		return isNegativeOp(exp.op)
	}
	return false
```

Apply the same shape to `kindStringOp`'s non-textual-slot arm: a string operator against a non-string stored value has no candidate, so a negative string operator answers `true` there.

```go
func validateFilterPaths(f spi.Filter) error {
	// Recurse on the presence of a subtree rather than on the operator name:
	// naming each branch operator reproduces this defect for the next one added,
	// and the property that matters is that the node HAS a subtree.
	if len(f.Children) > 0 {
		for _, c := range f.Children {
			if err := validateFilterPaths(c); err != nil {
				return err
			}
		}
		return nil
	}
	if f.Path == "" {
		return nil
	}
	return validateJSONPath(f.Path)
}
```
