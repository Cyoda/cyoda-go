Submit times, snapshots and the consistency time

This page shows, for each storage backend, four things. When a commit gets its submit time. When the commit becomes visible. When a transaction fixes the data that it reads. How the store calculates the consistency time C, and why a point-in-time read at or before C is final.

Terms

Each definition uses only the terms above it.

commit X

A change that the store makes visible to other readers as one unit. There are two kinds:

  • A transaction that ends with Commit.
  • A save, update or delete outside a transaction. The store commits it at once.

All of this page applies to both kinds.

store clock
The clock that the store reads to calculate its times. memory and sqlite read the clock of the cyoda-go process. postgres reads the clock of the database server, with clock_timestamp().
floor
A time value, to the microsecond, that the store keeps. The floor never goes back. memory and sqlite keep one floor per store instance, in memory (lastSubmitTime). postgres keeps one floor per database, in the sequence cyoda_stamp_floor. All nodes and all tenants share it.
submit time, s(X)

The date and time, to the microsecond, that the store records for commit X when X is submitted. GetSubmitTime returns it.

When: the store takes it inside Commit, after the waits and checks that come first, and before the commit is complete.

Value: s(X) = max(store clock, floor + 1 µs). The store then sets the floor to s(X). So each submit time is later than all earlier submit times.

Use: the store dates each entity version that X writes with s(X). That date is the lastUpdateTime of the version. For an entity that X creates, it is also the creationDate. Each audit event that X records has s(X) as its utcTime.

completion, f(X)
The moment from which other readers can see the writes of X. f(X) is always after s(X). The section of each backend shows what f(X) is.
in flight
X is in flight from s(X) until f(X), or until X aborts. While X is in flight, X has its submit time, but other readers cannot see its writes.
snapshot of A; A sees X
A is a transaction. The reads of A (without a pointInTime) return the entity versions of a fixed set of commits, plus the writes of A itself. That set of commits is the snapshot of A. "A sees X" means that X is in the snapshot of A.
SnapshotTime
memory and sqlite only. The value that Begin records for A: max(store clock, floor). Begin then sets the floor to SnapshotTime. So each later commit has a submit time after SnapshotTime. postgres records no SnapshotTime.
snapshot moment, m(A)
The moment, during Begin, at which the snapshot of A is fixed. After m(A), the snapshot does not change. A commit that is not in the snapshot stays invisible to A, also when A reads again. memory and sqlite: m(A) is when Begin records SnapshotTime. postgres: m(A) is when Begin runs its first statement.
point-in-time read at T
A read with pointInTime = T. For each entity, it returns the last committed version with a submit time at or before T. Inside a transaction A, it also reads committed versions only. It does not use the snapshot of A or the writes of A.
snapshot instant, T(A)

The instant at which the reads inside transaction A see the data.

  • memory and sqlite: T(A) = SnapshotTime.
  • postgres: T(A) = m(A), as a reading of the server clock. The plugin does not record this value.

The rule for which commits A sees is different on the two kinds of backend:

  • memory and sqlite: A sees X if, and only if, s(X) ≤ T(A).
  • postgres: A sees X if, and only if, X completed before T(A). So each commit that A sees has s(X) < T(A). But a commit with s(X) < T(A) that is still in flight at T(A) is not in the snapshot of A.

Example on postgres: commit B is submitted at 10:00:05. The snapshot of A is fixed at T(A) = 10:00:08. B completes at 10:00:09. A does not see B. A point-in-time read at 10:00:08 does include B, because s(B) ≤ 10:00:08.

This is not a consistency defect. A still sees one fixed set of complete commits. But on postgres, T(A) used as a pointInTime does not show exactly what A saw.

consistency time, C

The instant that ConsistencyTime calculates and returns for a tenant. GET /entity/consistency-time returns C. When ConsistencyTime returns C, two facts are true:

  • Each commit with s(X) ≤ C is complete or aborted. On postgres, this applies to the commits of the calling tenant. Reads are per tenant, so that is sufficient.
  • Each later commit has a submit time after C.

C never goes back. sqlite and postgres keep this property also after a restart. The engine compares the pointInTime T of each point-in-time read with C. If T ≤ C, the read runs, and its result is complete and final. If T > C, the engine refuses the read with 400 POINT_IN_TIME_AFTER_CONSISTENCY_TIME.

Why a read at T ≤ C is final

This is the same on every backend.

The floor and the consistency time

The floor follows the store clock, but it never goes back. Three events move it:

  • A commit gets its submit time. The floor moves forward by at least 1 µs.
  • A transaction on memory or sqlite gets its SnapshotTime.
  • ConsistencyTime calculates a consistency time.

The floor alone does not tell which commits are complete. On postgres, commits with a submit time at or before the floor can be in flight at any moment. C is a reading of the floor plus one guarantee: each commit with s(X) ≤ C is complete or aborted. ConsistencyTime makes this guarantee in three steps:

  1. Reserve. Set the floor to max(store clock, floor). That value is C. From now on, each new commit has a submit time after C.
  2. Wait. Wait until each commit that already has s(X) ≤ C is complete or aborted.
  3. Return C.

New commits move the floor forward while ConsistencyTime waits. C does not move with the floor. So C is always at or below the floor. The wait step is different on each backend:

  • memory: no wait is necessary. Each read waits for the write lock of a commit in flight.
  • sqlite: the reserve waits for the commit gate. So no commit is in flight at the reserve.
  • postgres: ConsistencyTime waits for the markers of the commits in flight.

The sections below define the write lock, the commit gate and the markers.

memory

The store has two locks:

  • The write lock entityMu. A commit takes it before its conflict checks, so before its submit time. The commit holds it until it publishes its writes. Each read takes this lock for reading. So each read waits for a commit in flight.
  • The floor lock mu. It protects the floor. Begin and ConsistencyTime take only this lock, so they do not wait for a commit in flight.

f(X) is the moment that X publishes its writes and releases the write lock.

sqlite

One commit gate serializes the whole commit path. A commit takes the gate before its submit time. It holds the gate until its database commit is complete. f(X) is the moment that the database commit of X is complete and X releases the gate.

Begin and ConsistencyTime take the same gate. So no commit is in flight while they hold it. A read outside a transaction does not take the gate. It sees X from f(X).

postgres

Commit

A commit runs these steps inside its own database transaction:

  1. It checks its read set.
  2. It runs SELECT cyoda_stamp(…). cyoda_stamp first takes the marker of the tenant. Then, under the floor lock, it sets s = max(clock_timestamp(), floor + 1 µs) and sets the floor to s.
  3. It dates its rows with s.
  4. It writes its row in submit_times.
  5. It runs COMMIT. f(X) is the moment that COMMIT is complete.

The marker is a transaction-level advisory lock with a key per tenant. PostgreSQL releases it when the transaction ends. So the marker exists while X is in flight. The floor lock is the advisory lock (0, 0). cyoda_stamp holds it for a very short time.

Commits that write different entities do not wait for each other. So a commit with a later submit time can complete first. Begin and reads do not wait for a commit in flight. Only ConsistencyTime waits, for the markers.

Begin and the snapshot

Begin runs BEGIN ISOLATION LEVEL REPEATABLE READ, and then its first statement, SELECT set_config(…). REPEATABLE READ fixes the snapshot at the first statement. So that moment is m(A), and T(A) = m(A). The PostgreSQL function now() returns the time of BEGIN, which is earlier than m(A). The snapshot contains the commits that completed before m(A). Submit times are not part of this rule.

ConsistencyTime

The database function cyoda_consistency_time runs these steps:

  1. Under the floor lock, it sets C = max(clock_timestamp(), floor) and sets the floor to C.
  2. It reads, one time, the list of markers of the tenant that are held at that moment.
  3. It waits for each marker in that list.
  4. It returns C.

A commit with s(X) ≤ C took its marker before its submit time, so before the reserve. So its marker is in the list, or the commit is already complete or aborted. A commit that takes its marker after step 2 takes its submit time after the reserve, so its submit time is after C.

The wait has a limit of 10 s, or the statement timeout if that is lower. After the limit, the call fails with 503 CONSISTENCY_TIME_UNAVAILABLE.

Point-in-time reads

A point-in-time read at T runs on a separate pool connection. It does not use the snapshot of a transaction. It selects the committed versions with a submit time at or before T. The engine runs it only when T ≤ C. At that time, each commit of the tenant with s(X) ≤ T is complete or aborted. So the result is complete and final.

cassandra (commercial plugin)

The cassandra plugin does not implement the consistency time yet. When it does, its C must have the same properties as on the backends above. cassandra reads at millisecond resolution. So its C must also cover the whole millisecond that contains C. This section will show its timing then.

Which instant shows what a transaction did

  • The result of commit X. On every backend, this instant is s(X). Each audit event of X has it as utcTime. A point-in-time read at s(X), when s(X) ≤ C, shows each entity that X wrote exactly as X left it. It also shows each commit with an earlier submit time.
  • The data that transaction A read. On memory and sqlite, this instant is T(A) = SnapshotTime. A point-in-time read at T(A) shows the committed data that A saw. On postgres, no single instant shows it. A point-in-time read at T(A) can also include commits that were in flight at T(A), which A did not see.
  • Neither point is a consistency defect. On every backend, a transaction sees one fixed set of complete commits, plus its own writes. A conflicting concurrent change makes its commit fail.
