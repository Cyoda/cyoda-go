# docs/cloud-parity — Cloud-facing implementation contracts

cyoda-go **defines** the API and integration contract; Cyoda Cloud follows and
mirrors it. This folder holds the Cloud-facing implementation specs — contracts
written precisely enough for the Cyoda Cloud team to implement twin-alignment.

There is no shared ticketing system across the two streams yet; this folder is
the interim coordination surface. Each file in this folder describes a feature
or behaviour that Cloud must implement to stay aligned with cyoda-go.

## Relationship to cloud-divergences.md

`../cyoda/cloud-divergences.md` is the **inverse vector**: fields cyoda-go
*declares* in its OpenAPI spec but does not yet implement on the OSS server side.
This folder is the opposite direction — behaviour cyoda-go *has implemented* that
Cloud needs to adopt.

| `signing-key-pairs.md` | Key pairs have no `audience`: one signer for every token. Key pairs are shared across the cluster and persisted, including the bootstrap key's invalidate/reactivate/delete state; a rotation (`invalidateCurrent`) ends issued key pairs only, never the bootstrap key, as Cloud's `LOCAL_FILE` key is never a sibling; deleting the bootstrap key is terminal until `CYODA_JWT_SIGNING_KEY` is replaced; replacing it retires every key pair the old key owned (no Cloud equivalent — Cloud's configured key is not stored); a retired, foreign-bootstrap-state or already-deleted-bootstrap key pair is `404`, never a stale `200` — a broken (unopenable) one still answers `200` on `invalidate`/`reactivate`/`delete` and only fails, `500` not `404`, on `current`/token issuance if it wins signer selection; `current`/JWKS read only the node's own copy and can answer `503` only when that copy is stale, `invalidate`/`reactivate`/`delete` read the store directly and can answer `503` only when the store itself reports unavailable, and a stale copy at token issuance is a plain `500` instead; at-rest sealing is an implementation detail, not part of the contract. For Cloud: CP-3979 |
| `tenant-id-grammar.md` | The shape of a tenant identifier. The grammar `^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$` — 1–100 bytes, case significant — enforced at each door a tenant id enters through (the `caas_org_id` claim, covering HTTP and gRPC alike; the `{tenant}` segment of the token URL; `cyoda token --tenant`, before signing), with a rejected claim answered as an ordinary `401` that never echoes the value; the evidence behind the charset and the 100-byte cap, and CP-3968 for Cloud, which constrains the claim nowhere today. | `trusted-key-tenant.md` | A trusted key belongs to the tenant that registered it and verifies tokens for that tenant only — never bound by a claim in the token it signs. In cyoda-go it verifies only the user assertion of a token exchange by an on-behalf-of client, read from the store in that client's tenant on every exchange; another tenant's `kid` is `400 invalid_request` like an unknown one. Trusted-key JWTs are not bearer tokens. Key ids are unique per tenant; register is an upsert; no grace period and no `audience`; the cap applies to reactivation. For Cloud (CP-3974): bind the key's legal entity, stop accepting trusted-key bearer tokens |
| `user-id-rule.md` | A user identifier is valid UTF-8, 1–255 characters, with no control character (C0, DEL, C1), no noncharacter and no U+FFFD — the characters CloudEvents forbids in `authid`, plus the one a JSON decoder substitutes for invalid input — is not the reserved id `system` in any letter case, and nothing is normalised. One check at every door: a token's `caas_user_id`/`sub` claim (`401`) and an OBO user assertion's `sub` (`400 invalid_request`); `cyoda token --user` checks it too before signing. A present `caas_user_id` that is empty, non-string or invalid never falls back to `sub`. For Cloud: check `sub` before auto-enrollment, reserve `system`, and reconcile the 100-character `userName` column with the 255 cap |
| `m2m-clients.md` | A tenant holds at most a configured number of M2M clients: `POST /clients` at the cap answers `400 M2M_CLIENT_CAP_REACHED` (not retryable) and creates nothing; every client of the tenant counts, a delete frees a slot, a secret reset is not capped; cyoda-go's check can be exceeded by one client per node under concurrent creates. On-behalf-of clients (`?onBehalfOf=true`): token exchange only, never `ROLE_ADMIN`, never in `PLATFORM`, `onBehalfOf` on the DTOs and the token-exchange `grant_type`; `503 SERVER_BUSY` when no secret-hashing slot is free. Clients being stored, shared by every node and kept across restarts is not a contract change — Cloud already behaves so. For Cloud: CP-3980 |
| `tenant-scoped-clients.md` | A client id is unique only inside its tenant: the token endpoint is `POST /api/tenants/{tenant}/oauth/token` (the old path is gone), a client is found by (tenant, client id), and an unknown tenant, unknown client and wrong secret are the same `401 invalid_client`, held to 500 ms when decided after a store read; a `{tenant}` that is not an API tenant, or any percent-encoding, is `400 invalid_request`. `POST /clients?clientId=` with the tenant grammar minus `system`; a taken id is `409 M2M_CLIENT_EXISTS` (before the cap, first write wins); a reset losing a race is `409 CONFLICT`, a delete wins; a new client's `cgen` starts at a random number; `SYSTEM` in any case is refused as a token tenant and by `cyoda token`. For Cloud: CP-3983, plus two Cloud defects (wrong secret `400` vs unknown `401`, `Random.Default`) |
| `audit-event-identity-and-order.md` | Audit events carry version / eventId; `actor` gains `kind`, entity-change and state-machine events carry `executedBy`, and state-machine events carry `actor`; one total order; position cursor; the finished endpoint picks the one that sorts first in the audit order when a transaction has two |
| `model-administration-not-joined.md` | Model and workflow administration never runs inside a transaction: a request carrying a transaction token that would import, delete, lock, unlock, change the level of or set the unique keys of a model, or import a workflow, is refused `400 MODEL_ADMIN_IN_JOINED_TRANSACTION` before the token is verified, on HTTP and gRPC alike; read-only model operations and every entity operation are unaffected |
| `commit-in-joined-transaction.md` | A callback never commits the transaction it joined: a `COMMIT_BEFORE_DISPATCH` processor reached from a callback's write is refused at that processor, before the joined transaction is flushed or committed, with `409 COMMIT_IN_JOINED_TRANSACTION` (not retryable), on every entity write door, both `startNewTxOnDispatch` values; the joined transaction is left to its owner; Cloud has no such mode yet |
| `platform-operator.md` | The five signing key-pair operations require `ROLE_ADMIN` in the tenant `PLATFORM`, not any tenant's admin, and refuse an on-behalf-of token; `/admin/log-level` and `/admin/trace-sampler` are cyoda-go only. Two prerequisites for Cloud: bind every token's legal entity to its stored client rather than a claim, and make `PLATFORM`/`SYSTEM` unclaimable by any token but the platform's own. Also found: key-pair lookups reach other tenants' keys by `keyId` alone, a role denial answers `401` not `403`, `SUPER_USER` is granted to every Auth0 user, and OIDC providers are not tenant-scoped (retired). For Cloud: CP-3981 |
| `obo-only-user-identity.md` | Only M2M clients reach the data API (`ROLE_M2M` on every data operation); an application authorizes its users and acts for them through an on-behalf-of client, exchanging an application-signed user assertion (RS256, ≤ 300 s, `aud` = the issuer, a trusted key of the client's tenant) for an OBO token with the client's roles, the user as `sub` and the client in `act`; the user is recorded, never verified; an OBO token never administers, never opens a stream and joins only its own user's transaction; attributed principal and executor on every change, audit event, callout and message; token lifetime 300 s default, 3600 s maximum; token-endpoint cost controls (verified-secret cache, bounded secret checks with `503`, per-client bucket with `429 slow_down`); OIDC provider endpoints retired |
| `consistency-time.md` | The consistency time `C` (complete, final, monotonic, read resolution) and the fence: a `pointInTime` later than `C` is `400 POINT_IN_TIME_AFTER_CONSISTENCY_TIME`, with no waiting; async submit without `pointInTime` records a fresh `C` on the job; `GET /entity/consistency-time` and the gRPC pair `EntityConsistencyTimeGetRequest`/`Response`; `503 CONSISTENCY_TIME_UNAVAILABLE` (retryable) and the gRPC envelope of both codes; pages of a list without `pointInTime` are read at different moments; conditional delete has no match-count limit (Cloud's `entitySearchLimit` is not part of the contract).
