cyoda-go · authentication

Access to the cyoda API

Only M2M clients connect to cyoda-go. An application signs its own users in and decides what each user may do. When it acts for a user, its client exchanges a user assertion the application signed for a cyoda token on the user's behalf (OAuth 2.0 token exchange, RFC 8693). The token carries the client's rights and the user's identity, so cyoda-go records the user and the client with every change and passes both to compute nodes.

Clientclient id + secret→client_credentials→cyoda token for the client→API
For a userapp authorizes the action→app signs an assertion for the user→client exchanges it→cyoda token: client's rights, user's identity→API

This page is the integration guide for application teams. The same guide, with every exact request, is the help topic cyoda help auth integration; the reference topics are cyoda help auth tokens, auth clients, auth trusted-keys, grpc, audit and config auth.

Who is responsible for what

cyoda-go keeps tenants apart, checks what each client may do, and records faithfully which client acted and for which user. The application decides who its users are and what each may do. Like any database, cyoda-go cannot protect data from an application that is itself compromised: that responsibility lies with the application.

DecisionMade by
Who the user isThe application, with any sign-in method it chooses.
What the user may doThe application, before it acts for the user. cyoda-go has no per-user permissions.
Which tenant a request acts incyoda-go: always the client's own tenant. No request can name another; only a platform operator's cyoda token, signed offline with the signing key, names its tenant.
What the client may docyoda-go, from three things only. ROLE_M2M reaches every data operation of the client's tenant (every entity, model and workflow import included), and lets a client's own token open a compute-node stream with any tags. ROLE_ADMIN adds the tenant's client and trusted-key administration. The on-behalf-of permission makes a client one that only exchanges user assertions. There is no finer split: treat every client secret as access to all of the tenant's data.
Rules inside a workflow that need the userThe application's processors and criteria, which receive the user and the client with each callout, for example to keep the submitter of a request from approving it.

Integrate an application, step by step

The common shape: a backend that calls cyoda for signed-in users, background jobs that work for no user, compute nodes that run your processors, and a tenant admin who provisions the rest. Every command below keeps secrets off the command line (-K-, -H @- read them from standard input).

1. Tenant and first admin client — platform operator

cyoda has no tenant registry: a tenant exists as soon as a token names it, and only cyoda token can name one. The node that takes the create call needs CYODA_IAM_M2M_ADMIN_ROLE_ENABLED=true.

ADMIN_TOKEN=$(cyoda token --tenant acme)    # on a host that holds CYODA_JWT_SIGNING_KEY
curl -X POST "https://cyoda.example.com/api/clients?withAdminRole=true" \
  -H @- <<<"Authorization: Bearer ${ADMIN_TOKEN}"

2. One client per part — tenant admin

curl -X POST "https://cyoda.example.com/api/clients?onBehalfOf=true" \
  -H @- <<<"Authorization: Bearer ${TENANT_ADMIN_TOKEN}"     # the backend
curl -X POST https://cyoda.example.com/api/clients \
  -H @- <<<"Authorization: Bearer ${TENANT_ADMIN_TOKEN}"     # each compute node, job, script

Each answer carries client_id (16 characters), client_secret (64 hex characters, shown once), roles, onBehalfOf and the grant_type the client uses. A client has no name: store id and secret at once in your secret store, under a name that says which part uses them. Provision idempotently by creating a client only for a part the store has none for; reconcile by listing GET /clients and deleting every id the store does not hold. A tenant holds at most CYODA_IAM_M2M_CLIENT_MAX_PER_TENANT clients (100). Your application takes its tenant id from configuration; the tenant admin reads it from GET /account.

3. Trusted key — tenant admin

openssl genrsa -out app-key.pem 2048
N=$(openssl rsa -in app-key.pem -noout -modulus | cut -d= -f2 \
    | xxd -r -p | openssl base64 -A | tr '+/' '-_' | tr -d '=')
curl -X POST https://cyoda.example.com/api/oauth/keys/trusted \
  -H @- -H "Content-Type: application/json" \
  -d "{\"keyId\":\"app-key-2026-10\",\"jwk\":{\"kty\":\"RSA\",\"n\":\"${N}\",\"e\":\"AQAB\",\"alg\":\"RS256\"}}" \
  <<<"Authorization: Bearer ${TENANT_ADMIN_TOKEN}"

The keyId matches ^[A-Za-z0-9._-]{1,128}$ and becomes the kid you sign with. Registration needs CYODA_IAM_TRUSTED_KEY_REGISTRATION_ENABLED=true on every node. Without validTo a key is valid CYODA_IAM_TRUSTED_KEY_MAX_VALIDITY_DAYS days (365) from validFrom. Any OBO client of the tenant can use any active trusted key of the tenant.

4. Act for a signed-in user — backend

After your application has authorized the action, sign an assertion — header alg: RS256, kid; claims sub (your stable user id, recorded byte for byte, never system), caas_org_id (your tenant), aud (CYODA_JWT_ISSUER, default cyoda; CYODA_JWT_AUDIENCE plays no part), iat, exp ≤ iat + 300 — and exchange it:

curl -X POST https://cyoda.example.com/api/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
  -d "subject_token_type=urn:ietf:params:oauth:token-type:jwt" \
  -K- <<EOF
user = "${OBO_CLIENT_ID}:${OBO_CLIENT_SECRET}"
data = "subject_token=${USER_ASSERTION}"
EOF

The answer: access_token, token_type: Bearer, expires_in, issued_token_type: urn:ietf:params:oauth:token-type:jwt. Client authentication is HTTP Basic only; form fields client_id/client_secret are not read (401). Cache one token per user and exchange again when less than a minute remains, or once after a 401. Each client may make CYODA_IAM_TOKEN_REQUESTS_PER_MINUTE (600) token requests per minute per node: about 3000 concurrently active users per node at 300-second tokens.

5. Work for no user — jobs and scripts

A plain client and client_credentials (HTTP Basic, grant_type=client_credentials). Changes are recorded as the client's own. Never use an OBO token for work no user asked for, nor a plain client for work a user asked for.

6. Connect a compute node

Open startStreaming with the node's own client_credentials token in metadata authorization, and join with your tags and joinedLegalEntityId = your tenant. The stream outlives its token; cyoda re-checks the client every 60 seconds. Authenticate each callback with the node's current client token, and echo cyodatxtoken as X-Tx-Token / tx-token when the callback must run in the callout's transaction. On Unauthenticated (client deleted or secret reset) re-read the credentials, fetch a token and reconnect, and stop if a fresh token is refused again; on Unavailable reconnect with backoff; PermissionDenied is a configuration error. The CYODA_COMPUTE_* variables are the convention of cyoda's own test compute node; cyoda does not read them.

Feature flags (CYODA_IAM_TRUSTED_KEY_REGISTRATION_ENABLED, CYODA_IAM_M2M_ADMIN_ROLE_ENABLED) are read by each node at startup, and the node that takes a call decides: set them on every node. Neither affects tokens: an exchange works with every key registered while registration was on, on every node.

The token exchange

  1. The client authenticates with its id and secret, and must hold the on-behalf-of permission. Each node bounds how many secret checks run at once and answers 503 when busy; a per-client rate limit (429) applies to every grant and exchange. Both answers carry Retry-After.
  2. subject_token_type is urn:ietf:params:oauth:token-type:jwt; other RFC 8693 parameters, such as actor_token, are refused.
  3. The trusted key named by the assertion's kid is read from the shared store, in the client's tenant; a key of another tenant is never found. If the store cannot be read, the exchange is refused: 503 when the store reports itself unavailable, 500 for any other failure.
  4. The assertion's RS256 signature, exp and iat (both required, at most 5 minutes apart, 30 seconds of clock skew), nbf if present, aud (must contain CYODA_JWT_ISSUER), its issuer if the key lists issuers, and caas_org_id = the client's tenant are checked. typ, jti and every other claim are ignored; an assertion can be exchanged again until it expires.
  5. sub must be a valid user id and not the reserved id system.
  6. The OBO token: sub = the user, act.sub = the client, the client's roles (any roles in the assertion are ignored), and exp no later than the assertion's exp or CYODA_JWT_EXPIRY_SECONDS from now, whichever is earlier.
  7. An on-behalf-of client only exchanges: client_credentials refuses it. An OBO token cannot open a compute-node stream.

Answers: 200 with the token; 400 for a malformed request, a refused parameter, a bad or unknown key, a bad signature or claim, or a bad sub (invalid_request), a wrong grant for the client (unauthorized_client) or an unknown grant (unsupported_grant_type); 401 invalid_client for failed client authentication; 403 access_denied for a tenant mismatch; 405 for a method other than POST; 429 slow_down over the per-client rate; 503 temporarily_unavailable when the client or trusted-key store cannot be read or no secret-check slot frees up within 1 second; 500 server_error with a ticket for any other store failure or a signing failure. Every error_description is a fixed string listed in cyoda help auth tokens.

Segregation of duties: "the submitter may not approve"

  1. Require authtype == "user": a client's own work and cyoda's own are not a person approving.
  2. Require authexectype == "service": a scheduled firing carries the user who armed it in authid, with executor system; that user did not approve now.
  3. Compare authid with the submitter's id byte for byte: copy authid into the entity when the user submits, or read the submit change's actor.id (with actor.kind == "user") from GET /audit/entity/{entityId}. Nothing is normalised.
  4. Optionally require authexecid to be one of your OBO client ids, kept in configuration and updated on rotation. A write-back cascade's callouts name the compute node's client as executor and fail such a check.

Go compute nodes can use the public package github.com/cyoda-platform/cyoda-go/api/grpc/authctx: Type/ID, ExecutorType/ExecutorID, Roles, and Require(ce, role), which is true only for a service executor holding the role — it says nothing about the user. Change history over HTTP (GET /entity/{entityId}/changes) returns user, attributedKind and executedBy; over gRPC, EntityChangesMetadataGetRequest returns user only. Audit actor.name repeats actor.id; externalId is never set. Async search jobs belong to the tenant, not to a user.

Token lifetime and revocation

  1. A token from /oauth/token lives at most CYODA_JWT_EXPIRY_SECONDS: 300 seconds by default, 3600 at most. An OBO token also ends no later than its assertion's exp; because an assertion lives at most 300 seconds, an OBO token never lives more than 300 seconds past its assertion's iat, whatever CYODA_JWT_EXPIRY_SECONDS says. The operator's CLI command cyoda token signs tokens that live 15 minutes by default, or CYODA_JWT_EXPIRY_SECONDS when that is shorter. There are no refresh tokens: the client repeats the grant or the exchange, and reuses a token until less than about a minute of its life remains.
  2. Every grant reads the client, and every exchange reads the client and the trusted key, from the shared store. Resetting a secret, deleting a client, or invalidating or deleting a trusted key stops new tokens at once on every node.
  3. Tokens issued before the change stay valid until they expire, at most the token lifetime.
  4. A gRPC stream checks its client against the shared store every minute. It closes if the client was deleted, or if the client's secret was reset after the token that opened it was issued. If the store cannot be read, the stream closes as unavailable and the node reconnects.
  5. Issuing a new signing key pair and invalidating every other one with no grace period, the bootstrap key included, ends every cyoda token signed before, for every tenant. It is the platform operator's last resort.

Rotation

  1. Client secret without downtime. Create a second client of the same kind (it needs a free slot under the per-tenant cap), roll every instance onto it, then delete the old client. A reset (PUT /clients/{clientId}/secret) instead refuses the old secret at once and closes the old streams within 60 seconds; use it when a short outage is acceptable or the secret leaked.
  2. Trusted key. Register the new key under a new keyId, switch the backend to it, and invalidate or delete the old key once no assertion signed with it can be in flight (300 seconds). invalidatePrevious: true on registration ends every other key at once.

Rules for the application

  1. Authorize every user action before acting for the user. cyoda-go applies the client's rights, not the user's.
  2. Sign an assertion only for a user the application has authenticated, and give it a short exp, a few minutes at most.
  3. Keep the trusted key's private key, client secrets and cyoda tokens on the server. They must never reach a browser or mobile app.
  4. Use one client per job: one with the on-behalf-of permission for user requests, a plain client for background work, a separate client for each compute node, and an admin client only for administration. This lets you rotate or revoke each part alone and makes the executor name the part; it does not narrow what each plain client may do.
  5. Connect through TLS. cyoda's HTTP and gRPC listeners serve plaintext and have no TLS of their own: TLS is terminated by the ingress, gateway or service mesh in front of them (the Helm chart's ingress.http.tls and ingress.grpc.tls), and every client and compute node verifies the server certificate. Processors may rely on the user and client identity in a callout only over such a connection. Plaintext is for localhost or a private Docker network during development.
  6. Never let an assertion leave the backend: cyoda does not check jti, so anyone holding an unexpired assertion and the OBO client's secret can exchange it again.

Running it locally

Mock mode (CYODA_IAM_MODE=mock, the default) runs every request, with or without a token, as user mock-user-001 in tenant mock-tenant, kind CYODA_IAM_MOCK_KIND (default service), roles CYODA_IAM_MOCK_ROLES. Callouts carry mock-user-001 as both principals, with that kind. With kind user or system, authctx.Require never passes and compute streams are refused. Mock mode has no client store: /oauth/token issues no token and the client and trusted-key endpoints answer 501. On-behalf-of access cannot be exercised in mock mode.

On-behalf-of end to end in jwt mode (also in Docker Compose, with the same variables on the service): the help topic cyoda help auth integration has the full script. In short:

openssl genrsa -out signing.pem 2048
export CYODA_IAM_MODE=jwt CYODA_JWT_SIGNING_KEY_FILE=$PWD/signing.pem \
  CYODA_IAM_TRUSTED_KEY_REGISTRATION_ENABLED=true
cyoda &
ADMIN_TOKEN=$(cyoda token --tenant acme --roles ROLE_ADMIN,ROLE_M2M)
# create the OBO client, register the app key (step 3), then sign an assertion:
b64url() { openssl base64 -A | tr '+/' '-_' | tr -d '='; }
NOW=$(date +%s)
HDR=$(printf '{"alg":"RS256","kid":"app-key-1"}' | b64url)
PAY=$(jq -cn --argjson iat "$NOW" --argjson exp "$((NOW+300))" \
  '{sub:"alice",caas_org_id:"acme",aud:"cyoda",iat:$iat,exp:$exp}' | b64url)
SIG=$(printf '%s.%s' "$HDR" "$PAY" | openssl dgst -sha256 -sign app-key.pem -binary | b64url)
# exchange "$HDR.$PAY.$SIG" as in step 4, then call GET /api/account with the token
