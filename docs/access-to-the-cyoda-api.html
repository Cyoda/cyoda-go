cyoda-go · authentication

Access to the cyoda API

Only M2M clients connect to cyoda-go. An application signs its own users in and decides what each user may do. When it acts for a user, its client exchanges a user assertion the application signed for a cyoda token on the user's behalf (OAuth 2.0 token exchange, RFC 8693). The token carries the client's rights and the user's identity, so cyoda-go records the user and the client with every change and passes both to compute nodes.

Who is responsible for what

cyoda-go keeps tenants apart, checks what each client may do, and records faithfully which client acted and for which user. The application decides who its users are and what each may do. Like any database, cyoda-go cannot protect data from an application that is itself compromised: that responsibility lies with the application.

DecisionMade by
Who the user isThe application, with any sign-in method it chooses.
What the user may doThe application, before it acts for the user. cyoda-go has no per-user permissions.
Which tenant a request acts incyoda-go: always the client's own tenant. No request can name another.
What the client may docyoda-go, from the client's roles and permissions: data access (ROLE_M2M), tenant administration (ROLE_ADMIN), joining as a compute node, acting for users.
Rules inside a workflow that need the userThe application's processors and criteria, which receive the user and the client with each callout, for example to keep the submitter of a request from approving it.

The token exchange

  1. The client authenticates with its id and secret, and must hold the on-behalf-of permission. A per-client rate limit applies to every grant and exchange.
  2. subject_token_type is urn:ietf:params:oauth:token-type:jwt; other RFC 8693 parameters, such as actor_token, are refused.
  3. The trusted key named by the assertion's kid is read from the shared store, in the client's tenant; a key of another tenant is never found. If the store cannot be read, the exchange answers 503.
  4. The assertion's signature, exp and iat (both required, at most 5 minutes apart), aud, its issuer if the key lists issuers, and caas_org_id = the client's tenant are checked.
  5. sub must be a valid user id and not a reserved one, such as system or anything starting with oidc:.
  6. The OBO token: sub = the user, act.sub = the client, the client's roles (any roles in the assertion are ignored), and exp no later than the assertion's exp or CYODA_JWT_EXPIRY_SECONDS from now, whichever is earlier.
  7. An on-behalf-of client only exchanges: client_credentials refuses it. An OBO token cannot open a compute-node stream.

Both identities appear wherever a change is reported: entity change history (GET /entity/{id}/changes), audit events (GET /audit/entity/{id}), and every callout to a compute node, including callouts another node forwards. A callout also carries the executor's roles. A scheduled task keeps the user and the client that armed it.

Token lifetime and revocation

  1. A cyoda token lives CYODA_JWT_EXPIRY_SECONDS: 300 seconds by default, 3600 at most. An OBO token never lives past its assertion's exp. There are no refresh tokens: the client repeats the grant or the exchange, and reuses a token until it nears expiry.
  2. Every grant reads the client, and every exchange reads the client and the trusted key, from the shared store. Resetting a secret, deleting a client, or invalidating or deleting a trusted key stops new tokens at once on every node.
  3. Tokens issued before the change stay valid until they expire, at most the token lifetime.
  4. A gRPC stream checks its client against the shared store every minute. It closes if the client was deleted, if the token that opened it was issued before the client's last secret reset, or if the store cannot be read.
  5. Invalidating every signing key pair, once a replacement is issued, ends every cyoda token for every tenant. It is the platform operator's last resort.

Rules for the application

  1. Authorize every user action before acting for the user. cyoda-go applies the client's rights, not the user's.
  2. Sign an assertion only for a user the application has authenticated, and give it a short exp, a few minutes at most.
  3. Keep the trusted key's private key, client secrets and cyoda tokens on the server. They must never reach a browser or mobile app.
  4. Use one client per job: one with the on-behalf-of permission for user requests, a plain client for background work, a separate client for each compute node, and an admin client only for administration.
  5. Connect compute nodes over TLS: processors rely on the user and client identity in each callout.
