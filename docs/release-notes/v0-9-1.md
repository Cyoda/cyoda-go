# Cyoda-Go v0.9.1

A processor decides what a failed callback means.

_Released 24 November 2026 · 1 issue delivered_

v0.9.0 made every callback of a compute node all-or-nothing: a callback that
fails keeps nothing in the transaction it joined. It also made a callback
write that failed with an answer that is not retryable doom that transaction:
the operation failed with `409 TRANSACTION_ROLLBACK_ONLY`, whatever the
processor then answered. That second rule added nothing to correctness — the
failed callback had already kept nothing — and it took the decision away from
the processor. v0.9.1 removes it.

## ✨ Highlights

- **The processor decides.** A failed callback keeps nothing, and the
  transaction goes on. The processor (criterion, schedule function) gets the
  callback's answer and decides whether the operation fails: it can handle the
  error and answer success, or fail.
- **`TRANSACTION_ROLLBACK_ONLY` is gone.** No operation and no callback is
  answered with it any more.
- **The OpenAPI document declares a joined request's `409 CONFLICT`.**

## 🔍 Details

### 🔁 A failed callback

- A failed callback keeps nothing: neither its writes nor its reads. The
  commit does not check what a failed callback read. A read answered with a
  `4xx` that is not retryable keeps what it read, as before.
- Later callbacks under the same callout are served.
- The operation still fails whatever the processor answers when the
  transaction itself can no longer commit: it lost a write race
  (`409 CONFLICT`, retryable for the operation), its session ended
  (`404 TRANSACTION_NOT_FOUND` to the callback), or the server could not undo
  the failed callback's work (`500 SERVER_ERROR` to the callback).
- A compute node that gets an answer of unknown outcome — a
  `503 TRANSACTION_NODE_UNAVAILABLE` that is not retryable, or no answer —
  cannot tell whether its write was kept, and must fail its callout.
- A write refused with `409 COMMIT_IN_JOINED_TRANSACTION` is a failed
  callback like any other: the processor can make that write as an
  independent request, without the transaction token, and go on.

`cyoda help workflows` (A callback that failed), `cyoda help grpc` and
`cyoda help cluster` state the rule.

## ⚠️ Behavioral updates

- An operation whose processor handles a failed callback and answers success
  now commits. In v0.9.0 it failed with `409 TRANSACTION_ROLLBACK_ONLY`.
- A client that matched on `TRANSACTION_ROLLBACK_ONLY` no longer sees it.

## 🧩 Storage plugins

`cyoda-go-spi v0.9.1`, which this binary pins, changes the optional
`TransactionCoordinationCapable` interface. No in-tree backend implements it.
`DiscardScope(ctx)` takes no failure code, `RollbackOnlyError` and
`ErrTxRollbackOnly` are removed, a discard of a completed scope is refused, and
`Seal` fails after any discard that failed. New conformance cases for every
backend check that a read rolled back to a savepoint is not checked at commit.
See the SPI's `CHANGELOG.md` and
[`COMPATIBILITY.md`](https://github.com/Cyoda/cyoda-go/blob/main/COMPATIBILITY.md).

## 📌 Versioning

v0.9.1 is a patch release: a bug fix to the callback contract v0.9.0
introduced. `cyoda-go-spi v0.9.1` is a breaking patch, as an exception: it
backs out the rollback-only mark `v0.9.0` added and adds conformance cases, as
its `### Breaking` section lists.
