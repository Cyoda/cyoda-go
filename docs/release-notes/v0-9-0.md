# Cyoda-Go v0.9.0

One security model, one owner for every piece of work, and one instant a read
can trust — on every node of the cluster.

_Released 22 November 2026 · 41 issues delivered_

v0.9.0 gives cyoda-go a security model you can state in one paragraph and audit
in one place. Only M2M clients reach cyoda-go. Your application authorizes its
own users — it is the party that knows them — and tells cyoda-go who they are
through an on-behalf-of client. cyoda-go then records, on every change, audit
event, callout and message, both the user the work was for and the client that
did it. What that buys:

- **One kind of credential to manage.** A client has a tenant, an id you can
  choose, and a secret you can reset; revoking it ends its tokens within the
  token lifetime, now five minutes by default and never more than an hour, and
  closes its compute streams within a minute. There is no identity-provider
  configuration, no forwarded user token and no second root credential to
  protect.
- **Attribution you can trust.** The user is stated by an assertion your
  application signs with a key registered in its own tenant. A client cannot
  speak for another tenant, and an audit trail shows who a change was for and
  who executed it, not only a token subject.
- **Separated duties.** A tenant's admin manages that tenant's clients and
  keys. Signing keys, the clock and the cluster belong to a platform operator,
  so no tenant can revoke the key every tenant depends on.
- **Safe by default.** Listeners bind loopback unless told otherwise, a node
  that cannot read its key store refuses every token rather than serve a stale
  answer, and a misconfigured IAM mode stops the server instead of starting it
  open.

The same release makes the cluster dependable to build on. Auth state — signing
key pairs and M2M clients — is stored and shared by every node, so a token
issued on one node is good on all of them and, on SQLite and PostgreSQL,
survives a restart. Work has
exactly one owner: a scheduled run is claimed and fenced, so a processor is not
run twice behind your back; a callout that loses its compute member is tried on
another, across nodes, when a repeat is safe; and a callback is all-or-nothing,
so a failed step can no longer leave half its writes in a transaction that then
commits. For an application this means fewer failures to handle, and the ones
that remain say plainly whether to retry.

Reads become predictable too. A write is dated at the instant its transaction
commits, and a point-in-time read is fenced by a cluster-wide consistency time,
so a paged read or a report that passes one consistency time as its
`pointInTime` sees one fixed state of the data on whichever node serves it. A
controllable platform clock lets a test deployment move that time and exercise
scheduled behaviour without waiting for it.

v0.9.0 is a minor release. Before 1.0, a minor release is where breaking
changes go, and this one has many. Read the
[breaking changes](#️-breaking-changes--behavioral-updates) before upgrading. There is no rolling upgrade from v0.8.4: stop the cluster.

## ✨ Highlights

- **M2M-only access with on-behalf-of identity.** Every data operation requires
  `ROLE_M2M`, which every M2M client holds. An on-behalf-of client exchanges a
  user assertion its application signed; the change is attributed to the user
  and executed by the client, and both are recorded.
- **Tenant-scoped clients and a platform operator.** The token endpoint is
  `POST /tenants/{tenant}/oauth/token`, client ids are unique per tenant and
  can be chosen, and cluster-wide administration needs `ROLE_ADMIN` in the
  tenant `PLATFORM`.
- **`cyoda token` replaces the bootstrap client.** It signs a short-lived admin
  token offline with the signing key the deployment already holds.
- **Auth state is the cluster's.** Signing key pairs and M2M clients are stored
  and shared by every node, and on SQLite and PostgreSQL survive a restart.
- **Callout failover.** A callout that never reached a compute member is given
  to another one, across nodes. One that reached a member and got no answer is
  repeated only when that is safe: every criterion and schedule function, and a
  processor that declares `idempotent: true`. Workflow schema moves to 1.5.
- **Callback scopes.** Each callback is all-or-nothing; a callback write that
  fails with an error that is not retryable makes the owner's transaction
  rollback-only; a replaced compute member is
  fenced; a callback never commits the transaction it joined.
- **Every scheduled run has one owner.** Nodes claim due tasks from storage,
  and the scheduler never repeats a processor that is not declared idempotent.
  A task can end `FAILED`, and `GET /scheduled-tasks` lists the tenant's
  waiting, running and failed tasks.
- **A consistency time for point-in-time reads.** `GET /entity/consistency-time`
  returns the latest instant at which a read is final on every node; a read
  later than it is refused instead of answered early.
- **One version per entity per transaction, and unique keys checked at
  commit**, on every backend. A schema extension commits on its own and never
  conflicts.
- **Conditions say what they test.** An operator that does not apply to the
  field's type, a missing operand, and an `array` clause that tests nothing are
  refused — several of them used to match every entity on conditional delete.
- **Typed JSON and query parameters are read strictly.** A misspelt member or
  parameter is a `400`, not a silently different request.
- **A generated client works.** Every polymorphic type in the OpenAPI document
  carries a discriminator mapping, every CloudEvent type has a published
  schema, and from this release the contract grows by addition only.
- **Cluster operations.** `GET /platform/cluster`, node lifecycle states, the
  standard gRPC health service, loopback bind by default, and a controllable
  platform clock for tests.

## 🔍 Details

### 🔑 Access: only M2M clients reach cyoda-go

cyoda-go has no per-user permissions, and it no longer pretends to hold user
sessions. An application is the party that knows its users and decides what
they may do; cyoda-go's job is to record truthfully who a change was for and
who made it.

- **Every API operation requires `ROLE_M2M`**, except `GET /account`,
  `GET /platform/clock` and the operations guarded by their own admin or
  operator rule. A caller without it gets `403 FORBIDDEN` before the operation
  runs; every gRPC method answers `PermissionDenied`, except the health `Check`.
- **An on-behalf-of client acts for a user.** Created with
  `POST /clients?onBehalfOf=true`, it exchanges a user assertion — signed with a
  trusted key of its own tenant, `aud` the cyoda issuer, at most 300 s long —
  for a token carrying the client's roles, never the assertion's. The token
  exchange is for on-behalf-of clients only; client credentials are for the
  others. An on-behalf-of client cannot be created in the tenant `PLATFORM` or
  hold `ROLE_ADMIN`.
- **Attribution has two parts everywhere.** Entity changes, audit events and
  messages record the attributed principal and the executor; a scheduled task
  records, as `armedBy`, the attributed principal of the write that armed it.
  A callout carries `authid`/`authtype` for the attributed principal and the
  new `authexecid`/`authexectype` for the executor. A compute node that used
  `authid` as "the request's caller" must read `authexecid` instead. A
  callout's `authclaims` are the executor client's roles, never the user's.
- **A compute node connects with its own client-credentials token.** An
  on-behalf-of token cannot open a stream or administer. A stream closes within
  a minute of its client being deleted or its secret reset. In mock IAM,
  `CYODA_IAM_MOCK_KIND` now defaults to `service` (was `user`), so a compute
  node can connect; with `user` it cannot.
- **An on-behalf-of callback may join only its own user's transaction**
  (`403 FORBIDDEN` otherwise).
- **The OIDC provider endpoints, their error codes and the `CYODA_OIDC_*`
  settings are removed.** `cyoda help auth integration` is the step-by-step
  guide for application teams, with a section on moving from OIDC and forwarded
  identity-provider tokens; `docs/access-to-the-cyoda-api.html` carries the same
  guide with scenario diagrams.

**Tenant-scoped clients.** The token endpoint is
`POST /tenants/{tenant}/oauth/token`; `/oauth/token` is gone. A client
id is unique within its tenant and can be chosen (`POST /clients?clientId=`,
`409 M2M_CLIENT_EXISTS` when taken). A per-tenant cap,
`CYODA_IAM_M2M_CLIENT_MAX_PER_TENANT` (default `100`), answers
`400 M2M_CLIENT_CAP_REACHED`. Clients now live in the cluster's store: a create,
reset or delete takes effect on every node when it returns, where a client used
to exist only on the node that created it and vanish on restart.

The token endpoint is rate-limited per client and node,
`CYODA_IAM_TOKEN_REQUESTS_PER_MINUTE` (default `600`, answered
`429 slow_down`), and the secret checks it runs at once are bounded by
`CYODA_IAM_TOKEN_MAX_CONCURRENT_SECRET_CHECKS` (`503 temporarily_unavailable`;
`503 SERVER_BUSY` on `POST /clients` and a secret reset).

**The platform operator.** The signing key-pair endpoints, `/admin/log-level`,
`/admin/trace-sampler`, `POST /platform/clock` and `GET /platform/cluster`
accept only `ROLE_ADMIN` in the tenant `PLATFORM` (in JWT mode; an
on-behalf-of token is refused whatever its roles). Before, any tenant's admin
could revoke the signing key for the whole cluster.

**`cyoda token`.** `cyoda token --tenant <tenant>` signs a short-lived admin
token offline with `CYODA_JWT_SIGNING_KEY` and prints it. It opens no store and
makes no network call. The bootstrap M2M client it replaces was a second root
credential, weaker than the first: whoever holds the signing key can already
sign any admin token. In Kubernetes, `kubectl exec <pod> -- /cyoda token
--tenant <tenant>`; create the clients applications use with that token. The
default roles are `ROLE_ADMIN` only — add `--roles ROLE_ADMIN,ROLE_M2M` to
reach data.

### 🗝️ Signing keys, trusted keys and identifiers

- **Signing key pairs are shared and persisted by the cluster.** A
  runtime-issued key pair used to work only on the node that issued it: a token
  signed with one was rejected by every other node, and the key pair did not
  survive a restart (it now does, on SQLite and PostgreSQL). A node that
  cannot read the key store for ten reconcile intervals fails closed and
  refuses every key; it does not serve a stale answer.
- **A key pair signs and verifies only inside its validity window**, and an
  invalidated key pair verifies until the end of its grace period — at most
  3600 s, the longest token lifetime — and no longer.
- **A rotation no longer ends the key from `CYODA_JWT_SIGNING_KEY`**, so
  `cyoda token` keeps working through routine key management. Only an
  invalidate or delete that names its key id ends it, and on SQLite and
  PostgreSQL that is now durable across restarts.
- **Token lifetime is bounded.** `CYODA_JWT_EXPIRY_SECONDS` must be 1–3600 and
  defaults to `300` (was `3600`, and accepted up to a year).
- **Trusted keys verify the token exchange's subject token only**, have key ids
  unique per tenant (the same id may exist in two tenants), have no audience
  and no grace period, and are read from the store on every exchange. An
  invalidate request carries no body. Registration refuses a JWK carrying a
  private member or an RSA modulus under 2048 bits, and stores only the public
  members.
- **A tenant id has a grammar** — `^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`, case
  significant — enforced wherever a tenant id enters cyoda-go. `SYSTEM`, in any
  letter case, is refused wherever a tenant id enters.
- **A user id has one rule at every door**: valid UTF-8, 1 to 255 characters,
  no control character, noncharacter or U+FFFD; `system`, in any letter case,
  is reserved as a user id and a client id.
- **`CYODA_IAM_MODE` must be `mock` or `jwt`.** Any other value used to start
  the server in mock authentication, every request running as the mock admin,
  without the mock-mode warning.

### 📞 Callouts: failover, and the rule for a repeat

A callout — a processor, a function criterion or a schedule function sent to a
compute member — used to be sent once, to whichever member a map iteration
returned first. It is now tried on more than one member, across nodes, under
one rule about when a repeat is allowed.

The dividing line is the hand-off: the moment the work is on a member's
connection. Work that never got there is tried elsewhere while tries remain,
whatever the callout is. Work that did,
and then got no answer, is tried elsewhere only when a repeat is safe: every
criterion, every schedule function, and a processor whose `config` declares the
new **`idempotent: true`** — the author's statement that running it more than
once, possibly at the same time on two members, equals running it once, in
cyoda-go and in every system it touches.

- `retryPolicy` selects the number of tries (`NONE`: one; `FIXED` or unset: one
  plus `CYODA_RETRY_FIXED_NUM_RETRIES`, default `3`). The hard limit on time is
  `tries × answer limit + CYODA_DISPATCH_WAIT_TIMEOUT +
  CYODA_CALLOUT_HANDOVER_ALLOWANCE`, where the answer limit is the callout's
  `responseTimeoutMs` or the new `CYODA_CALLOUT_RESPONSE_TIMEOUT_MS` (default
  `30000`) — 155 s at the defaults, 275 s for a callout at the 60 s bound.
- In a cluster, the node holding the transaction tries its own members and then
  offers the callout to one peer node after another, in random order, each
  connection attempt bounded by the new `CYODA_DISPATCH_CONNECT_TIMEOUT`
  (default `2s`). Every try carries the same `requestId`, so a member that
  de-duplicates on it recognises a repeat.
- On each node, members are picked round robin among the tenant's matching
  members.
- When the callout runs out of tries or time after more than one try, the
  client gets the new retryable **`503 CALLOUT_FAILED`**, listing them. A
  failure that forbids another try — a member's `success: false`, an unreadable
  answer, no answer from a processor not declared idempotent — answers its own
  code, as does a callout that made one try.
- A callout with no matching member waits `CYODA_DISPATCH_WAIT_TIMEOUT`
  (default `5s`) for one to attach, on a single node too, before answering
  `503 NO_COMPUTE_MEMBER_FOR_TAG`.
- `responseTimeoutMs` is bounded by `CYODA_CALLOUT_RESPONSE_TIMEOUT_MAX_MS`
  (default `60000`) at import, so that all tries of a callout fit inside
  PostgreSQL's idle-in-transaction ceiling (5 minutes by default) that would
  otherwise abort it.

**What a compute member's answer means is now stated.** An answer that omits
`success` is a success, as the published schema always said; a member reporting
a failure must send `success: false` explicitly — an `error` object without it
is a success, and `"success": null` is unreadable. A criteria answer that omits
`matches` is refused rather than read as `false` — a criterion decides a
transition, and no verdict is not a verdict. An answer that arrives and cannot
be read ends its callout at once with `400 WORKFLOW_FAILED`, naming why, instead
of being waited out and reported as a timeout. A member's own failure message,
its `retryable` verdict and its warnings now reach the client, from whichever
node the member was attached to; each piece of member text is cut at 512
characters. A `success: false` answer ends the callout: it is never tried on
another member, whatever its `retryable` says.

Workflow schema moves 1.4 → 1.5: `idempotent` on a processor's `config`,
`retryPolicy` on `schedule.function`, and function conditions inside `AND`,
`OR` and `NOT` groups. 1.5 also refuses inputs 1.4 accepted (see the breaking
changes). Schemas 1.1 through 1.5 are accepted. See
`docs/cloud-parity/callout-failover.md`.

### 🔁 Callbacks: all-or-nothing, fenced, never committing

A callback is a request a compute member makes during a callout, carrying the
transaction token so that it runs inside the operation's transaction. Four
things about it were wrong, and each could commit something nobody intended.

- **Each callback is all-or-nothing.** It runs in a scope of its own: either
  all its writes become part of the transaction or none do (a schema extension
  it made stays either way), and a `2xx` is sent only for a callback whose
  writes were kept. Before, a failed callback's writes stayed in the
  transaction and the operation could commit them.
- **A failed callback write fails the operation.** A callback write answered
  with an error that is not retryable makes the transaction rollback-only: the
  operation fails with the new **`409 TRANSACTION_ROLLBACK_ONLY`**, whatever
  the compute member goes on to answer — or, when the transaction lost a write
  race, with the retryable `409 CONFLICT`. Under an `ASYNC_NEW_TX` processor
  only that processor fails. A retryable error leaves the transaction usable,
  so the callback can be sent again.
- **A callback never commits the transaction it joined.** A callback write whose
  workflow reached a `COMMIT_BEFORE_DISPATCH` processor used to commit the
  calling operation's transaction part-way through, and the operation carried
  on in a transaction that no longer existed. It is refused with
  `409 COMMIT_IN_JOINED_TRANSACTION`. A joined collection write is no longer
  split into `transactionWindow` chunks, for the same reason, and a joined
  request that sets `transactionWindow` is refused with `400 BAD_REQUEST`.
- **A replaced member is fenced.** A transaction token is minted per try and is
  accepted only while the callout it was issued for is still that member's;
  after that, `410 CALLOUT_SUPERSEDED`. A slow member's write can no longer land
  after its replacement has answered — or, under `ASYNC_NEW_TX`, after the
  failed processor's savepoint was undone.

On the in-tree backends the callbacks of one transaction are served one at a
time, reads included. Two at once used to crash the node on memory and SQLite
(`concurrent map writes`) and fail with `conn busy` on PostgreSQL. A member that
parallelises its callbacks gains nothing; send them in series. The queue is
bounded by `CYODA_CALLOUT_JOINED_MAX_WAITERS` (`503 TOO_MANY_JOINED_REQUESTS`),
and a callback's answer by `CYODA_CALLOUT_JOINED_RESPONSE_MAX_BYTES`
(`413 JOINED_RESPONSE_TOO_LARGE`).

**A callback read returns the entity as the workflow has it** — including the
changes earlier processors returned, and on a create the entity is found.

The rule that goes with it: a processor, a function criterion and a schedule
function must never write or delete the entity they run for, nor any entity
whose workflow is running in the same transaction. A processor changes its
entity only through the data it returns. The engine does not refuse such a
write; it is a design rule for the compute author. Writing other entities
through the token is unchanged.

**Model and workflow administration never runs inside a transaction.** A request
carrying a transaction token that imports a workflow or changes a model is
refused with `400 MODEL_ADMIN_IN_JOINED_TRANSACTION`.

A storage plugin can now supply transaction coordination itself, through an
optional SPI capability, and get location-independent transactions: every node
serves a callback where it lands, with no proxy hop. None of the in-tree
backends offers it. See `docs/cloud-parity/callback-scopes.md`.

### ⏰ Scheduled transitions have one owner

One node used to scan for due tasks and hand them round robin to its peers; a
task still running after 30 seconds was started a second time, so its
processors could run twice — and a single callout at its default timeout took
30 seconds.

Every node now claims due tasks from storage and runs them itself. A claimed
task has one owner at a time, every write of the run is checked against that
claim, and another node takes a task over only after the owner's heartbeats
have stopped for `CYODA_SCHEDULER_STALE_AFTER` (default `2m`).

- **The scheduler never runs a processor twice unless it is declared
  `idempotent`.** If a processor that is not may have reached a compute member
  and the run does not commit, the task ends `FAILED` and is not run again. A
  run that failed with nothing unsafe handed off is retried, with a delay that
  doubles from `30s` up to `15m`, until the transition's `timeoutMs` passes
  (then `FAILED`), or without end when it has none.
- **A task can end `FAILED`**, with a reason (`UNSAFE_WORK_NOT_COMPLETED`,
  `STOPPED_AFTER_PARTIAL_COMMIT`, `EXPIRED_AFTER_FAILED_ATTEMPTS`,
  `OWNER_LOST_REPEATEDLY`, `RUN_PANICKED`). It is kept, logged at ERROR with a
  ticket, and recorded on the entity as the new audit event
  `SCHEDULED_TRANSITION_FAIL`. A failed task never moves its entity; an entity
  write in the source state arms it afresh.
- **`GET /scheduled-tasks`** lists the tenant's tasks by status, model and
  entity, with attempts, lost owners, last error and failure reason.
- **One scheduled transition of an entity runs at a time.**
- **Entity writes, deletes and workflow imports remove the tasks they make
  moot**, in the same transaction, and can answer a retryable `409 CONFLICT`
  when they race the scheduler — the conditional and delete-all
  `DELETE /entity/{entityName}/{modelVersion}` included.
- **A node withdrawn after a recovered panic claims nothing.** It used to keep
  its share of every scan.
- **Shutdown drains scheduled runs first.** A run with a non-idempotent
  processor in flight is allowed to finish rather than be cut and end `FAILED`,
  so a node can take more than six minutes to stop; the Helm chart sets
  `terminationGracePeriodSeconds: 390`.

The scheduler's settings are replaced whole — see the breaking-changes list and
`cyoda help config scheduler`. See also `cyoda help scheduled-tasks` and
`docs/cloud-parity/scheduled-transitions.md`.

### 🕰️ Time: commit stamps, the consistency time, the platform clock

**A write is dated at the instant its transaction commits.** PostgreSQL dated a
write at transaction start, so a read at an instant between a transaction's
start and its commit missed its writes, and the same read after the commit
found them: the past changed after it had been served. A transaction's writes
now share its commit instant — `creationDate`, `lastUpdateTime`, the
submit time and audit timestamps included — on every backend. A caller-supplied
`creationDate` is ignored everywhere.

**A point-in-time read is fenced by the consistency time.** The consistency
time is the latest instant at which a read is final: it includes every save
confirmed before it on any node, and no later save can land at or before it. A
read at a `pointInTime` later than it is refused with
`400 POINT_IN_TIME_AFTER_CONSISTENCY_TIME`, on every read that takes
`pointInTime`, HTTP and gRPC. These reads, and the consistency-time read
itself, can also answer the new retryable
`503 CONSISTENCY_TIME_UNAVAILABLE` when the store cannot certify the
consistency time in time. There is no waiting: a client that used to send
"now" from its own clock takes the instant from the new
`GET /entity/consistency-time` (gRPC `EntityConsistencyTimeGetRequest`), and a
read at a time returned there is never refused, on any node. `cyoda help crud`
shows how to read a list in consistent pages with it. An async search submitted
without `pointInTime` now runs at a fresh consistency time, so it no longer
misses confirmed saves.

The stats reads and gRPC get-all accepted `pointInTime` and ignored it; they
honour it now.

**A point-in-time read costs what the model costs, not what the history
costs** (PostgreSQL). On 10,000 entities of 250 revisions, a search whose
condition matches one entity went from 4.9 s to 178 ms. Transaction submit
times are durable, so `GET /entity/{id}/transitions?transactionId=` answers on
any node and after a restart, for the one-hour retention.

**A controllable platform clock, for tests.** With
`CYODA_CLOCK_CONTROL_ENABLED=true` (off by default), a platform operator can
set the clock to an earlier time, move it forward or change its rate through
`POST /platform/clock`. An earlier time is refused if it is before the latest
time the store has recorded (`409 CLOCK_BEFORE_RECORDED_TIME`), so in practice
it is for a fresh store. Revision, audit, consistency and scheduled times
follow the clock, and a move forward fires each scheduled transition at its
due time; authentication, timeouts and leases stay on real time. A change
answers only once every node of the cluster holds the new setting, and
`503 CLOCK_NOT_CONFIRMED` otherwise. See `cyoda help clock`.

**An async search's `expirationDate` is when it stops being readable.** It
answered `createTime + 24h` while the job was deleted at the first reap after
`CYODA_SEARCH_SNAPSHOT_TTL` (default `1h`) had passed since it finished. It is
now `finishTime + CYODA_SEARCH_SNAPSHOT_TTL` (`createTime` plus the TTL, a lower
bound, while the job runs), and the job stops being readable at that instant on
every backend. A failed async search also
says why, in the new `failureReason`.

### 🧾 Versions, unique keys and schema extensions

- **One version per entity per transaction, on every backend.** A later write
  of an entity the transaction already wrote replaces its pending version.
  `/entity/{id}/changes` and the `EntityChange` audit events carry one entry
  per transaction, and `GET /entity/{id}?transactionId=X` reads committed
  versions only: it returns X's final entity once X has committed.
- **Unique keys are checked at commit, on the final entities.** Two entities
  that swap key values, a chain of moves, and a value freed and claimed in one
  transaction now commit on every backend; each backend used to answer
  differently, sqlite by map order.
- **A schema extension commits on its own and never conflicts.** A write that
  extends a model under its `changeLevel` commits the extension in a short
  transaction of its own. Two writes extending one model both succeed, where
  PostgreSQL answered the second `409` and held a lock on the model for the
  whole transaction, callouts included. The extension stays if the write fails.
  An extension also survives its model being unlocked or re-imported, on every
  backend.
- **An entity's model is fixed for the life of its id**, a storage-level guard
  that no current request triggers, and an entity's data is a JSON object at
  every change level.
- **`If-Match` states the version an update starts from, and is checked once.**
  A write to the entity later in the same transaction — the engine's own write
  before a callout, or a `COMMIT_BEFORE_DISPATCH` segment's commit — no longer
  fails it with `412`. An empty `If-Match` on `PATCH` is
  `428`, as an absent one is; it used to be last-writer-wins.
- **A write race lost inside a transaction answers a retryable `409 CONFLICT`**,
  whatever the transaction did after it, on every backend. It used to surface as
  a ticketed `500`, a `400 WORKFLOW_FAILED` or a `412`.
- **A conditional delete without `transactionSize` is atomic on every backend.**
- **A gRPC `EntityTransitionRequest` no longer writes an older copy of the
  entity over a concurrent write**, and a search fails when stored data does
  not decode rather than returning `data: null` or leaving the entity out.

### 🔎 Conditions say what they test

Several condition shapes were accepted, evaluated against something the caller
did not mean, and — on conditional delete — matched far more than intended.
Each is now refused.

- **An operator that does not apply to the field's type is
  `400 CONDITION_TYPE_MISMATCH`.** A string operator on a number used to be
  evaluated: a positive one answered an empty result and a negated one matched
  every entity with a value there. `NOT_CONTAINS` on a numeric field, in a
  conditional delete, deleted them all. A workflow criterion is checked when it
  is evaluated, so one that used to read as "not satisfied" now fails the save
  or transition with `400 WORKFLOW_FAILED`.
- **An `array` condition carries a required `operatorType`**, applied at every
  tested position. A clause that tests no position — `values` missing, empty or
  all `null` — used to match every entity. Migration: add
  `"operatorType":"EQUALS"` to existing array clauses.
- **A missing or `null` operand is `400 INVALID_CONDITION`** under every
  operator but `IS_NULL` and `NOT_NULL`. It used to compare with an empty
  string, so `CONTAINS` matched every string.
- **An array operand is refused outside `BETWEEN` and `BETWEEN_INCLUSIVE`**,
  and a range must hold two non-null scalar bounds.
- **A conditional delete whose body is only non-JSON white space no longer
  deletes every entity of the model**, and its body is limited to 10 MiB.
- **A condition is checked in one order** — structure, patterns, the model's
  paths, types — so one malformed condition gets the same code on search,
  conditional delete and grouped statistics. A condition tests at most 10,000
  entries.

**Function conditions compose.** A workflow criterion can hold function
conditions at any depth of `AND`, `OR` and `NOT` groups, evaluated in
declaration order with short-circuiting, so a function that evaluation does not
reach makes no callout. A function condition's pre-check
(`function.criterion`) is now evaluated before the function is called; it was
ignored. See `docs/cloud-parity/function-conditions-in-criteria.md`.

### 📐 Typed JSON and query parameters are read strictly

Go's `encoding/json` matched member names ignoring case, let a duplicate member
replace the first, and on most bodies ignored an undeclared one. So one body
could mean two things: a workflow import holding both `"transitions"` and
`"Transitions"` stored a transition sent without `manual` as automatic, and a
compute answer that misspelt `success` was read as a success.

Every HTTP request body, the `data` of every gRPC request event, a compute
member's answer, every condition and every paging cursor is now decoded under
one rule: a name that differs from a declared member only in case, an undeclared
member, a duplicate member and anything after the value are each refused. The
message names the location — a JSON Pointer, or a byte offset where the text is
not JSON — and never a Go type. Over gRPC, an event whose `data` is `null`, and
a required typed member that is `null`, are refused; a `null` member used to
read as its zero value.

Query parameters follow the same rule. **Every HTTP operation refuses a query
parameter it does not declare.** `DELETE /entity/{entityName}/{modelVersion}?PointInTime=…`
with no body used to delete every current entity of the model, because the
misspelt parameter was ignored. Date-time values are read as RFC 3339, exactly
as in a body: a bare date, an empty value, a comma before the fractional
seconds, a one-digit hour and an offset of `+24:00` are refused.

Entity and message payload contents are not typed JSON — no member there is
unknown, and `"a"` and `"A"` are two fields — but a member written twice is
refused in any payload. See
`docs/cloud-parity/strict-member-names.md`.

### 📜 The published contract generates a working client

- **Every polymorphic type in the OpenAPI document is a base with a
  discriminator mapping**, and every condition position is a `$ref` to
  `QueryConditionDto`. Four discriminators used to declare no mapping, so a
  generated client expected schema names where the wire carries `simple`,
  `group`, and so on.
- **Every state-machine audit event carries typed `data`**, one schema per
  event type, never `null`.
- **Every CloudEvent type has a published schema**, and the 47 event schemas
  that built on `BaseEvent` with the draft-03 `extends` keyword — ignored under
  the 2020-12 draft they declare — compose with `allOf` and assert what they
  always appeared to.
- **The document declares the `X-Tx-Token` header and the statuses a joined
  request is answered with**, `410` among them, which appeared nowhere before.
- **`ProblemDetail` declares `ticket`.**
- **HTTP responses carry warnings in `Cyoda-Warning` headers**; they used to be
  returned only in the gRPC `warnings` array.
- **From this release the contract grows by addition only.** A field, a member
  of a base and an event type can be added; nothing published is renamed or
  removed. A client must ignore unknown fields and unknown discriminator
  values. See `cyoda help openapi`.

### 🧭 Audit

Audit events carry an identity: `version` on an entity change, `eventId` on a
state-machine event. Two entity-change events of one transaction used to be
identical on the wire. Events of one instant come back in a fixed order, and
`nextCursor` is the sort key of the last event rather than an offset into a
list rebuilt per request, so a walk no longer repeats or skips rows. `actor`
gains `kind`, and events carry `executedBy`. A failed state-machine audit read
answers `503` or `500` instead of a trail with those events silently missing.

### 🛰️ Cluster and operations

- **`GET /platform/cluster`** lists the cluster's nodes with reachability,
  lifecycle state, database check, version and clock setting, and answers `200`
  only when the cluster is operational. `waitForNodes` waits for a node count.
- **Node lifecycle states** — `STARTING`, `NORMAL`, `DRAINING`, `UNHEALTHY` —
  are gossiped, and counted in the new `cyoda.cluster.member.count` gauge.
- **`grpc.health.v1.Health/Check`** is served without a token, for
  `grpc_health_probe` and Kubernetes `grpc` probes.
- **`/readyz` fails from the start of shutdown**, so a load balancer stops
  sending a draining node new requests.
- **The HTTP and gRPC listeners bind `127.0.0.1` by default**
  (`CYODA_HTTP_BIND_ADDRESS`, `CYODA_GRPC_BIND_ADDRESS`). Both used to bind
  every interface with no way to change it, so a node in mock IAM — where every
  caller is an admin — was reachable from the whole network. The Helm chart and
  the bundled compose files set `0.0.0.0`.
- **A node whose `CYODA_NODE_ID` is already held refuses to start**, and a
  duplicate seen by a serving node is logged at ERROR. Two nodes sharing an id
  used to join silently and be invisible to their peers.
- **A node hosting compute members of more than a handful of tenants no longer
  vanishes from the cluster.** Tenants and tags overflowed the membership
  layer's 512-byte metadata; the lists now travel over its reliable channel.
- **Startup and shutdown are honest.** Every port is bound before anything
  serves, and telemetry
  is flushed when a port cannot be bound or a server fails. A shutdown signal
  that arrives once the ports are bound but before the gRPC server is serving
  is a clean exit. An unrecognised
  `cyoda` argument is a usage error (exit `2`) rather than a server start —
  `cyoda version` used to start a second server against the real data store —
  and `cyoda serve` names the server start explicitly.
- **PostgreSQL pools.** The model store (`CYODA_POSTGRES_MODEL_CONNS`, default
  `8`) and the scheduler (`CYODA_POSTGRES_SCHEDULER_CONNS`, default `10`) run
  on pools of their own, so entity transactions cannot starve them.
- **New instruments** for callouts, the scheduler, the cluster's tag lists and
  refused auth secret checks; see `cyoda help telemetry`.

### 📚 Help, install and release verification

`cyoda help` was corrected against the server and states what cyoda-go does.
New topics: `install`, `design`, `clock`, `config clock`, `scheduled-tasks`,
`auth integration` and `cli token`; `auth oidc` is gone. Seventeen error topics
are new and fourteen are retired — eight codes the server never answered,
`KEY_OWNED_BY_DIFFERENT_TENANT` (key ids are now unique per tenant), and the
five OIDC codes. `cyoda help`
accepts a topic's dotted id (`cyoda help auth.tokens`). `ARCHITECTURE.md` was

`install.sh` verifies signatures again — with `cosign` on `PATH` it had refused
every install — and a chart release no longer takes GitHub's "Latest" mark from
the binary release. A new `Verify release` workflow installs each release the
way users do, after it is published, and the newest stable release weekly: the
install script with
signatures required, the `.deb` and `.rpm` in clean containers, the signed
image, Homebrew and the Helm repository.

Thirty-four new contract documents under `docs/cloud-parity/` (65 in total)
state the behaviours Cyoda Cloud mirrors.

## ⚠️ Breaking changes & behavioral updates

This list is long, and it is not complete: the
[CHANGELOG](https://github.com/Cyoda/cyoda-go/blob/main/CHANGELOG.md) carries
every entry. The short version: re-issue your credentials through the new token
endpoint, declare `idempotent` where a repeat is safe, add `operatorType` to
array clauses, and stop the cluster to upgrade it.

**Upgrade**

- **Every node of a cluster must run this version; there is no rolling
  upgrade.** The node-to-node message changed and is sealed per recipient, and
  an older node fires scheduled tasks without claiming them, so in a mixed
  cluster a task can run twice. Stop the cluster.
- **Every node needs its own `CYODA_NODE_ID`**, and `CYODA_NODE_ID`,
  `CYODA_NODE_ADDR` and `CYODA_GRPC_NODE_ADDR` together must fit 406 bytes.
- **The listeners bind loopback by default.** A deployment reached from other
  hosts, and every container, sets `CYODA_HTTP_BIND_ADDRESS` and
  `CYODA_GRPC_BIND_ADDRESS` to `0.0.0.0`.
- **PostgreSQL migrations `000011`–`000018` and SQLite `000008`–`000014` are
  new.** On PostgreSQL, `000011`–`000013` build indexes and backfill columns
  while blocking writers; size the window to `entities`, `entity_versions` and
  `sm_audit_events`. `000014` briefly blocks readers and writers of
  `scheduled_tasks`. See `docs/plugins/POSTGRES.md`.
- **Each node opens up to 19 more PostgreSQL connections** at the defaults: the
  scheduler pool (`CYODA_POSTGRES_SCHEDULER_CONNS`, `10`) and its heartbeat
  (`1`), and the model pool (`CYODA_POSTGRES_MODEL_CONNS`, `8`). Check
  `max_connections`.
- **Helm chart 0.9.0**: `terminationGracePeriodSeconds: 390`;
  `jwt.expirySeconds` defaults to `300`, at most `3600`; the `bootstrap.*`
  values are gone; with `gateway.enabled=true` (the default) an empty
  `gateway.parentRefs` fails the install; `CYODA_NODE_ADDR` names the HTTP
  port, where it named the gRPC port.
- **The Go module paths are `github.com/cyoda/...`**, for cyoda-go, its plugins
  and `cyoda-go-spi`. An importer changes its imports and `require` lines in
  one change. OpenTelemetry instrumentation scope names change with the paths.
- **Go 1.27.4 is required to build.**

**Access and tokens**

- **The token endpoint is `POST /tenants/{tenant}/oauth/token`**;
  `/oauth/token` is gone.
- **Every API operation requires `ROLE_M2M`** (see the exceptions above).
- **The bootstrap M2M client and all `CYODA_BOOTSTRAP_*` variables are
  removed.** Use `cyoda token`.
- **The OIDC provider endpoints, their error codes and `CYODA_OIDC_*` are
  removed.**
- **Platform-wide admin endpoints need `ROLE_ADMIN` in the tenant `PLATFORM`.**
- **`POST /message` no longer reads `X-User-ID`.**
- **Callouts: `authid` names the attributed principal; `authexecid` names the
  executor; `authclaims` are the executor's roles.** A compute node must
  connect with its own client-credentials token.
- **The token exchange is for on-behalf-of clients only**, and client
  credentials for the others (`400 unauthorized_client`). A rejected assertion
  answers `400 invalid_request` (was `invalid_grant`); the assertion must carry
  `aud` and live at most 300 s; the key must be registered in the client's own
  tenant.
- **The token endpoint can answer `429 slow_down`** (per-client rate limit) and
  `503 temporarily_unavailable` (secret checks bounded).
- **`CYODA_JWT_EXPIRY_SECONDS` defaults to `300` and must be 1–3600.** An empty
  `CYODA_JWT_ISSUER` is refused. `CYODA_IAM_MODE` must be `mock` or `jwt`.
- **`CYODA_IAM_MOCK_KIND` defaults to `service`** (was `user`), and a value
  other than `user`, `service` or `system` stops startup.
- **Signing key pairs and trusted keys have no audience**;
  `CYODA_JWT_BOOTSTRAP_AUDIENCE` is removed. A key pair's grace period is at
  most 3600 s; a trusted key has none, and its invalidate request carries no
  body (`gracePeriodSec` is `400`).
- **A tenant id and a client id must match
  `^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`**; a token whose tenant or user claim is
  outside its rule is an ordinary `401`. The user and client id `system` and
  the tenant `SYSTEM` are reserved, in any letter case.

**Workflows and compute nodes**

- **A criterion and a schedule function can run twice for one callout** — they
  are repeat-safe by rule. Move one that has effects into a processor.
- **A processor is repeated, by failover or by the scheduler, only when it
  declares `idempotent: true`.** A scheduled processor that is safe to repeat
  must now declare it to be retried.
- **A compute member reporting a failure must send `success: false`
  explicitly**; an omitted `success` is a success. A criteria answer must carry
  `matches`.
- **A transaction token is valid only for the try it was minted for.**
  `CYODA_TX_TOKEN_TTL` is removed: a token lives for its try's answer limit
  plus the new `CYODA_CALLOUT_PASS_ALLOWANCE` (default `30s`). A superseded
  member gets `410 CALLOUT_SUPERSEDED` and must stop.
- **A callout must never write or delete the entity it runs for**, nor any
  entity whose workflow is running in the same transaction. A processor
  changes its entity through the data it returns.
- **Callback answers changed.** A callback in a transaction that lost a write
  race gets `409 CONFLICT` with `retryable: false` (the owner retries the
  operation). A callback whose transaction is no longer usable gets
  `404 TRANSACTION_NOT_FOUND`, where a PostgreSQL session ended under it used
  to answer the retryable `503 STORAGE_UNAVAILABLE`. A joined request that sets
  `transactionWindow` is `400 BAD_REQUEST`.
- **Callbacks of one transaction are served one at a time** on the in-tree
  backends. While a callback's own inner callout is out, any other callback of
  the transaction is refused with the retryable `503 TRANSACTION_BUSY`.
- **A failed callback write fails the owning operation**
  (`409 TRANSACTION_ROLLBACK_ONLY`).
- **Model and workflow administration with a transaction token is
  `400 MODEL_ADMIN_IN_JOINED_TRANSACTION`.**
- **A callout payload's `meta.transactionId` is the callout's
  `transactionId`**; a callout without one carries the id of the stored
  version it describes.
- **Workflow schema moves to 1.5.** Update any CI pin reading `"current"`.
- **Workflow import refuses what it used to accept**: a transition without
  `manual`; a processor `type` other than `externalized` or empty; a
  `schedule.delayMs` beside a `schedule.function` (v0.8.3 and v0.8.4 exports
  carry `"delayMs": 0` there — remove it); `startNewTxOnDispatch` inside
  `config` (it belongs beside `executionMode`); a negative `responseTimeoutMs`
  or one above `CYODA_CALLOUT_RESPONSE_TIMEOUT_MAX_MS`; a `retryPolicy` other
  than `NONE` or `FIXED` on a criterion function or a `schedule.function`; and,
  with `400 VALIDATION_FAILED`, a criterion that is not a valid condition — an
  array clause without `operatorType`, a missing or misplaced operand, a
  function condition without `function.name`.
- **A criterion whose operator does not fit the field's type fails the save or
  transition with `400 WORKFLOW_FAILED`**; it used to read as "not satisfied".
- **A client may see the retryable `503 CALLOUT_FAILED`.** A client that
  switches on the code treats it as it treats `DISPATCH_TIMEOUT`,
  `DISPATCH_FORWARD_FAILED` and `COMPUTE_MEMBER_DISCONNECTED`.
- **A client's own timeout ending a callout answers `408 TRANSACTION_TIMEOUT`**,
  not a retryable `503`.
- **The available-transitions list holds only transitions a client can name** —
  not disabled, not scheduled.

**Scheduler**

- **Settings are replaced.** No longer read: `CYODA_SCHEDULER_DISTRIBUTION`,
  `CYODA_SCHEDULER_COORDINATOR`, `CYODA_SCHEDULER_REDISPATCH_BACKOFF`,
  `CYODA_SCHEDULER_BATCH_SIZE`, `CYODA_SCHEDULER_EXPIRY_GRACE` and
  `CYODA_DISPATCH_FORWARD_TIMEOUT`. New: `CYODA_SCHEDULER_MAX_RUNS`,
  `CYODA_SCHEDULER_MAX_RUNS_PER_TENANT`, `CYODA_SCHEDULER_HEARTBEAT_INTERVAL`,
  `CYODA_SCHEDULER_STALE_AFTER`, `CYODA_SCHEDULER_MAX_LOST_OWNERS`,
  `CYODA_SCHEDULER_RETRY_DELAY`, `CYODA_SCHEDULER_RETRY_DELAY_MAX`,
  `CYODA_SCHEDULER_SHUTDOWN_DRAIN`.
- **Scheduler settings are checked at startup.** `CYODA_SCHEDULER_STALE_AFTER`
  must be at least `50s` + 3 × `CYODA_SCHEDULER_HEARTBEAT_INTERVAL`, and
  `CYODA_SCHEDULER_SCAN_INTERVAL` greater than zero; a value outside its rule
  stops startup. Set `CYODA_SCHEDULER_STALE_AFTER` the same on every node.
- **A scheduled task can end `FAILED`**, and the audit event type
  `SCHEDULED_TRANSITION_FAIL` is new. The grace band above `timeoutMs` is gone.
- **`DELETE /entity/{entityId}`, workflow import, and the conditional and
  delete-all `DELETE /entity/{entityName}/{modelVersion}` can answer a
  retryable `409 CONFLICT`** (with `transactionSize`, per entity in
  `idToError`).

**Entity API and reads**

- **A `pointInTime` later than the consistency time is
  `400 POINT_IN_TIME_AFTER_CONSISTENCY_TIME`.** Take the instant from
  `GET /entity/consistency-time` rather than the client's clock. These reads
  can also answer the retryable `503 CONSISTENCY_TIME_UNAVAILABLE`.
- **PostgreSQL timestamps move later**: a write is dated at commit, not at
  transaction start.
- **Every HTTP operation refuses an undeclared query parameter**, a repeated
  scalar one and a malformed query string. `waitForConsistencyAfter`, accepted
  and ignored since v0.8.4, is now refused. A date-time parameter must be
  RFC 3339: `?pointInTime=2024-01-02` and an empty `?pointInTime=` are `400`.
- **Typed JSON must spell its member names exactly, once.** An undeclared,
  duplicate or wrong-case member is refused, as is anything after the value.
- **One version per entity per transaction.** `GET /entity/{id}?transactionId=X`
  reads committed versions only, so a caller inside X gets `404`, where
  PostgreSQL returned X's first uncommitted write; change history carries one
  entry per transaction.
- **Unique keys are checked at commit.** On PostgreSQL a key broken by a joined
  callback is found at the owner's commit, not on the callback request.
- **`If-Match` is checked once, when the update starts.** A change committed by
  another transaction afterwards is a retryable `409 CONFLICT`, where it could
  be `412`. An empty `If-Match` on `PATCH` is `428`.
- **A lost write race is a retryable `409 CONFLICT`** where it could be `500`,
  `400 WORKFLOW_FAILED` or `412`. Retry on it.
- **A conditional delete without `transactionSize` is atomic**: a failed
  entity — other than a lost race, which is retried, or an entity already
  gone — fails the request and deletes nothing, where memory and SQLite
  deleted the rest. With `transactionSize`, each batch is atomic.
- **`DELETE /model/...` answers `MODEL_ALREADY_LOCKED`**, not
  `MODEL_HAS_ENTITIES`.
- **Setting a model's unique keys without `uniqueKeys` is refused**; send `[]`
  to remove them.
- **An entity's data must be a JSON object** at every change level.
- **`CYODA_SCHEMA_EXTEND_MAX_RETRIES` is removed**, and on PostgreSQL
  `CYODA_SCHEMA_SAVEPOINT_INTERVAL` now counts one model's extensions, as on
  SQLite.
- **PostgreSQL: a message saved under a transaction token is no longer part of
  that transaction**, as on memory and SQLite.

**Search and conditions**

- **`400 CONDITION_TYPE_MISMATCH`** for an operator that does not apply to the
  field's type. A string operator on a date, time or UUID field used to match
  its stored text and is now refused; query a date with ordering or range
  operators, e.g. `GREATER_OR_EQUAL "2024"` and `LESS_THAN "2025"`. A string
  operator on `creationDate` or `lastUpdateTime` moves from
  `INVALID_CONDITION` to `CONDITION_TYPE_MISMATCH`.
- **An `array` clause requires `operatorType`.**
- **A missing, `null`, object or misplaced array operand is
  `400 INVALID_CONDITION`**, as is a `BETWEEN` value that is not a two-element
  array (was `BAD_REQUEST`).
- **A condition that does not parse is `400 INVALID_CONDITION`** on direct and
  async search (was `BAD_REQUEST`), and an unknown model is
  `404 MODEL_NOT_FOUND` before the condition is checked.
- **An async search's `expirationDate` is `finishTime` + the snapshot TTL**
  (`createTime` + the TTL while it runs), and the job answers `404` from that
  instant. `CYODA_SEARCH_SNAPSHOT_TTL` and
  `CYODA_SEARCH_REAP_INTERVAL` must be greater than zero.
- **gRPC: cancelling a snapshot that has already ended is refused**, as on
  HTTP.

**Audit and OpenAPI**

- **An audit-events cursor issued before this release answers
  `400 BAD_REQUEST`.**
- **State-machine audit `data` is typed.** `TRANSITION_ABORTED` names the
  transition in `data.transition` (was `transitionName`; absent on a
  loopback). `STATE_PROCESS_RESULT` carries `processorName`, `executionMode`
  (was `mode`) and `success`, plus `failReason` when the compute member sent
  failure text; the schema's never-sent `stateProcessId`,
  `stateProcessClassName` and `stateProcessType` are removed.
- **A client generated from the OpenAPI document gets different class and type
  names**: `AbstractConditionDto` is removed; the enums `AuditEventSeverity`
  and `GroupOperator` are named; scalar condition values and the entity-create
  and model-import bodies are schemas with no `type` instead of a `oneOf`.
- **The outer `eventType` of a state-machine audit event is a plain string**,
  not an `enum`.
- **`grant_type` in the client credentials gains the token-exchange URN**,
  answered for an on-behalf-of client. A value added to a response `enum` is
  breaking: a client generated from the v0.8.4 document cannot read it.
- **Fourteen error codes are retired** — `NOT_FOUND`, `TX_REQUIRED`,
  `TX_CONFLICT`, `TX_COORDINATOR_NOT_CONFIGURED`, `TX_NO_STATE`,
  `CLUSTER_NODE_NOT_REGISTERED`, `IDEMPOTENCY_CONFLICT`,
  `SEARCH_SHARD_TIMEOUT`, `KEY_OWNED_BY_DIFFERENT_TENANT` and the five OIDC
  codes.

**Operational**

- **A node can take more than six minutes to shut down.** Raise the
  termination grace period where you set it yourself.
- **`/readyz` fails from the start of shutdown.**
- **`CYODA_PROXY_TIMEOUT` must be greater than zero.**
- **A callout with no compute member waits `CYODA_DISPATCH_WAIT_TIMEOUT`
  (`5s`) before failing**, on a single node too. Set `0` for a single node's
  old fail-at-once behaviour; in a cluster, `0` also removes the wait v0.8.4
  had. A negative value stops startup.
- **`POST /admin/log-level` refuses an unrecognised level**; it used to
  substitute `info`.
- **An unrecognised `cyoda` argument is a usage error** (exit `2`), not a
  server start.

**SPI (plugin authors)**

Out-of-tree plugins must be rebuilt against `cyoda-go-spi v0.9.0`, under its
new module path `github.com/cyoda/cyoda-go-spi`. There is no deprecation
window on any of the following:

- **`ScheduledTaskStore` is replaced whole**: claims, heartbeats, fenced owner
  writes and task lives.
- **New required methods**: `TransactionManager.LostRace`, `ConsistencyTime`
  and `LatestRecordedTime`; `ScheduledTaskStore.SchedulerActivity`;
  `StoreFactory.Ping`; `KeyValueStore.PutIfAbsent`, `CompareAndPut` and
  `DeleteIfEqual`, with no key-value operation joining a transaction.
- **Changed signatures**: `AsyncSearchStore.ClearResults` takes the claim
  epoch; `EntityStore.Count` and `CountByState` take `asAt`; `DesugarCondition`
  returns an error, and `predicate.ArrayCondition` carries `OperatorType`.
- **Removed**: `ScheduledTask.RedispatchAfter` and `AttemptCount`, and the
  root-package `RunScheduledTaskStoreConformance` (replaced by `spitest`'s
  `ScheduledTasks` group).
- **Changed contracts**: one version per entity per transaction; unique keys
  checked at commit from the store's own model (`WithUniqueKeys` and
  `UniqueKeysFromContext` are removed); `ModelStore.ExtendSchema` commits in
  its own transaction and `Get` ignores the caller's; a transaction's own
  delete is its latest state; a delete of an absent key is not an error;
  savepoint nesting follows SQL semantics; a rollback to a savepoint keeps a
  lost write race; the store assigns an entity's dates, transaction id and
  change type, ignores caller values, and refuses a change of model
  (`ErrEntityModelMismatch`); `StateMachineAuditStore.Record` assigns the
  event id and joins the caller's transaction; messages and state-machine
  events carry the attributed principal and the executor, which a store keeps;
  a plugin given `spi.WithClock` takes every business stamp from it.
- **One operand rule, `ValidateOperand`, refused by the SPI itself**, and
  conditions parsed by the SPI's `strictjson`.
- **`StartNewTxOnDispatch` moves from `ProcessorConfig` to
  `ProcessorDefinition`;** `ExecutionResult` keeps only `State`.
- **Optional**: `TransactionCoordinationCapable`, for location-independent
  transactions.
- **`spitest` gains conformance groups for all of it.** A plugin that does not
  meet them fails its conformance run; the groups for optional capabilities
  (transaction coordination, a business clock) are skipped when the plugin
  does not offer them.

See
[`COMPATIBILITY.md`](https://github.com/Cyoda/cyoda-go/blob/main/COMPATIBILITY.md)
for the full list of obligations.

## 🛡️ Security

- **A cross-tenant token grant is closed.** The token exchange found the key
  that verifies a subject token by `kid` across every tenant, and bound the
  result to a tenant only through a claim the key holder writes. A holder of a
  trusted key registered in one tenant, with the credentials of any M2M client
  of another, could get a token for that other tenant with any user id and
  roles. The key is now looked up in the exchanging client's tenant only.
- **A tenant admin can no longer manage the cluster's signing key pairs.**
  Those endpoints need a platform operator.
- **The tenant id cannot spell a path.** The in-memory backend built a message
  blob's path from the raw tenant id, so on a case-insensitive filesystem two
  tenants whose ids differ only in case shared a directory, and one could read
  the other's bytes. Both path segments are now hex-encoded under an `os.Root`:
  a traversing, colliding or case-folding name is unrepresentable rather than
  rejected. The tenant id also has a grammar at every entry.
- **A cross-tenant existence oracle is closed.**
  `GET /entity/{id}/transitions?transactionId=` no longer tells another
  tenant's transaction from a missing one, and no longer puts raw storage error
  text in a `400`. A node's own internal error text no longer reaches a
  client in a callout failure either, where it could quote bytes of an entity
  payload.
- **A callout may not run as one tenant over another's entity.** A hand-over
  between nodes carried two tenants and nothing compared them.
- **Answers between nodes are authenticated.** The answer to a handed-over
  callout could be replaced by anyone on the network path; it is now sealed for
  the one request it answers and the node it was sent to.
- **Listeners bind loopback by default**, so a node in mock IAM is not
  reachable from the network unless it is told to be.
- **Trusted-key registration refuses a JWK carrying private members** and no
  longer stores or returns them.
- **Responses that carry a credential are never cached**, and the token
  endpoint refuses any query parameter, so a credential never travels in a
  URL.
- **Conditional delete reads at most 10 MiB of condition body.**
- **The Go module paths no longer name an organization nobody owns.** The
  earlier `cyoda-platform` name is only redirected by GitHub; anyone who
  registered it could serve new versions of those paths.
- **Token endpoint hardening.** Token requests are rate-limited per client,
  concurrent secret checks are bounded, and a refused client is answered no
  faster than 500 ms, so the answer's timing does not tell an anonymous caller
  whether a tenant has that client.
- **Dependencies.** Go 1.27.4 clears GO-2026-6809 and GO-2026-6859; the move
  to Go 1.26.9 with `golang.org/x/net` v0.60.0 (now v0.61.0) cleared twelve
  reachable advisories; `klauspost/compress` v1.20.2 clears GO-2026-6865.

## 📌 Versioning

v0.9.0 is a minor release. Pre-1.0 the minor component is the breaking-change
signal, and this release changes the HTTP and gRPC contract, the compute-node
contract, the access model, the cluster wire format and the SPI — listed under
[Breaking changes](#️-breaking-changes--behavioral-updates) above. From this
release the published API contract grows by addition only.

`cyoda-go-spi v0.9.0`, which this binary pins, ships its own breaking changes.
It is versioned on an independent axis from the binary — see
[`COMPATIBILITY.md`](https://github.com/Cyoda/cyoda-go/blob/main/COMPATIBILITY.md)
for the supported combinations.
